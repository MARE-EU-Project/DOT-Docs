SFC integration handoff

This page is the implementation handoff from DOT-Design to Security Function Composer (SFC) maintainers. It defines the DOT-owned discovery and resolution contract, identifies the information that remains composer-owned, and records the evidence available in this repository.

This handoff is informational. It does not prescribe or modify the SFC-owned schema. SFC continues to own wires, exposed anchors, transformations, and composition policy. DOT-Design owns the anchors model, Contract resolution, deployment bindings, and their validation rules.

For the complete ownership model, DOT JSON examples, wire and materializer semantics, lifecycle behavior, and extension guidance, see DOT Anchors and Composition. The versioned, executable integration contract is documented in DOT Anchor consumer acceptance.

Integration boundary

A DOT declares stable logical anchors. A contract-backed anchor references an authoritative contract already declared by that DOT and selects one operation. It does not repeat direction, transport, media type, message schema, or security facts from the contract.

{
  "id": "a0000000-0000-4000-8000-000000000001",
  "name": "submit-alert-http",
  "role": "PROVIDES",
  "semanticTypes": ["urn:mare:security:alert"],
  "contract": {
    "id": "11111111-1111-4111-8111-111111111111",
    "selector": "#/paths/~1alerts/post"
  }
}

A contractless anchor is reserved for an interaction without a supported authoritative contract. Only that form declares the missing communication facts explicitly:

{
  "id": "a0000000-0000-4000-8000-000000000006",
  "name": "packet-stream",
  "role": "PROVIDES",
  "semanticTypes": ["urn:mare:security:packet-stream"],
  "direction": "EGRESS",
  "protocols": ["TCP"],
  "mediaTypes": ["application/octet-stream"]
}

anchors is the normative DOT field. SFC may expose an anchor or connect two anchors, but DOT does not define SFC’s wire/exposure object shape.

Stable references

SFC should persist the DOT identity/version selected for a composition and the anchor UUID. Anchor names are display labels and may change.

The following is a non-normative illustration, not an SFC schema proposal:

from:
  dotId: d0000000-0000-4000-8000-000000000001
  dotVersion: 1.0.0
  anchorId: a0000000-0000-4000-8000-000000000002
to:
  dotId: d0000000-0000-4000-8000-000000000001
  dotVersion: 1.0.0
  anchorId: a0000000-0000-4000-8000-000000000003

The same logical anchor keeps its UUID across compatible DOT versions. Renames and documentation changes do not create a new identity. An incompatible semantic replacement uses a new UUID. Cross-version enforcement and future deprecation/replacement metadata remain publishing-governance work.

Selector conventions

Contract standard Anchor selector

OpenAPI

RFC 6901 URI-fragment JSON Pointer to an Operation Object, for example #/paths/~1alerts/post

AsyncAPI

RFC 6901 URI-fragment JSON Pointer to an Operation Object, for example #/operations/publishAlert

Protobuf

Fully qualified service method, for example mare.security.AlertService.PublishAlert

GraphQL

Root-field schema coordinate, for example Mutation.publishAlert

Selector syntax is checked in the DOT model. Parsing the authoritative payload and proving that the selected element exists occurs in the Registry.

URI-fragment percent encoding is required for characters which cannot appear literally. For example, /routes/{id} is represented by #/paths/1routes1%7Bid%7D/put; the Registry decodes the URI fragment before applying the JSON Pointer.

Registry API

The consumer endpoints are:

  • GET /dots/{dotId}/anchors

  • GET /dots/{dotId}/anchors/{anchorId}

  • GET /dots/{dotId}/anchors/resolved

  • GET /dots/{dotId}/anchors/{anchorId}/resolved

  • GET /contracts/{contractId}

Prefer the resolved endpoints for composition decisions. Their versioned response contains contract metadata but intentionally omits the potentially large payload:

{
  "apiVersion": "1",
  "anchor": {
    "id": "a0000000-0000-4000-8000-000000000001",
    "name": "submit-alert-http",
    "role": "PROVIDES",
    "semanticTypes": ["urn:mare:security:alert"],
    "contract": {
      "id": "11111111-1111-4111-8111-111111111111",
      "selector": "#/paths/~1alerts/post"
    }
  },
  "contract": {
    "id": "11111111-1111-4111-8111-111111111111",
    "name": "alert-http-api",
    "version": "1.0.0",
    "standard": "OPENAPI",
    "format": "YAML"
  },
  "selectedElement": {
    "selector": "#/paths/~1alerts/post",
    "identifier": "submitAlert",
    "interaction": "REQUEST_RESPONSE",
    "protocols": ["HTTPS"],
    "mediaTypes": ["application/json"],
    "inputSchemas": ["#/components/schemas/Alert"],
    "outputSchemas": ["#/components/schemas/Receipt"],
    "securitySchemes": ["oauth2"]
  }
}

For a contractless anchor, contract and selectedElement are null. A dangling contract reference is an error and is never represented as a contractless anchor.

Errors have the stable shape {"code":"…​","message":"…​"}. DOT_NOT_FOUND, ANCHOR_NOT_FOUND, and CONTRACT_NOT_FOUND map to HTTP 404. INVALID_CONTRACT, INVALID_SELECTOR, SELECTOR_NOT_FOUND, and UNSUPPORTED_CONTRACT_FEATURE map to HTTP 422.

Compatibility behavior

The current compatibility evaluator is an internal Registry service; there is no public compatibility endpoint yet. Its result is COMPATIBLE, INCOMPATIBLE, or UNKNOWN. INCOMPATIBLE means a deterministic mismatch was found. UNKNOWN means no mismatch was proved but an external or schema-aware check is still needed.

Stable reason codes are:

  • ROLE_MISMATCH

  • SEMANTIC_TYPES_NOT_DECLARED

  • SEMANTIC_TYPE_MISMATCH

  • INTERACTION_NOT_DERIVABLE

  • INTERACTION_MISMATCH

  • PROTOCOLS_NOT_DERIVABLE

  • PROTOCOL_MISMATCH

  • MEDIA_TYPES_NOT_DERIVABLE

  • MEDIA_TYPE_MISMATCH

  • INPUT_SCHEMA_COMPATIBILITY_UNKNOWN

  • OUTPUT_SCHEMA_COMPATIBILITY_UNKNOWN

  • SECURITY_REQUIREMENTS_NOT_EVALUATED

Exact schema identifiers prove compatibility only inside the same authoritative contract UUID. Cross-contract structural schema comparison, ontology inference, transformations, and deployment-environment security satisfaction are intentionally not guessed.

Runtime handoff

DeploymentService.anchorBindings maps an anchor UUID to a named service port. The deployment layer then resolves the selected service and port name to a live endpoint. SFC should not copy hosts, numeric ports, URLs, credentials, certificates, network slices, or current policy state into the wire’s logical anchor reference.

Reference lifecycle execution

dotx compose apply provides a first reference executor for the provisional composition document. It topologically orders DOT instances from explicit dependsOn readiness constraints while preserving document order among otherwise independent instances, supplies declared instance configuration and explicit wire materializers to the existing single-DOT deploy path, and optionally maps a named exposed anchor to a local port. Kubernetes and Helm workloads must become rollout-ready before the executor advances to a dependent instance. It does not copy those values into an Anchor or infer application configuration from a Contract.

The serialized dot.mare6g.eu/v1alpha1 composition format has a canonical JSON Schema Draft 2020-12 document in DOT-CLI. dotx compose schema emits that exact schema for editor, CI, and third-party composer integration. Every composition is schema-validated before anchor, contract, deployment, and materializer resolution; unknown fields fail closed. JSON Schema defines the portable document shape, while Registry/DOT-CLI semantic validation remains authoritative for graph references and contract compatibility.

Successful applications are recorded under the dotx user cache by composition UUID. dotx compose status inspects each recorded runtime, and dotx compose destroy removes instances in reverse order and deletes state only after successful cleanup. Apply rolls back earlier instances on failure unless the operator requests --keep-on-failure, in which case partial state is kept. Each pending instance is recorded before runtime mutation so an interrupted apply remains discoverable for cleanup or explicit apply --resume. Resume requires the same composition source and runtime options, verifies the resolved plan and pinned-input fingerprint, Docker-network ownership, instance ordering, deployment selections, runtime identities, and the status of every applied instance, then retries only the trailing interrupted instance and remaining suffix. A fully applied compatible composition is an idempotent no-op; input or state drift fails closed. Dry-run mode writes no state and cannot be resumed.

Every planned DOT has a deterministic runtimeIdentity. For DOCKER_IMAGE compositions, apply uses that identity for the container name and network DNS, creates a composition-owned Docker network, and scopes named volumes per instance. Repeated instances of one Docker-image DOT are therefore isolated. Wires describe Anchor connectivity and do not implicitly impose startup order. Composition instances use explicit dependsOn edges for readiness constraints; document order is preserved among otherwise independent instances. This permits reciprocal and brokered connection graphs when endpoint identities are known before startup while still rejecting cycles in the explicit readiness graph. Identical environment materializations shared by several operations are coalesced, while conflicting values fail closed. Before runtime mutation, deployment also rejects any required environment declaration that has neither a DOT-declared defaultValue nor a resolved deploy-time override. Planning remains available for fixtures that intentionally document an incomplete integration boundary. Docker-image dry runs redact values whose DOT declarations mark them as sensitive.

Sensitive instance inputs use reference-only secretRef objects rather than literal values. Each reference identifies an open logical store, a provider-side name, and optional key and version; secret-store credentials remain deployer configuration. The built-in environment store resolves its name only at apply time. Plans and persisted composition state contain the reference, never the resolved value. This follows the explicit access boundary of the Compose Specification secrets model and Kubernetes Secret references without making either platform’s resource schema part of DOT.

Docker image and Docker Compose deployments resolve the built-in environment store only at the final deployment handoff. Kubernetes manifest and Helm deployments accept store: kubernetes with an existing Secret name and key; dotx patches matching Deployments, StatefulSets, and DaemonSets through valueFrom.secretKeyRef without reading the value or claiming ownership of the Secret. Vagrant remains unsupported while its runtime metadata persists environment values. Unsupported stores may still be planned, but apply requires a configured resolver.

The executable slice remains intentionally fail-closed: it rejects UNKNOWN compatibility, readiness-dependency cycles, ambiguous deployment selection, repeated DOT instances for deployment mechanisms whose manifest-owned resource names are not yet isolated, and operation/channel values that cannot yet be derived authoritatively from the selected Contract. It also rejects a materialized wire across different runtime platforms until an explicit cross-platform network binding can establish reachability. Concrete credentials remain outside the composition state.

Known limitations and deferred work

  • Compatibility is internal until its public request identity and policy inputs are stable.

  • Ontology reasoning and cross-contract structural schema comparison require dedicated evaluators.

  • Transformations are composer-owned and must be explicit.

  • Workload identity, mTLS, OAuth scope satisfaction, remote attestation, confidentiality, network-slice, placement, latency, and availability constraints are composition/deployment policy, not anchor fields.

  • Broker-channel, Unix-socket, network-device, eBPF/XDP, WASM import/export, and lifecycle-event bindings require separately reviewed polymorphic binding types. Portable object-store or artifact-registry exchange should normally remain a service Contract; local host paths remain deployment configuration rather than wires.

Acceptance material

The repository’s DOT-Testing/conformance/anchors/ directory contains the complete OpenAPI, AsyncAPI, Protobuf, GraphQL, contractless, binding, failure, and incompatibility examples. It also contains an APISIX/Keycloak scenario derived from SFC requirements while preserving the DOT/SFC ownership boundary. Run task testing:conformance to validate them through Java, the Registry resolvers, generated JSON Schema, and DOT CLI.

DOT-Testing/e2e/api-gateway-oidc/ is the first opt-in live composition scenario. It models Keycloak as the provider of OIDC discovery and OAuth token operations, APISIX as the consumer of discovery and provider of a bearer-protected operation, and a headless OAuth client as the consumer of the token and protected operations. Three composer-owned wires materialize only deployment inputs; the protected wire explicitly binds the OpenAPI security scheme to RFC 6749 client credentials. task testing:e2e:anchors:api-gateway-oidc:dry-run exercises compose apply --dry-run; task testing:e2e:anchors:api-gateway-oidc applies the three-DOT composition, checks recorded status and native Secret references, proves anonymous access is rejected, proves token-authenticated access succeeds, and destroys the composition. The PoC-derived scenario backlog and pinned evidence revisions are documented in DOT-Testing/e2e/USE-CASES.md.

DOT-Testing/composition/federation-peers/ is a read-only PoC11-derived planning and lifecycle-rendering fixture. It resolves two named instances of one federation-agent DOT plus two instances of one local-core adapter DOT. Eight compatible OpenAPI wires cover reciprocal peer receipt and the pinned implementation’s Open5GS subscriber list, add, and modify operations. Each agent explicitly depends only on its local core; reciprocal peer wires do not fabricate a readiness cycle. The dry run proves scoped runtime identities, local-core-first ordering, non-sensitive local/peer node inputs, and both peer/core URL materializers without moving concrete addresses into logical anchors. Run it with task testing:compose:federation-peers. The source-adapted E2E under DOT-Testing/e2e/poc11-federation-peers/ additionally builds pinned revision 303b35351697a0fd3941dccd0feff91144ef4257, deploys two federation agents with two isolated Open5GS-compatible core doubles, and proves reciprocal far-end subscriber updates. This is implementation evidence for subscriber synchronization, not acceptance of PoC11 attestation, governed disclosure, or trust-policy enforcement.

Federated learning and artifact boundaries

The PoC2-derived fixture under DOT-Testing/composition/poc2-federated-inference/ instantiates one Flower trainer DOT twice and connects both instances to one Flower server using the exact flwr.proto.FlowerService.Join bidirectional-stream selector from Flower v1.4.0’s authoritative Protobuf contract. The composer materializes the provider as host:port, which matches Flower’s client input without copying a concrete address into either anchor. Two BentoML inference anchors are exposed separately through a source-derived OpenAPI contract.

The PoC2 task also executes compose apply --dry-run. It proves that the two trainer instances receive unique container identities, share only their composition-owned network, resolve the Flower server through its scoped DNS identity, and do not collide on named volumes. The fixture images are normalization placeholders, so this is lifecycle rendering evidence rather than a live partner-PoC deployment claim.

The pinned PoC publishes model bundles and an atomic current_model.json pointer through a shared host directory. That path is declared as a service volume because it is real deployment configuration, but it is not represented as an Anchor wire. For portable cross-domain deployment, model publication should use a content-addressed artifact service such as the OCI artifact model and OCI Distribution API, optionally complemented by MLflow lifecycle metadata. The registry operation then has an authoritative service Contract and can participate in ordinary Anchor compatibility; artifact digests, provenance, and signatures remain data carried by that protocol rather than new nullable fields on Anchor.

Brokered interactions

For brokered protocols, the semantic producer, semantic consumer, and connection endpoint can be three different components. The PoC6-derived fixture under DOT-Testing/composition/poc6-closed-loop/ therefore keeps distinct AsyncAPI send and receive selectors on the two anchors, selects a Mosquitto service port as the composition-owned connection endpoint, and materializes that endpoint’s host and port into the actuator. The interpreter receives the same selected endpoint through a CACAO 2.0 external playbook variable at execution time, not through an invented deployment field. The MQTT address is not copied into either anchor, while the OpenC2 message shape is described once in the AsyncAPI contract. The current PoC6 fixture reconstructs that contract from pinned source evidence and does not claim it is producer-authoritative. CACAO playbooks remain orchestration artifacts rather than anchor fields. The source-adapted E2E under DOT-Testing/e2e/poc6-cacao-openc2/ proves the chain from the pinned interpreter through MQTT/OpenC2 and the pinned actuator to an isolated NWDAF API; telemetry, AI inference, playbook selection, and a real NWDAF remain outside that acceptance boundary.

Environment-variable materializers declare whether they consume an operation URL, endpoint URL, endpoint host/port, or AsyncAPI channel address. Variable names are never treated as enough information to infer the required value. For OPERATION_URL, the planner resolves the effective OpenAPI server base path and selected operation path, then apply combines that contract fact with the selected deployment service endpoint. For CHANNEL_ADDRESS, it follows the AsyncAPI operation’s local channel reference and uses the channel’s address. The plan exposes these facts as operationPath and channelAddress; neither is duplicated in the DOT Anchor.

AsyncAPI 3 allows a Channel Object address to be absent or null, meaning that it is unknown. Operations that reference the same logical channel can still be compatible in that case, but a CHANNEL_ADDRESS materializer is rejected because no value is available. Channel parameter defaults are applied when the contract supplies them; expressions without defaults remain unresolved.

Automatic materialization is deliberately fail-closed. Multiple distinct effective OpenAPI server paths are ambiguous. OpenAPI path templates and AsyncAPI channel templates accept explicit value-only wire parameters bindings such as realm: {value: drax}. The Contract remains authoritative for the name, location, schema, requirement, and template. DOT-CLI validates those facts, applies AsyncAPI defaults, percent-encodes values, and rejects unknown, empty, incomplete, or still-unresolved bindings. Runtime-derived values, query/header/cookie parameters, and complex serialization styles remain future adapters rather than inferred behavior.

When an application needs a derived URI rather than one of those values verbatim, a materializer may apply an RFC 6570 uriTemplate. The only template variable is value, which is the explicitly selected source value. Reserved expansion such as \{+value}/keycloak/realms/drax preserves an endpoint URI while adding an application-specific path. The transform belongs to the wire; neither the concrete URI nor the realm path belongs in the logical anchor.

The PoC1-derived fixture under DOT-Testing/composition/poc1-ric-aaa/ binds the contract-declared Keycloak token operation’s realm path parameter in a six-DOT RIC AAA feedback loop. Its separate issuer setting remains an explicit URI transform because an issuer is not the JWKS operation URL. Seven wires cover Keycloak JWKS and token acquisition, OPA decisions and deny-list updates, Config API forwarding, proxy metrics, and rogue traffic. The client secret is a declared sensitive deployment input represented in the composition only by an environment store reference; its value never appears in the document, plan, logs, or state. All seven wires are deterministically compatible at composition planning time. The environment-independent Registry keeps the bearer-protected proxy wire UNKNOWN with SECURITY_REQUIREMENTS_NOT_EVALUATED. The composition resolves that reason by binding the contract’s bearerAuth scheme to the RFC 6749 client-credentials mechanism and verifying that the consumer declares and receives its token URL, client ID, and sensitive reference-only client secret. The resulting security.status is CONFIGURED; token validity, issuer trust, and runtime authorization remain acceptance and policy concerns.

The generic APISIX/Keycloak/OAuth-client E2E supplies reusable live acceptance evidence for one concrete client-credentials deployment. The source-adapted PoC1 E2E under DOT-Testing/e2e/poc1-ric-aaa/ goes further: it builds pinned proxy and rogue-xApp modules unchanged behind thin dRAX-SDK bootstraps and executes all seven wires against digest-pinned Keycloak and OPA. A separately labelled controller adapter observes the producer Prometheus counter and JSON-patches OPA’s deny list; a separately labelled Config API double records forwarding. The test proves JWT issuer validation, an allow-to-deny transition, subsequent 403 responses, unauthenticated rejection, exact far-end forwarding counts, and secret isolation from plan and state. This is SOURCE_ADAPTED_E2E; it does not change the meaning of CONFIGURED or claim acceptance of the absent producer AAA xApp, absent RIC Config API, dRAX, or a live RIC.

The PoC5-derived fixture under DOT-Testing/composition/poc5-security-pipeline/ demonstrates a linear multi-stage pipeline built from actual FastAPI forwarding code. Log Analysis provides its events operation to Monitoring, Assessment provides its assessment operation to Log Analysis, and Mitigation provides its operation to Assessment. The three wires materialize endpoint base URLs because the consumers append their known OpenAPI paths. Business data flows from monitoring toward mitigation, while wire from/to continues to mean contract PROVIDES/REQUIRES.

Standards-described contractless composition

The PoC3-derived fixture under DOT-Testing/composition/poc3-insider-threat-pipeline/ uses contractless Anchors for four semantic JSON handoffs across five analytics stages. Unlike an ordinary request/response dependency, each wire explicitly selects the receiving stage as connectionEndpoint; this covers push/ingest dataflow without changing the logical PROVIDES → REQUIRES ownership rule.

That plan intentionally stops at topology and compatibility. The pinned PoC3 services do not call one another, its documented pipeline orchestrator is absent, and its unused PREV_SERVICE_URL settings target a nonexistent route. Sequencing and payload transformation therefore remain composer-owned behavior, not Anchor fields. A standard such as Open Workflow should be evaluated before defining a DOT-specific workflow grammar.

The PoC10-derived fixture under DOT-Testing/composition/poc10-secure-capability-exposure/ combines one reused OpenID Connect discovery contract with four contractless wires for W3C SPARQL, OPA decision/policy APIs, and Prometheus-style metrics. The pinned PoC source identifies those interaction boundaries but does not publish supported producer-owned OpenAPI documents for them. The contractless form therefore records only explicit direction, protocol, media type, and semantic identifiers instead of fabricating a duplicate contract.

dotx compose checks contractless directions, protocols, and media types with the same deterministic rules as the Registry. Both sides must use the same mode: a contract-backed Anchor cannot be wired to a contractless Anchor because that would compare facts with different authority. Concrete GraphDB, OPA, Keycloak, and telemetry addresses remain deployment bindings. Secrets and sample credentials from the PoC deployment are intentionally absent from the DOT and composition documents.

The official PoC10 objective additionally covers third-party event subscriptions, network-behaviour triggers, and automated restriction. Those paths remain explicit coverage gaps until the producers publish supported operations and authoritative Contracts, at which point AsyncAPI, CloudEvents, CAMARA/Open Gateway, or 3GPP CAPIF should be evaluated before defining any new DOT-specific schema.

The PoC9-derived fixture under DOT-Testing/composition/poc9-edge-ddos-collection/ applies the same evidence rule to a heterogeneous collection path. It composes an Amarisoft WebSocket, Open5GS AMF enrichment, InfluxDB ingestion/query, and a FastAPI export using contractless Anchors plus explicit host/port materializers. Credentials remain declared sensitive deployment configuration and never appear in the wires. The official behavioural-detection and dynamic-mitigation outcome is not claimed: Kafka is disabled and has inconsistent topic names at the pinned revision, the copied 3GPP NWDAF OpenAPI files are not wired into runtime code, classification is notebook-only, and no mitigation operation is present.

The PoC8-derived fixture under DOT-Testing/composition/poc8-ndt-observability/ demonstrates the corresponding admission rule for observability. It connects cAdvisor’s Prometheus/OpenMetrics exposition endpoint to Prometheus through a composition-owned configuration file and exposes the pinned MARE FastAPI service separately. A proposed Prometheus-to-enhanced-NDT wire is intentionally absent: the consumer hard-codes localhost, has no bound consumer service endpoint, and provides no explicit endpoint materializer. dotx compose validate therefore prevents that local implementation detail from being represented as a portable connection. Producer-reviewed DOTs should register Prometheus' version-specific OpenAPI document when its HTTP query API becomes a composed boundary; they should not copy a reduced query schema into Anchor fields. PCAP devices, local snapshot files, unwired alert receivers, and absent mitigation remain deployment or implementation gaps rather than logical service wires.

The complementary source-adapted scenario under DOT-Testing/composition/poc8-twin-integrity/ and DOT-Testing/e2e/poc8-twin-integrity/ exercises the official synchronization- integrity objective without redefining a container volume as an Anchor. A thin OpenAPI 3.1 adapter invokes the pinned PoC8 generate_hash.sh and check_hash.sh files unchanged. A separate synchronization-driver DOT receives the resolved checker URL through one Anchor wire and submits a matching and a forged physical/twin snapshot pair. The exposed results Anchor must return the exact producer outcomes, including pcap file corrupted/forged. This promotes only the SHA-256 consistency subset to SOURCE_ADAPTED_E2E; AI anomaly detection, live capture, configuration containment, and mitigation remain explicit gaps.

The PoC4-derived fixture under DOT-Testing/composition/poc4-continuous-monitoring/ extends that rule across a heterogeneous OSS monitoring stack. Five contractless wires connect node-exporter, Prometheus, Filebeat, Elasticsearch, Grafana, and Kibana using official protocol/API semantics and explicit config-file or environment materializers. The pinned PoC publishes no version-matched producer contracts, so the fixture does not fabricate OpenAPI payloads. Product-owned contracts may replace those declarations once exact versions and supported operations are reviewed.

Zeek log directories, tcpdump PCAP output, host networking, packet-capture capabilities, and /proc//sys mounts are not service endpoints. OCI bind sources cover declared host paths, while DeploymentConfig.ociRuntime now declares OCI CAP_* requirements and inherited host namespace types. A composition must grant the exact pinned set explicitly; the DockerImage adapter supports capabilities plus host network/PID/IPC and rejects other namespace or composition-network topologies. Unrestricted privileged mode is intentionally absent. DeploymentConfig.cdiDevices separately declares logical CNCF CDI device requirements by vendor.example/class kind. Composition binds each one to an exact kind-matched vendor.example/class=device; the DockerImage adapter emits only that validated name via --device. CDI specification installation and allocation remain operator/orchestrator concerns. PoC4/PoC8 capture devices can reuse this model when deployable components exist, while eBPF/XDP attachment and portable PCAP artifact exchange remain separate binding/Contract work. Keeping all of this out of Anchor prevents a general-purpose Anchor from accumulating Linux-specific nullable fields. The official MITM detection and automated-mitigation outcome also remains unclaimed because those source components are still under development.

The PoC7-derived fixture under DOT-Testing/composition/poc7-trust-scoring/ tests non-admission without misrepresenting source intent. Its FastAPI trust-scoring operation is exposed as a contractless provider, but the Scapy collector only prints normalized flows to stdout and names REST, Kafka, or OTLP as future work. The valid plan therefore contains both DOTs and zero wires. A negative fixture attempts to inject TRUST_SCORING_URL; planning rejects it because the collector declares no such input. A future producer-reviewed FastAPI OpenAPI export, or a standard event contract such as CloudEvents/AsyncAPI, can become authoritative once the transport exists. Capture-device attachments and Python scoring plugins remain separately typed deployment/artifact concerns. The collector DOT declares CAP_NET_RAW, CAP_NET_ADMIN, and a logical CDI device kind for packet capture; its composition grants the exact capabilities and binds the concrete CDI device name mare6g.eu/network-interface=eth0. A lifecycle dry run proves least-privilege Docker rendering without host networking, host device paths, or --privileged.

The separate executable scenario under DOT-Testing/e2e/poc7-trust-scoring/ keeps that source gap visible while testing a standards-oriented integration. It invokes the pinned collector’s packet aggregation and stdout normalization, then a declared adapter publishes the resulting batch as a CloudEvents 1.0 structured HTTP event. An explicit mediator DOT validates the event and calls the pinned FastAPI scorer through a frozen OpenAPI 3.1 Contract. Two ordinary Anchor wires materialize the mediator and scorer base URLs; no transformation syntax is added to Anchor or hidden inside a wire. The live test verifies the far-end Subjective Logic vector and semantic equality between the registered Contract and runtime /openapi.json. This is SOURCE_ADAPTED_E2E evidence, not acceptance of production capture/CDI, plugin governance, trust-policy quality, or the official ASPO quarantine and retraining response.

dotx compose validates selectors for the same four standards supported by the Registry: OpenAPI, AsyncAPI, Protocol Buffers, and GraphQL. Protocol Buffers and GraphQL payloads are parsed with maintained ecosystem libraries, not repository-local regular expressions.

End-to-end DOT-to-SFC execution remains a joint external acceptance step after the SFC team implements its consumer side.
