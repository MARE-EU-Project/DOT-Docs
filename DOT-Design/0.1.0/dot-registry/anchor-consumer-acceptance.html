DOT Anchor consumer acceptance

The DOT Anchor consumer profile turns the Registry integration boundary into a repeatable acceptance contract. It is intended for composition engines, catalogues, deployment controllers, and the Security Function Composer team. It does not prescribe their internal wire or orchestration model.

The current profile is DOT Anchors consumer profile v1. Its status is release-candidate and its Registry response version is apiVersion: "1".

Profile contents

Artifact Purpose

testing/acceptance/dot-anchors/v1/profile.yaml

Machine-readable manifest that binds the profile version to its source fixture, golden responses, error families, and verification gates.

DOT Registry Anchor Read API v1

OpenAPI 3.1 contract for raw and resolved Anchor reads, schemas, status codes, and stable error codes.

testing/acceptance/dot-anchors/v1/expected/

Complete resolved-Anchor responses generated from the OpenAPI, AsyncAPI, Protobuf, GraphQL, and contractless conformance Anchors.

testing/acceptance/dot-anchors/v1/consumer-checklist.md

Manual checklist for discovery, resolution, composition-boundary checks, and joint runtime acceptance.

AnchorConsumerAcceptanceTests

Executable drift guard connecting the profile to the Java DTOs, Contract resolvers, error taxonomy, and OpenAPI document.

The profile reuses testing/conformance/anchors/valid/; it does not copy the authoritative Contract payloads into a second fixture. The golden responses are consumer-facing outputs, not alternative Contract definitions.

What a conforming consumer must do

A conforming v1 consumer must:

  • address DOTs and Anchors by UUID and reject missing references;

  • recognize resolved response version 1;

  • distinguish contract-backed and contractless Anchors;

  • use the selected Contract element instead of expecting duplicated protocol, schema, media-type, or security metadata in a contract-backed Anchor;

  • support the stable 404 and 422 error families;

  • fail closed on selectors or Contract features it cannot resolve;

  • keep runtime endpoints, credentials, wires, parameter values, readiness, and policy outside the DOT Anchor; and

  • distinguish UNKNOWN compatibility from COMPATIBLE.

The complete operational checklist is maintained with the executable profile so that it can be attached to an integration report without copying this page.

Run the acceptance gate

From the repository root:

task testing:anchors:acceptance

This focused gate requires Java and Maven but no MongoDB or deployed security function. It proves that every golden response can still be produced from the authoritative conformance fixture and that the published OpenAPI operations are resolvable by the same Contract resolver used by the Registry.

For the full deterministic cross-module gate, including DOT JSON Schema, CLI, composition planning, and lifecycle dry-runs:

task testing:conformance

For behavioral evidence, continue with the APISIX, Keycloak, and OAuth-client scenario documented in Verification and examples.

Versioning policy

The profile version and ResolvedAnchor.apiVersion are explicit compatibility boundaries:

  • compatible clarifications, additional fixtures, and new optional examples may extend v1 without changing its response version;

  • removing or renaming a response field, changing its meaning or nullability, changing stable error semantics, or narrowing an accepted value requires a new response and acceptance-profile version;

  • adding a Contract standard or a new normalized interaction requires a v1 golden case before it can be claimed as supported;

  • old profiles remain executable during a migration window; and

  • individual DOT semantic versions do not replace the consumer profile version.

Anchor UUID continuity is evaluated independently: the same logical connection capability keeps its UUID across compatible DOT revisions. An incompatible replacement receives a new UUID and must not be hidden by a profile-version change.

Joint SFC acceptance

DOT-Design owns and executes this profile. The Security Function Composer remains unchanged until its maintainers choose to integrate it. A joint session should record:

  1. the exact DOT-Design and SFC revisions;

  2. the profile version and Registry API version;

  3. the completed consumer checklist;

  4. the DOT and Anchor UUIDs used by each wire;

  5. the Contract operation selected for each side;

  6. planning, deployment, and active runtime-probe results separately; and

  7. every unsupported requirement or adapter boundary.

Passing the deterministic profile is necessary but does not prove endpoint reachability, credential validity, authorization policy, or live security behavior. Those claims require explicit runtime probes and remain separate from the Anchor model.
