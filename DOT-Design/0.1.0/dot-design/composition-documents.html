Composition Documents and DOT Instances

A composition document is owned by the composer or operator, not by any member DOT. It selects immutable DOT identities and creates deployment instances whose topology may vary between environments.

Composition documents and DOT instances

A composition is a separate versioned document. It names concrete instances of DOT definitions and pins their identities independently of local paths:

apiVersion: dot.mare6g.eu/v1alpha1
kind: Composition
id: e3000000-0000-4000-8000-000000000001
name: api-gateway-oidc
version: 1.0.0
dots:
  - name: identity
    source: ./keycloak
    dotId: d3000000-0000-4000-8000-000000000001
    dotVersion: 1.0.0
    deployment: kubernetes
  - name: gateway
    source: ./apisix
    dotId: d4000000-0000-4000-8000-000000000001
    dotVersion: 1.0.0
    deployment: kubernetes
    dependsOn: [identity]
contracts:
  - id: c3000000-0000-4000-8000-000000000001
    source: ./contracts/oidc-discovery.yaml

name identifies an instance inside this composition. dotId and dotVersion must match the loaded dot.json; a path cannot silently substitute a different DOT. deployment selects a deployment by its stable deployment ID or unambiguous manifest alias.

dependsOn is a readiness graph, not a connection graph. A wire does not imply startup order. This distinction permits reciprocal peer wires and brokered topologies without creating false dependency cycles.

Composition field reference

The emitted Draft 2020-12 JSON Schema is normative for the serialized v1alpha1 shape. This table is the study guide for its top-level ownership:

Field Required Meaning

apiVersion, kind

Yes

Fixed discriminators: dot.mare6g.eu/v1alpha1 and Composition.

id

Yes

Stable UUID of this composition, also used to derive local state and runtime identities.

name, version

Yes

Human-readable identity and version of the composition document.

dots[]

Yes, at least one

Named deployment instances. Every entry pins source, dotId, and dotVersion; deployment, dependsOn, and deploymentInputs refine execution.

contracts[]

When a referenced Contract is needed

Maps an exact Contract UUID to a local Contract document. The document’s embedded id must match.

wires[]

No

Connections between one PROVIDES and one REQUIRES Anchor. A composition with no wires can still expose a standalone capability.

exposedAnchors[]

No

Composition-local names for member Anchors that an operator may expose or forward.

Each wire requires name, from, and to. Both ends contain an instance name and Anchor UUID. Optional endpoint selects a third-party or otherwise non-default service port; parameters supplies only Contract-declared template values; materializer or materializers writes resolved values; and security binds Contract security requirements to declared participant configuration. Unknown fields are rejected.

DOT definition versus DOT instance

One pinned DOT definition can appear more than once in a composition. Each entry has a distinct composition-local name, runtime identity, deployment inputs, and wires while retaining the same dotId and dotVersion:

dots:
  - name: site-a
    source: ./federation-agent
    dotId: d5000000-0000-4000-8000-000000000001
    dotVersion: 1.0.0
    deployment: docker
    deploymentInputs:
      environment:
        - {name: FEDERATION_NODE_ID, value: site-a}
  - name: site-b
    source: ./federation-agent
    dotId: d5000000-0000-4000-8000-000000000001
    dotVersion: 1.0.0
    deployment: docker
    deploymentInputs:
      environment:
        - {name: FEDERATION_NODE_ID, value: site-b}

Wires reference site-a or site-b, never the source path. Docker Image deployments receive deterministic per-instance container, DNS, network, and named-volume identities. Apply rejects repeated instances for deployment mechanisms whose manifest-owned resource names cannot yet be isolated safely.

The executable example is testing/composition/federation-peers/scenario.yaml.
