Verification and examples

DOT-Design keeps model correctness, resolved planning, deployment dry-runs, and live behavioral acceptance as separate evidence levels. A passing lower level never implies a higher one.

Evidence model

Level Demonstrates Does not demonstrate

Model and schema conformance

dot.json shape, Bean Validation constraints, stable references, selectors, service-port bindings, and generated-model compatibility

Contract payload resolution or multi-DOT topology

Contract resolution and compatibility

Selected operations exist and normalized semantic, interaction, protocol, media, schema, and security facts can be evaluated conservatively

Runtime reachability or valid credentials

Composition validation and plan

Pinned DOTs, wires, endpoints, materializers, parameters, grants, and readiness ordering resolve deterministically

Successful deployment

Lifecycle dry-run

The reference executor accepts the supported profile and renders runtime actions without writing composition state

Workload startup or traffic

Source-adapted E2E

Pinned upstream logic or artifacts execute behind explicit test adapters and satisfy the assertions documented by that scenario

Unmodified partner runtime, production infrastructure, or full PoC acceptance

Live production acceptance

The intended workloads, network, identity, policy, and Contract operations work in the target environment

Nothing beyond the probes and acceptance criteria actually executed

Read that scenario’s README first; commonly Docker and network access

Test asset layout

testing/
├── acceptance/        versioned consumer profiles and golden API responses
├── conformance/       deterministic valid and invalid DOT fixtures
├── composition/       read-only validate, plan, and dry-run scenarios
├── e2e/               opt-in deployable behavioral scenarios
└── interoperability/  revision-pinned evidence and remaining-gap ledger

testing is repository-level infrastructure, not a Maven module and not a deployable DOT. Generated secrets, logs, reports, and materialized configuration belong under scenario-local target/ directories and must not be committed.

The focused task testing:anchors:acceptance gate verifies the published DOT Anchor consumer profile and its complete cross-standard golden Registry responses without MongoDB or a deployed workload.

Canonical Anchor scenario

testing/e2e/api-gateway-oidc/ is the primary tutorial and lifecycle fixture. It contains three independently valid DOTs:

  • Keycloak provides OpenID Connect discovery and token operations;

  • APISIX requires discovery information and provides a protected operation; and

  • an OAuth client requires the token and protected operations.

The composition uses three OpenAPI Contracts, three wires, explicit security configuration, Kubernetes Secret references, configuration-file and environment materializers, readiness dependencies, and one exposed Anchor.

task testing:e2e:anchors:api-gateway-oidc:dry-run

Negative evidence is intentional

Rejected fixtures are part of the design evidence. They demonstrate that the model does not invent connectivity where the pinned source lacks a declared consumer input, does not treat stdout or a host path as a portable connection, and does not silently grant privileged runtime access.

Examples include:

  • PoC7 rejects a collector-to-scorer wire when the collector declares no such Anchor or configuration input;

  • PoC8 rejects an undeclared Prometheus-to-NDT handoff; and

  • invalid conformance fixtures cover missing Contracts, selectors, ports, duplicate bindings, and incompatible Anchor pairs.

Failing closed is a successful test outcome when the available evidence cannot support the proposed composition.

Adding or promoting a scenario

  1. Pin the exact external source revision used as evidence.

  2. Document what the source actually produces and consumes.

  3. Define Contracts only for supported, observable interactions.

  4. Use contractless Anchors only when no supported Contract standard applies.

  5. Declare all service ports, configuration targets, privileges, and devices.

  6. Add negative fixtures for tempting but unsupported connections.

  7. Start under testing/composition/ with validate and plan assertions.

  8. Add a lifecycle dry-run before any live execution.

  9. Promote to testing/e2e/ only with isolated resources, explicit prerequisites, reliable cleanup, and externally observable assertions.

  10. Record what remains unproved in the interoperability ledger.

Interpreting results

A successful plan proves model consistency. A successful apply proves that the supported deployment adapters completed. Only an active scenario probe can prove that traffic, authentication, authorization, policy, or security behavior worked as intended.
