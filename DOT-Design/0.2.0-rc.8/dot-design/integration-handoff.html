Integration handoff

This handoff defines the interoperability boundary for a team implementing a catalogue, composer, Security Function Composer adapter, or other DOT consumer. It intentionally does not prescribe a service, database, API style, language, or framework.

Authoritative inputs

The reference source of reusable definitions is DOT-Repository. Resolve a DOT by its immutable UUID and pinned version, then verify the returned dot.json matches both. Resolve referenced Contract payloads without copying their protocol, schema, media, or security facts into an Anchor.

Use these commands as executable reference behavior:

dotx repository inspect <dot-id>@<version> --repository DOT-Repository --json
dotx validate DOT-Repository
dotx compose validate composition.yaml
dotx compose plan composition.yaml --json

An implementation may expose equivalent behavior through REST, gRPC, events, an SDK, or an embedded library. Its external contract should be versioned and tested independently from the DOT model.

Disposition of legacy SFC requests

The original SFC issues 6 through 9 predate the stable repository-backed model. Their consumer needs are handled at the integration boundary without creating parallel sources of truth:

  • Parameter forms: derive an SFC-facing form from exact service-scoped environment and configuration declarations plus authoritative Contract schemas. Composition validation rejects missing or ambiguous required inputs before runtime mutation. A duplicate root params model is not defined.

  • Skill search: resolve stable Skill UUID references through the authoritative DOT-Repository/Skills/ catalogue. Every referenced capability has one category there; dotx repository list --skill <uuid-or-name> and --category <uuid-or-name> expose the tested consumer projection without copying names or categories into every DOT as a second controlled vocabulary.

  • Catalogue API: DOT-Repository and dotx repository define reference behavior. A catalogue team may expose equivalent queries through any versioned API; DOT-Design does not own or prescribe that service.

  • Low-barrier authoring: a DOT author may hand-write one dot.json, place its folder under the appropriate recursive DOT-Repository/DOTs/ category, and validate the whole filesystem catalogue with dotx validate DOT-Repository. There is no duplicate inventory file or wrapper script. This path requires no Maven, Jsonnet, MongoDB, or running service. dot.json remains the sole deployment definition; a parallel YAML format and inline copies of referenced entities are intentionally not introduced.

These dispositions settle DOT-side model ownership. They do not replace joint SFC acceptance or prove a partner catalogue/search implementation.

Required semantics

An interoperable consumer must:

  • address DOTs, Contracts, and Anchors by stable UUID and pin DOT versions;

  • resolve contract-backed selectors against the authoritative OpenAPI, AsyncAPI, Protocol Buffers, or GraphQL document;

  • use anchorBindings to map a logical Anchor to a named service port;

  • keep instance topology, endpoints, parameter values, credentials, and policy outside reusable DOT definitions;

  • evaluate compatibility conservatively and preserve UNKNOWN as distinct from COMPATIBLE; and

  • keep secret values out of DOTs, plans, persisted state, and logs.

Contractless Anchors are valid only when a supported Contract standard cannot describe the interaction. Their explicit direction, protocols, media types, and semantic types must be complementary before a wire is accepted.

Acceptance evidence

The versioned consumer profile is under DOT-Testing/acceptance/dot-anchors/v1/. It resolves two catalogued test DOTs, verifies the committed composition lock, and plans 12 compatible wires across all supported Contract standards and versions.

task testing:anchors:acceptance
task testing:conformance

Passing the deterministic profile proves discovery and planning semantics. A joint live test must separately prove endpoint reachability, credential and token handling, authorization, policy enforcement, and application behavior.

Future implementation freedom

The removed catalogue-service prototype is not part of the production architecture. A future team may replace it or implement discovery elsewhere in a different language or framework. Compatibility is judged by the stable DOT model and executable acceptance profile, not by reproducing the prototype’s internal classes or former HTTP response shapes.
