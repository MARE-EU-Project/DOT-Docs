DOT-Domain model

DOT-Domain is the persistence-neutral Java library that defines the portable DOT aggregate and its validation rules. It contains no application, web, or storage-adapter layer.

Aggregate overview

Type Responsibility

Dot

Aggregate root: identity, version, description, classification groups, metadata, Skills, Contracts, Anchors, and Runtimes.

Skill

Standalone human-readable capability description.

Contract

Standalone authoritative OpenAPI, AsyncAPI, Protobuf, or GraphQL document.

Anchor

Embedded stable logical point through which the DOT participates in composition.

Runtime

A target Platform plus one or more compatible deployment definitions.

Deployment

Stable deployment ID, one polymorphic manifest, and the logical services it materializes.

DeploymentService

Service identity, host, named ports, Contract references, Anchor bindings, and its supported configuration surface.

Dot, Skill, and Contract are independently identified domain entities. Other types are embedded values owned by a DOT. The module carries no database or ORM annotations; persistence is an adapter concern.

Identity, versioning, and references

Root entity IDs are UUIDs. Equality for Dot, Skill, and Contract is ID-based so changes to mutable metadata or collections do not destabilize sets or persistence identity.

Version accepts Semantic Versioning 2.0.0 values and the special latest selector. It serializes as a string and implements SemVer precedence; latest sorts after concrete versions. A new Dot or Contract defaults to 0.0.0, while Platform.version defaults to latest so no platform-specific release is implied.

JSON serializes Dot.skills, Dot.contracts, and DeploymentService.contracts as ID-only objects. Consumers resolve those UUIDs against authoritative definitions rather than relying on object embedding.

Catalogue uniqueness rules are:

  • Skill.name is globally unique;

  • Dot is unique by (name, version); and

  • Contract is unique by (name, version).

Contract.isFormatCompatibleWithStandard() rejects mismatched standard/format pairs. Payload parsing and selected-element existence are resolver concerns; the domain model validates selector syntax and references within the aggregate.

Anchors and bindings

A contract-backed Anchor contains:

  • a stable UUID and display name;

  • a PROVIDES or REQUIRES role;

  • optional semantic-type URIs; and

  • a Contract UUID plus standard-specific selector.

It omits direction, protocol, and media type because those facts come from the selected Contract operation. A contractless Anchor must declare direction, at least one protocol, and at least one media type explicitly.

DeploymentService.anchorBindings maps an Anchor UUID to a named ServicePort on that same service. An Anchor contains no host, numeric port, credential, placement, or live policy state.

The class-level @ValidAnchor constraint delegates cross-reference validation to AnchorValidator. It rejects:

  • duplicate Anchor UUIDs within one DOT;

  • Contract references not declared by the same DOT;

  • selectors invalid for the referenced Contract standard;

  • bindings to undeclared Anchors;

  • bindings to port names absent from that service; and

  • duplicate bindings of one Anchor within the same service.

See DOT Anchors and Composition for authoring and wiring examples.

Runtime two-layer model

Runtime separates infrastructure from deployment mechanism:

Enum Used by Answers

PlatformEngine

Platform.engine

Where the workload runs: DOCKER, KUBERNETES, VAGRANT, or WEBASSEMBLY.

DeploymentManifestType

DeploymentManifest.type

How it is deployed: Docker image, Docker Compose, Kubernetes manifest, Helm chart, Vagrantfile, or WASM module.

Every DeploymentManifestType declares its required PlatformEngine. Runtime.isDeploymentPlatformAligned() validates every deployment against the runtime platform. Runtime.isDeploymentIdsUnique() enforces stable deployment selection within that runtime.

Deployment.services is a set. DeploymentService uses ID-based equality, so logical service IDs remain unique within the deployment.

WebAssemblyModule

Relative/file or HTTPS module URI, WASI execution world, command arguments, and required SHA-256 integrity pin

Docker Compose and Kubernetes manifest payloads accept YAML or JSON only. Helm values also preserve YAML/JSON order: later entries override earlier entries as with repeated Helm -f arguments.

Runtime instance concerns do not belong in a manifest. For example, a Helm release name and namespace are selected by deployment tooling, not embedded in HelmChart.

Service configuration declarations

Every DeploymentService owns one DeploymentConfig containing:

  • environment variables, including default, required, and sensitive metadata;

  • configuration-file paths, content type, defaults, and sensitivity;

  • logical volume mounts;

  • logical CNCF CDI device requirements; and

  • optional OCI capability and host-namespace requirements.

These are supported inputs and requirements, not applied runtime state. Operator values, host paths, concrete CDI device names, and permission grants belong to deployment or composition input.

OCI requirements use standard CAP_* capability names and typed Linux namespaces. The model deliberately has no unrestricted privileged flag.

A CDI requirement declares a stable logical name and a vendor.example/class kind. A composition binds it to one exact vendor.example/class=device identifier. CDI installation, allocation, and authorization remain operator responsibilities.

Serialization and persistence adapters

  • Collections have initialized builder defaults and do not become null when constructed through Lombok builders.

  • Version is JSON-serialized as a normalized string.

  • Persistence adapters must preserve UUID and version representations.

  • Referenced Skill and Contract objects expose only id when nested in DOT JSON.

  • Domain values carry no database or ORM annotations.

Build and test

# Unit tests only; no service or database required
mvn -pl DOT-Domain test

# Regenerate schema and diagram through the reactor lifecycle
mvn -pl DOT-Domain clean install

Representative tests cover version precedence, reference serialization, manifest polymorphism, runtime/manifest alignment, deployment configuration, Anchor rules, and entity equality.
