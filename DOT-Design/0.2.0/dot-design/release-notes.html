Release notes

0.2.0

0.2.0 promotes the fully accepted 0.2.0-rc.8 candidate as the first stable release of the dot.mare6g.eu/v1 composition profile. There are no behavioral changes from that candidate: the stable tag regenerates the versioned domain artifact, schemas, SBOMs, documentation, and Linux CLI assets from the same pinned DOT-CLI 4f415d43f08bb546d333ab61d6de272e92113903 and DOT-Repository 2fe0ecc81f9caea43c5bf6e0dc824c3e0faf34e3 revisions.

The release pipeline classifies 0.2.0 as stable and publishes it as the latest GitHub release. Before promotion, 0.2.0-rc.8 passed the full pushed commit matrix, reproducible release packaging, and post-publication Linux amd64 acceptance using the downloaded checksummed binary, including two repeated external-DOT lifecycle and cleanup cycles. Arm64 remains a cross-built preview until equivalent native evidence exists, and joint SFC acceptance remains a separate integration activity.

0.2.0-rc.8

0.2.0-rc.8 supersedes 0.2.0-rc.7 with a current stable build and CI toolchain while retaining the accepted dot.mare6g.eu/v1 composition, runtime, lifecycle, Contract, Skill-taxonomy, reusable-catalogue, and WASI profiles. Node.js 26 is now the explicit documentation and Contract-validation baseline; Go 1.27.2, Rust 1.98.1, Ruby 4.0, Java 27, and Maven 3.10.0 provide the remaining release toolchains. Direct Maven and Go dependencies and all third-party GitHub Actions were updated to compatible stable releases and immutable Action SHAs, with weekly Dependabot checks for Actions, Maven, Go, and the independently cloneable repositories. Documentation CI now rejects prerelease Ruby runtimes before Antora/PDF assembly.

Release publication now uses a tested, fail-closed SemVer channel classifier: prerelease versions such as 0.2.0-rc.8 are published as GitHub prereleases, while 0.2.0 is published as the latest stable release. The exact pinned revisions are DOT-CLI 4f415d43f08bb546d333ab61d6de272e92113903 and DOT-Repository 2fe0ecc81f9caea43c5bf6e0dc824c3e0faf34e3.

0.2.0-rc.7

0.2.0-rc.7 supersedes 0.2.0-rc.6 with two release-evidence hardening changes while retaining the same stable dot.mare6g.eu/v1 profile and pinned DOT-CLI and DOT-Repository revisions. Source-adapted PoC harnesses now acquire private producer source through one guarded helper: it checks out the full pinned commit in a fresh temporary directory, verifies HEAD and the expected GitHub origin, retries bounded transient failures, and rejects partial, untrusted, missing-revision, or unsafe-destination results. Deterministic tests exercise those positive and negative boundaries without network access.

Contract conformance now installs the official Protocol Buffers 36.2 compiler for Linux amd64 or arm64 through the shared local bootstrap, verifies the download with an architecture-specific SHA-256, and uses that exact binary for both positive and deliberately invalid Protobuf fixtures. Local Taskfile runs and GitHub Actions no longer depend on different compiler setup paths. The exact pinned revisions remain DOT-CLI b01f736393caa1a93d32e2c5593e032e854052ac and DOT-Repository d0b7fc1f3aac13a2b785482b07d5529f1d53404f.

0.2.0-rc.6

0.2.0-rc.6 supersedes 0.2.0-rc.5 with one shared, fail-closed bootstrap for the official WASI HTTP fixture. Local task ci:live and GitHub Actions now fetch and build the same exact Bytecode Alliance sample-wasi-http-rust revision before executing the same Wasmtime lifecycle assertions. The stable dot.mare6g.eu/v1 composition profile, runtime adapters, lifecycle behavior, Contract model, Skill taxonomy, and reusable catalogue structure are otherwise unchanged. The exact pinned revisions remain DOT-CLI b01f736393caa1a93d32e2c5593e032e854052ac and DOT-Repository d0b7fc1f3aac13a2b785482b07d5529f1d53404f.

The bootstrap verifies the exact upstream URL and commit, rejects non-Git, wrong-origin, and modified tracked source caches, and rebuilds the .wasm component rather than trusting an ignored build artifact. The GitHub workflow no longer contains a separate checkout/build implementation; it invokes the same ci:wasm-runtime Taskfile gate available locally. Documentation records the Rust 1.98.1, wasm32-wasip2, and first-build network prerequisites and the optional WASI_HTTP_COMPONENT override for a deliberately supplied component.

0.2.0-rc.5

0.2.0-rc.5 supersedes 0.2.0-rc.4 with one fail-closed representation for complete Contract payloads. The stable dot.mare6g.eu/v1 composition profile, runtime adapters, lifecycle behavior, Skill taxonomy, and reusable catalogue structure are unchanged. The exact pinned revisions are DOT-CLI b01f736393caa1a93d32e2c5593e032e854052ac and DOT-Repository d0b7fc1f3aac13a2b785482b07d5529f1d53404f.

Complete Contract declarations now carry a structured payload object:

"payload": {
  "url": "https://vendor.example/contracts/service-openapi.yaml",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}

The URL must be absolute HTTPS without user information or a fragment, and the digest must be exactly 64 lowercase hexadecimal characters. Raw embedded Contract documents and the former flat payloadUrl/payloadSha256 fields now fail schema and dotx validate checks. UUID-only Contract references remain a migration-compatible form for verified repository-local wrapper definitions.

dotx validate downloads the authoritative bytes, verifies their digest, and uses MARE_READ_ONLY_TOKEN or GITHUB_TOKEN only for raw.githubusercontent.com. Authorization is removed before following a cross-host redirect. Unit and repository tests cover malformed URLs and digests, unavailable assets, digest mismatch, authentication scoping, redirect credential leakage, inline payload rejection, flat-field rejection, and the official external Contract composition. The standalone DOT-Repository gate also runs the pinned validator directly for every catalogue revision.

GitHub Actions and local pre-push verification now share root ci:* Taskfile gates. task ci:deterministic covers the deterministic non-live release boundary; task ci:live covers the mutable Linux runtime workflows and requires the same official WASI HTTP component exercised by Actions, preventing a reduced local test path from being mistaken for workflow parity.

0.2.0-rc.4

0.2.0-rc.4 retains the runtime and lifecycle profile accepted in 0.2.0-rc.3 and completes the closed SFC-requirement audit with repository-backed Skill discovery. DOT-Repository/Skills/ now contains an authoritative asset for every capability UUID referenced by the catalogue and links each capability to one of the five controlled MARE categories.

dotx validate DOT-Repository resolves all 67 DOT definitions against that catalogue and rejects missing capabilities, category assets used as capabilities, duplicate references, and invalid category links. dotx repository list --skill <uuid-or-name> and --category <uuid-or-name> provide resolved, machine-readable discovery without copying category fields into every dot.json. The exact published revisions were DOT-CLI 3069f907bfd2056b16b92800bb5b98552c28832d and DOT-Repository 3117a18da3004c57f4edf3714494fd3954225ae7.

The audit also reconfirmed the existing DOT-side dispositions for stable Anchor identity and semantics, authoritative payload Contracts, service-scoped pre-deployment configuration validation, and single-file dot.json authoring. The separate DOT-Registry REST API remains outside this candidate, and joint SFC/partner acceptance remains a manual gate.

External products now have one canonical reusable DOT root rather than PoC-specific identities. Seventeen product roots plus two shared external test fixtures replace the former duplicated Keycloak, OPA, Prometheus, Elasticsearch, and APISIX definitions. PoC realms, policies, routes, scrape targets, data sources, secrets, and files remain composition-owned inputs; unavoidable source adaptations are named deployment variants under the same product UUID. Repository validation rejects any new deployable definition below DOTs/external/pocs/.

Composition lifecycle commands preserve the exact deployment ID rather than reducing it to a manifest type. The --deployment selector prefers an exact ID and accepts a manifest type or alias only when it identifies one deployment, so source-adapted and upstream deployments of the same type cannot be selected silently.

Catalogue placement now records ownership rather than Contract maturity: third-party software is under DOTs/external/, MARE-owned/developed software is under DOTs/internal/, and only synthetic fixtures remain under DOTs/testing/. Every DOT bundle includes a local quickstart README.md. External/internal bundles opt into strict reusable validation by publishing a contracts/ evidence directory whose assets identify their authority as upstream-official, runtime-extracted, DOT-ecosystem-derived, or adapter-owned, along with source revision, license, and SHA-256. Loki and Wireshark are now correctly classified as external runtime-only definitions without fabricated vendor Contracts.

0.2.0-rc.3

0.2.0-rc.3 supersedes 0.2.0-rc.2 after post-publication, exact-pin lifecycle acceptance found that the Keycloak Helm workload could not reliably complete Quarkus augmentation within its declared 1536-MiB container limit. Three independent real-cluster runs retained pod and event diagnostics showing OOMKilled exit 137; the runner had 62 GiB of host memory and Minikube exposed 16.8 GB and 20 CPUs, isolating the defect to the DOT resource declaration.

Keycloak-DOT 0.1.1 declares a 2-GiB memory request and 4-GiB limit while retaining the same official Keycloak 26.3.3 Contract, Anchor selectors, chart, image, service, and Docker Compose mechanism. The external-DOT render suite now inspects the real upstream chart output and rejects any mismatch in the Keycloak container’s CPU or memory requests and limits before live deployment. The official external-Contract composition and content-addressed lock resolve the versioned 0.1.1 definition.

External DOT examples run 38708940363 passed both the non-mutating chart conformance job and two complete Linux lifecycle cycles. Each cycle passed all 47 checks with zero failures and cleanup verification across Keycloak, Loki, Prometheus, and Wireshark’s eight deployment-mechanism cells. The downloaded, checksum-verified evidence pins DOT-CLI f8cf796afd985cc0514d42fb149ef67b6a1b7b53 and DOT-Repository 76585f6ec68a892f6cc6d48c9b2acdce6b08d48d.

This candidate also adds a post-publication workflow that downloads the actual checksummed Linux amd64 dotx release asset, verifies its release manifest and source revisions, then runs repository validation, Anchor acceptance, Composition v1 acceptance, and two complete external-DOT lifecycle cycles. Maven dependency submission is now an explicit self-hosted workflow; the billing-blocked GitHub-managed automatic submission feature is disabled. Linux amd64 is the release-accepted executable target. The cross-built arm64 asset remains preview-only until equivalent native arm64 evidence exists. Joint SFC/partner acceptance remains a separate manual gate and is not claimed by this candidate.

0.2.0-rc.2

0.2.0-rc.2 supersedes the first candidate with the fixes and acceptance evidence completed after 0.2.0-rc.1 was tagged. The stable serialized composition API remains dot.mare6g.eu/v1.

Changes since rc.1

  • Exact service-to-workload selection and configuration isolation for multi-service Docker Compose, Kubernetes-manifest, and Helm deployments.

  • Exact official, digest-pinned OpenAPI Contracts and Contract-backed Anchors for reusable Keycloak and Prometheus external DOTs, with every Helm and Docker Compose deployment binding the same interface.

  • dotx validate --profile reusable now enforces declared HTTPS Contract provenance, payload integrity, selector resolution, Contract use, and per- deployment Anchor binding. Review establishes that the pinned source is the official upstream artifact. dotx validate <repository-root> recursively discovers every dot.json; the later rc.4 ownership migration derives strict reusable validation from adjacent Contract evidence rather than category path, and is the single DOT-Repository GitHub Actions gate; no duplicate inventory or shell wrapper is required.

  • Same-DOT alternative deployment mechanisms for the Keycloak, Loki, Prometheus, and Wireshark external-product examples. Loki and Wireshark were initially retained as runtime-tested samples; rc.4 reclassifies them as external runtime-only DOTs without claiming Contract-backed interoperability.

  • A locked Keycloak/Prometheus/consumer composition proves that both stable external Anchors resolve and materialize the exact official operations.

  • Failed Kubernetes/Helm workloads now retain pod, event, workload, and bounded log diagnostics before cleanup; causally blocked endpoint assertions are skipped rather than counted as independent failures.

  • Repeated hosted-Linux acceptance run 38600327954 covering all eight external-DOT mechanism cells: two complete lifecycle cycles, 46 checks per cycle, zero failures, verified cleanup, and four successful official- Contract operation checks per cycle. The checksummed evidence pins DOT-CLI 848b2d56e9e416ae87fa46d221c9649041b64541 and DOT-Repository b681c937422fa3db13ad16587cf271700eff5d79.

  • Portable evidence checksums and retained GitHub Actions artifacts.

  • Separate workflow concurrency lanes for push conformance and manually requested live stress, preventing one evidence class from canceling the other.

Linux amd64 is the release-accepted executable target. The published arm64 executable is a cross-built preview and is not a supported final-release target until equivalent native arm64 evidence exists. Producer/partner acceptance, non-Linux executables, multi-host orchestration, general stateful migration, and automatic provisioning of cross-platform gateways remain outside this candidate. GraphQL, gRPC, and event-driven runtime probes beyond the documented safe profile remain standards-led roadmap work rather than an rc.2 blocker.

The candidate assets and verification procedure are the same classes described for rc.1 below, with filenames versioned as 0.2.0-rc.2. The tag workflow rebuilds the Java artifact, both schemas, SBOMs, and Linux dotx binaries from the immutable revisions recorded in release-manifest.json, then verifies reproducibility and SHA256SUMS before publication.

0.2.0-rc.1

0.2.0-rc.1 is the first integrated release candidate for the stable dot.mare6g.eu/v1 composition profile. It replaces the narrower 0.1.0 artifact set with a traceable domain model, both machine-readable schemas, and version-stamped dotx binaries built from the exact DOT-CLI revision pinned by this repository.

Highlights

  • Stable, repository-backed Composition v1 lifecycle, probe, and upgrade commands.

  • Contract-driven Anchors for OpenAPI 3.0/3.1/3.2, AsyncAPI 3.0/3.1, Protobuf/gRPC, GraphQL, and declared contractless interactions.

  • Immutable repository resolution, content-addressed locks, resumable lifecycle operations, and last-known-good upgrade rollback.

  • Managed Docker image, Docker Compose, Kubernetes manifest, Helm chart, Vagrant/libvirt, and Wasmtime/WASI profiles.

  • Explicit cross-platform networking through externally owned gateway bindings with pinned host, port, ownership, and no-cleanup semantics.

  • Service-scoped configuration, secrets, OCI requirements, CDI devices, and exact native-workload bindings.

Assets and verification

The candidate includes the DOT-Domain JAR, DOT and Composition v1 schemas, CycloneDX SBOMs, and dotx binaries for Linux amd64 and arm64. release-manifest.json records the immutable DOT-Design, DOT-CLI, and DOT-Repository revisions. The repository revision pins its DOTs/, Skills/, and Schema/ assets together. Verify the download set with:

sha256sum --check SHA256SUMS

The tag workflow publishes only after the Java build, generated-schema drift check, DOT-CLI tests, repository test, Composition v1 acceptance suite, deterministic packaging comparison, manifest validation, and checksum verification pass.

Compatibility and boundaries

The serialized composition API is dot.mare6g.eu/v1; breaking serialized changes require a new API version. The experimental local catalogue/registry prototype from the 0.1.0 era is not included: DOT-Repository is authoritative.

This candidate does not claim multi-host orchestration, automatic provisioning of cross-platform gateways/tunnels/brokers, general stateful data migration, arbitrary privileged workloads, non-Linux dotx executables, or producer/partner acceptance. The current CLI includes Linux process controls for its managed WASI runtime, so this candidate publishes Linux amd64 and arm64 binaries only. Closed legacy SFC issues record DOT-side disposition; joint consumer acceptance remains a separate manual gate.

See the repository-root RELEASE_NOTES.md included with the source for the complete candidate notes and upgrade guidance.
