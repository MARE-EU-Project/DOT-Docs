Authoring Anchors

This page covers the DOT publisher’s side of composition. Start with the model overview if the distinction between Contracts, Anchors, bindings, and wires is not yet familiar.

Authoring two composable DOTs

Use this sequence when introducing a new connection:

  1. Put the operation or message boundary in an OpenAPI, AsyncAPI, Protobuf, or GraphQL Contract. Use the contractless form only when none of those standards can describe the boundary.

  2. Add a stable PROVIDES Anchor to the provider DOT and a stable REQUIRES Anchor to the consumer DOT. Select the authoritative Contract element from each Anchor; do not copy its protocol or payload fields.

  3. On every deployable implementation, bind each Anchor UUID to the named ServicePort that implements it.

  4. Declare every consumer configuration input on its DeploymentService, including sensitivity. This declaration is the allow-list for composition.

  5. Validate each DOT independently with dotx validate before writing a composition.

  6. Add named, UUID/version-pinned DOT instances and UUID-pinned Contract inputs to a separate composition document.

  7. Connect the Anchor UUIDs with a wire. Add an explicit broker endpoint, parameter values, security binding, or materializer only when the connection requires it.

  8. Run dotx compose lock and commit the generated lock beside the composition. Review digest changes as changes to the resolved DOT-to-DOT graph.

  9. Run dotx compose validate to check the document and dotx compose plan to inspect the resolved topology. Treat UNKNOWN compatibility as missing evidence, not as success.

  10. Use apply --dry-run before execution. After apply, use compose probe for safe Contract-derived traffic and status for native runtime status, configuration evidence, and the latest redacted probe evidence. Dedicated acceptance tests remain necessary for authentication, authorization, mutable operations, and application-specific outcomes.

The complete three-DOT worked example is under DOT-Testing/e2e/api-gateway-oidc/: its keycloak/, apisix/, and oauth-client/ directories contain independently valid DOTs; contracts/ contains the authoritative APIs; and scenario.yaml owns the wiring.

Concrete identifiers in this guide use the canonical lowercase UUID text form with UUIDv4 version and IETF variant bits defined by RFC 9562. Deterministic values are retained where they identify executable repository fixtures, making the documentation traceable to the tested examples. Generate new UUIDs for production DOTs; do not reuse documentation or fixture identifiers.

Contract-backed Anchors

A contract-backed Anchor carries stable identity and selects one authoritative contract element. It deliberately omits protocol, direction, media type, payload schema, and security fields that the Contract already defines.

{
  "id": "a0000000-0000-4000-8000-000000000001",
  "name": "submit-alert-http",
  "role": "PROVIDES",
  "semanticTypes": ["urn:mare:security:alert"],
  "contract": {
    "id": "11111111-1111-4111-8111-111111111111",
    "selector": "#/paths/~1alerts/post"
  }
}

The opposite DOT declares its own REQUIRES Anchor. It may select the same Contract UUID or an independently authored Contract. Compatibility is deterministic when authoritative facts are comparable; otherwise the result is UNKNOWN, never an invented match.

Reading compatibility results

The plan compares the provider and consumer across independently explainable dimensions:

Dimension Meaning

Role and direction

The connection is from PROVIDES to REQUIRES, and the selected interaction directions can communicate.

Semantics

Declared semantic-type URIs intersect when both sides provide them.

Protocol and media

Resolved protocol and media-type sets have a usable intersection.

Interaction

Request/response, publish/subscribe, streaming, query, mutation, or subscription behavior agrees.

Schema

Provider output and consumer input schema identities are compared in the correct direction when both select the same authoritative Contract; cross-Contract structural comparison remains UNKNOWN.

Security

Contract requirements are understood and, for execution, a complete supported binding has all required declared inputs.

INCOMPATIBLE means comparable evidence conflicts. UNKNOWN means evidence is missing or the current resolver cannot prove the dimension. Validate and plan may explain UNKNOWN; apply rejects it. An explicit mediator DOT is preferable to weakening compatibility when protocols or payloads genuinely differ.

dotx compose plan --json exposes the resolved contractStandard, contractFormat, providerInteraction, and consumerInteraction on each contract-backed wire. These fields are derived from the supplied Contract and therefore do not duplicate authoring metadata in either Anchor or composition. Semantic types

semanticTypes is a list of URI identifiers describing the security or domain meaning of the interaction independently of its transport. Prefer stable, governed ontology or vocabulary URIs when one exists; a project URN is suitable for concepts that have no external vocabulary yet.

Current matching is deliberately conservative: both Anchors must declare at least one semantic type and their sets must intersect exactly. Missing values produce UNKNOWN; different values produce INCOMPATIBLE. The evaluator does not infer subclass, equivalence, or broader/narrower ontology relations. Such reasoning belongs in a separately reviewed semantic-policy layer.

Contractless Anchors

Use a contractless Anchor only when no supported authoritative contract exists, for example a raw packet stream or a legacy metrics boundary. It must state the facts that cannot otherwise be derived:

{
  "id": "a0000000-0000-4000-8000-000000000006",
  "name": "packet-stream",
  "role": "PROVIDES",
  "semanticTypes": ["urn:mare:security:packet-stream"],
  "direction": "EGRESS",
  "protocols": ["TCP"],
  "mediaTypes": ["application/octet-stream"]
}

Contract-backed and contractless forms are mutually exclusive. A contract-backed Anchor must not repeat direction, protocols, or mediaTypes. A contractless Anchor must declare all three.

Role is not traffic direction

role answers who offers the selected capability:

  • PROVIDES means this DOT makes the capability available;

  • REQUIRES means this DOT depends on that capability.

It does not mean that bytes move in only one direction. An OpenAPI request/response operation has a providing server and requiring client while both send data. An AsyncAPI provider may select a send operation and its consumer a complementary receive operation. For a contract-backed Anchor, the resolver derives that interaction from the selected operation. Only a contractless Anchor states INGRESS, EGRESS, or BIDIRECTIONAL explicitly.

When two DOTs implement the same published Contract, referencing the same Contract UUID gives the strongest deterministic evidence. Independently authored Contracts are allowed, but identical-looking schema names do not prove structural compatibility across Contract identities; that comparison remains UNKNOWN until a schema-aware adapter or policy evaluates it.

Stable identity and version evolution

  • The UUID, not name, identifies an Anchor in a wire.

  • A rename or documentation correction preserves the UUID.

  • A compatible DOT version preserves the UUID for the same logical Anchor.

  • An incompatible semantic replacement receives a new UUID.

  • Removal and any future deprecated/replacedBy metadata are publishing governance decisions; they are not inferred from contract changes.

  • Names remain useful in logs and displays but are never foreign keys.

Binding an Anchor to a deployment

An Anchor is logical until a selected deployment maps it to a named service port:

{
  "id": "security-function",
  "name": "Security Function",
  "host": "security-function",
  "ports": [
    {"name": "http", "protocol": "HTTP", "port": 8080}
  ],
  "anchorBindings": [
    {
      "anchorId": "a0000000-0000-4000-8000-000000000001",
      "port": "http"
    }
  ],
  "config": {
    "environment": [],
    "configFiles": [],
    "volumes": []
  }
}

This says which logical service and named port implement the Anchor. The deployer still decides the concrete container DNS name, cluster Service, allocated address, forwarded port, certificate, or network path.

@ValidAnchor and AnchorValidator reject duplicate Anchor UUIDs, undeclared Contract references, invalid selector syntax, undeclared ports, undeclared Anchor bindings, and duplicate service-local bindings.

Runtime configuration portability

Every DeploymentService declares its supported configuration surface through environment, configFiles, and logical volumes. A composition may supply only values whose names or target paths the selected service declares. Required environment variables and files without defaults fail before runtime mutation; sensitive environment values require a secretRef instead of a literal. When an input is omitted, dotx reuses the non-sensitive defaultValue or defaultContent declared by that service. Explicit composition values and wire materializers override defaults; conflicting explicit inputs fail closed. Declarations marked sensitive are forbidden from embedding either kind of default and must use a deployment-time secret reference or runtime-native secret facility.

Each composition input carries the stable service id it targets. Authors may omit service only when exactly one service in the selected deployment declares that environment name, file path, or volume name; planning resolves and records the service explicitly. If two services declare the same item, omission is an error. Duplicate detection is service-local, so two services can intentionally receive different values for the same environment-variable name.

Configuration remains service-scoped. A Docker image or Vagrant deployment is one workload or VM, so several logical services may safely share its declared configuration surface. Docker Compose, Kubernetes, and Helm may materialize several independent workloads. Their composition therefore supplies deploymentInputs.workloads: a Compose binding names one native service; a Kubernetes/Helm binding supplies exact native labels and optionally a container. Dotx intersects those labels with its composition-owned instance label and requires exactly one workload. Missing, duplicate, cross-runtime, ambiguous workload, and ambiguous container bindings fail closed. This prevents environment values, secrets, or mounted files from reaching the wrong security function without adding platform-specific selectors to the reusable DOT model.

deploymentInputs:
  workloads:
    - service: api
      kubernetes:
        matchLabels:
          app.kubernetes.io/component: api
        container: api

Storage and privilege configuration is deliberately runtime-native. Docker image deployments support composition-scoped named volumes, explicit OCI bind sources, exact capability/host-namespace grants, and CNCF CDI devices. Compose payloads own their volume graph; Kubernetes and Helm own claims, storage classes, and volume topology; Vagrantfiles own disks and synced folders. A composer must not translate a host bind path into a cluster volume or silently grant privileged mode.

WASM_MODULE uses a reviewed Wasmtime/WASI profile. Each module is SHA-256 pinned and loaded from a relative/file or HTTPS URI. WASI_CLI executes command modules/components; WASI_HTTP serves a component on one declared TCP/HTTP service port bound to loopback. Dotx exposes only declared environment values, staged configuration files, and explicitly bound host directories. It does not translate OCI capabilities, host namespaces, or CDI devices into broader WASI permissions. Sensitive values are never printed or persisted. Because the Wasmtime CLI cannot enforce read-only permissions on a directory preopen, that request fails closed unless the host filesystem already supplies the boundary. The deterministic DOT-Testing/composition/runtime-configuration/ matrix exercises every executable adapter. The DOT-Testing/composition/service-workloads/ matrix verifies isolation between two services across Compose, Kubernetes, and Helm dry-run adapters.

Discovering and resolving Anchors

The authoritative test and reference definitions are stored in DOT-Repository and addressed as repository://<dot-id>@<version>. Consumers can inspect one immutable definition or validate the complete repository:

dotx repository inspect <dot-id>@<version> --repository DOT-Repository --json
dotx validate DOT-Repository

dotx compose validate and dotx compose plan --json resolve Anchor UUIDs, service-port bindings, and selected Contract elements conservatively. The plan reports COMPATIBLE, INCOMPATIBLE, or UNKNOWN; missing evidence is never treated as a match. Contract payloads remain authoritative and are not copied into Anchors or composition wires.

This command boundary is the reference behavior, not a requirement to embed dotx. Another catalogue or composer may use any language, framework, storage, or API shape if it preserves the same identities, fail-closed resolution, and ownership boundaries. See integration handoff.
