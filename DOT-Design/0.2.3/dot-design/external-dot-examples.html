External DOT examples and stress profile

The external-product examples demonstrate how an existing open-source workload can be described as a DOT without modifying that workload. The upstream project remains authoritative for the software, configuration, and interface Contract. The DOT descriptor selects a pinned artifact and declares the portable service surface that dotx can validate and deploy.

Upstream documentation is useful source evidence, but it is not acceptance evidence. DOT-Design therefore tests each example at separate levels:

  1. direct dotx validate, using the reusable publication profile where applicable;

  2. Contract-selector and DOT-to-DOT Anchor composition for reusable definitions;

  3. offline inspection and deployment rendering;

  4. networked rendering of the exact pinned Helm charts;

  5. one real Linux lifecycle on Kubernetes/Helm or Docker; and

  6. bounded repeated lifecycle stress with cleanup verification.

Canonical external catalogue

The external catalogue currently has one root for each of these 17 products: APISIX, cAdvisor, Elasticsearch, Filebeat, Grafana, GraphDB, InfluxDB, Keycloak, Kibana, Loki, Eclipse Mosquitto, Prometheus node-exporter, OPA, OpenTelemetry Collector, Oxigraph, Prometheus, and Wireshark. PoC compositions reuse those identities and supply routes, realms, policies, scrape targets, data sources, credentials, files, and deployment selection as instance inputs. They do not create pocN-* copies of the product.

The following four products form the bounded release stress matrix. They are not the complete external catalogue.

Each product is kept under DOTs/external/ because it is owned outside MARE, with its supported deployment mechanisms in the same dot.json. Ownership does not imply interoperability maturity. Keycloak and Prometheus publish adjacent official Contract evidence and pass the strict reusable profile. Loki and Wireshark currently provide runtime evidence only; they must not be misrepresented as Contract-backed interface interoperability. Chart versions, Compose image indexes, and the direct Wireshark image tag are deliberately pinned. latest is convenient for exploration but unsuitable for release evidence because a repeated run could execute different bytes. The Wireshark OCI index currently contains Linux amd64 and arm64 manifests. Stable 0.2.0 retained a historical cross-built arm64 preview, but subsequent DOT-Design release packaging and automated acceptance intentionally target Linux amd64 only.

Run the examples

Run commands from the DOT-Design root with a dotx built from the checked-out DOT-CLI revision.

# Fully offline and non-mutating
task testing:dots:external:offline

# Downloads and renders the pinned charts, but does not deploy them
task testing:dots:external:dry-run

# Deploys each example once and cleans it up
task testing:dots:external:live

# Repeats the complete lifecycle three times by default
task testing:dots:external:stress

The live profiles require Linux, Docker, Kubernetes, Helm, kubectl, curl, jq, and network access to the pinned public artifacts. dotx tool check starts Minikube when the current environment has no selected cluster. Set DOTX_E2E_SKIP_HELM=1 or DOTX_E2E_SKIP_DOCKER=1 only for focused local diagnosis; a release acceptance run must not skip either runtime.

What the stress profile adds

DOTX_E2E_STRESS_REPEATS accepts a bounded value from 1 through 5. Every cycle uses a new namespace, Docker runtime name, Compose project names, marker, and host-port range. It executes validation again before runtime mutation, selects each mechanism explicitly, verifies workload readiness and HTTP/HTTPS reachability, and destroys all resources. The runner then fails if the cycle namespace, Wireshark container, or any of the four Compose projects still exists. If a Kubernetes deployment or readiness check fails, the runner records pod, workload, event, and bounded container-log diagnostics before cleanup and skips only the assertions that are causally blocked by that failed workload. The root failure still fails the cycle; dependent timeout noise is not counted as independent evidence.

The resulting matrix contains eight cells:

  • Keycloak: HELM_CHART and DOCKER_COMPOSE;

  • Loki: HELM_CHART and DOCKER_COMPOSE;

  • Prometheus: HELM_CHART and DOCKER_COMPOSE; and

  • Wireshark: DOCKER_IMAGE and DOCKER_COMPOSE.

This is a runtime-mechanism matrix, not a reusable-interface count. Only the Keycloak and Prometheus cells carry official machine-readable Contracts and Contract-backed Anchors. A separate locked three-DOT composition wires those two providers to a headless consumer, resolves the exact official selectors, binds the Keycloak {realm} parameter, and asserts the resulting operation paths and environment materializers:

task testing:compose:official-external-contracts
DOTX_E2E_STRESS_REPEATS=5 task testing:dots:external:stress

Evidence is written to DOT-Testing/e2e/target/external-dots/:

  • one log per cycle;

  • summary.json, including the DOT-CLI and DOT-Repository revisions; and

  • SHA256SUMS covering the summary and logs.

The dedicated External DOT examples GitHub Actions workflow runs the non-mutating profile for relevant changes. Its weekly and manually dispatched Linux job runs the stress profile and uploads the evidence bundle. Push, schedule, and manual runs use distinct concurrency lanes, so requesting a live stress run cannot cancel the required push conformance result for the same revision.

Interpreting a pass

A pass means the pinned public artifacts satisfied the assertions executed in the disposable test environment. For Keycloak and Prometheus this includes a successful request to the exact operation selected by the DOT Anchor, in addition to readiness. It does not establish production sizing, availability, security hardening, backup/restore, or every upstream feature. In particular, the Wireshark example checks its web application surface; it does not grant packet-capture capabilities, host networking, or a CDI device. Those requirements must be declared and explicitly authorized in a separate acceptance profile.

When adding another external DOT, place it under DOTs/external/ because of its ownership and provide an immutable runtime artifact. Use a vendor/project- official Contract whenever available. Otherwise either pin a runtime-extracted Contract, maintain a clearly identified derived Contract with live conformance, or expose an adapter-owned Contract. Every Contract asset declares its authority, source revision, license, and SHA-256. A runtime-only external DOT remains valid without a contracts/ evidence directory but makes no interoperability claim. Add production claims only after a test explicitly proves them.
