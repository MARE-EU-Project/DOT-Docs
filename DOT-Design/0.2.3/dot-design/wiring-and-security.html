Wiring, Materialization, and Security

Wires express composition topology outside every participating DOT. They refer to stable Anchor UUIDs, resolve deployable endpoints through service bindings, and materialize only values that the target service has declared as configurable.

Direct request/response wire

A wire uses instance names and stable Anchor UUIDs:

wires:
  - name: oauth-token-to-client
    from:
      instance: identity
      anchorId: a3000000-0000-4000-8000-000000000002
    to:
      instance: client
      anchorId: a5000000-0000-4000-8000-000000000001
    materializer:
      type: ENVIRONMENT_VARIABLE
      valueFrom: OPERATION_URL
      target:
        instance: client
        service: oauth-client
        environmentVariable: TOKEN_URL

Planning performs the following sequence:

  1. Resolve the two pinned DOT instances.

  2. Resolve both Anchor UUIDs and require complementary PROVIDES/REQUIRES roles.

  3. Resolve the selected Contract elements.

  4. Evaluate semantic, interaction, protocol, media, schema, and security compatibility.

  5. Resolve the connection endpoint through the selected deployment’s anchorBindings.

  6. Verify that the target service declares TOKEN_URL.

  7. Build OPERATION_URL from the runtime endpoint and the authoritative OpenAPI server/operation path.

The resulting URL is deployment data. It is never copied back into dot.json or the Anchor.

Cross-platform external gateway

A wire whose participants use different runtime platforms must declare a reviewed network adapter. The first supported adapter represents a gateway that the operator provisions outside dotx:

wires:
  - name: identity-discovery-to-proxy
    from: {instance: identity, anchorId: a3000000-0000-4000-8000-000000000001}
    to: {instance: proxy, anchorId: aa100000-0000-4000-8000-000000000002}
    network:
      adapter: EXTERNAL_GATEWAY
      host: identity-gateway.example.net
      port: 8080

The Contract and bound service port remain authoritative for protocol and interaction semantics. The binding replaces only the deployment-specific host and port used by materializers. The plan, lock, and private lifecycle state record ownership=EXTERNAL and cleanup=NONE; apply, resume, status, and destroy never claim to create, inspect, or remove the gateway. Cross-platform wires without a binding, same-platform wires with a redundant binding, unknown adapters, URL-shaped hosts, and invalid ports fail before runtime mutation.

Composition-owned gateways, ingresses, tunnels, and brokers require dedicated lifecycle adapters and remain unsupported.

A wire and a materializer are intentionally separate. The wire says these Anchors are connected; the materializer says write this derived value into this declared consumer setting. A wire needs no materializer when the runtime already provides discovery, a service mesh performs routing, both participants use a fixed broker declared elsewhere, or the composition is documenting an Anchor relation without an executable handoff. Apply still requires every actually required service configuration value to have a default or explicit input.

For the example above, the human-readable plan makes every resolution step inspectable before apply:

oauth-token-to-client:
  identity/a3000000-0000-4000-8000-000000000002
    -> client/a5000000-0000-4000-8000-000000000001 [COMPATIBLE]
  endpoint: keycloak:8080
    (HTTP, instance=identity service=keycloak port=http)
  contract: c3000000-0000-4000-8000-000000000002
    selector=#/paths/~1realms~1dotx~1protocol~1openid-connect~1token/post
  materializer: OPERATION_URL -> client/oauth-client env:TOKEN_URL

The same plan with --json is the machine-readable automation output. It includes stable instance and Anchor references, compatibility reasons, the selected Contract, resolved endpoint, derived operation/channel value, materializer targets, security status, and exposed-Anchor endpoints. Consumers should parse JSON rather than scrape the human-readable form.

Brokered wire

For messaging, the semantic provider, semantic consumer, and connection endpoint may be three different instances. Select the broker explicitly:

wires:
  - name: openc2-command-via-mqtt
    from:
      instance: interpreter
      anchorId: a6000000-0000-4000-8000-000000000003
    to:
      instance: actuator
      anchorId: a6000000-0000-4000-8000-000000000006
    endpoint:
      instance: broker
      service: mqtt
      port: mqtt
    materializers:
      - type: ENVIRONMENT_VARIABLE
        valueFrom: ENDPOINT_HOST
        target:
          instance: actuator
          service: openc2-actuator
          environmentVariable: MQTT_BROKER_HOST
      - type: ENVIRONMENT_VARIABLE
        valueFrom: ENDPOINT_PORT
        target:
          instance: actuator
          service: openc2-actuator
          environmentVariable: MQTT_BROKER_PORT

The AsyncAPI operations and message schema stay in the Contract. The broker’s host and port stay in the resolved plan. If a channel has a templated address, the wire supplies only values for parameters declared by the Contract.

Materializers

Materializers are explicit adapters between a resolved endpoint and a configuration surface already declared by a service.

Type Behavior

ENVIRONMENT_VARIABLE

Writes one resolved scalar to a declared environment variable.

CONFIG_FILE

Mounts a declared file and optionally replaces one YAML/JSON value selected by an RFC 6901 JSON Pointer.

Supported valueFrom values are:

Value Result

ENDPOINT_HOST

Resolved service host only.

ENDPOINT_PORT

Resolved numeric service port only.

ENDPOINT_HOST_PORT

host:port.

ENDPOINT_URL

scheme://host:port, using the bound port protocol.

OPERATION_URL

Endpoint URL plus the authoritative OpenAPI server base and operation path.

CHANNEL_ADDRESS

Address of the authoritative AsyncAPI Channel Object.

An optional RFC 6570 uriTemplate can derive an application-specific URI from one resolved scalar. It is explicit composition behavior, not an Anchor or Contract fact.

Configuration-file materialization

A CONFIG_FILE materializer always names an operator-controlled source and a file path already declared by the target service. Without valueFrom, the source is supplied unchanged. With valueFrom, the source must be YAML or JSON and jsonPointer selects the scalar to replace:

materializer:
  type: CONFIG_FILE
  source: ./prometheus/prometheus.yml
  valueFrom: ENDPOINT_HOST_PORT
  target:
    instance: prometheus
    service: prometheus
    path: /etc/prometheus/prometheus.yml
    jsonPointer: /scrape_configs/0/static_configs/0/targets/0

This produces a deployable Prometheus configuration without putting the provider’s runtime address in either DOT. The corresponding executable fixture is DOT-Testing/composition/poc4-continuous-monitoring/scenario.yaml.

URI-template derivation

Use uriTemplate only when the application needs an explicit deterministic derivation that is not already the selected Contract operation URL:

materializer:
  type: ENVIRONMENT_VARIABLE
  valueFrom: ENDPOINT_URL
  uriTemplate: "{+value}/realms/drax"
  target:
    instance: proxy
    service: proxy-xapp
    environmentVariable: OIDC_ISSUER

The RFC 6570 variable is named value. The template belongs to the composition because it adapts one deployment to another; it does not amend the Contract or redefine the Anchor.

Materialization fails when the target configuration is undeclared, the Contract path/channel remains unresolved, alternative server paths are ambiguous, two wires produce conflicting values for one target, or the endpoint and target are on different runtime platforms without an explicit network binding.

Path and channel parameters

Only deployment-specific scalar values belong in the wire:

parameters:
  realm:
    value: drax

The Contract remains authoritative for the parameter name, location, requirement, schema, default, and serialization rules. Current composition bindings cover OpenAPI path parameters and AsyncAPI channel parameters. Query/header/cookie parameters, complex serialization, and runtime-derived parameter values require explicit future adapters.

Security and secrets

Contract security remains authoritative. A wire may demonstrate how one declared scheme is satisfied by deployment configuration:

security:
  bindings:
    - scheme: bearerAuth
      mechanism: https://www.rfc-editor.org/rfc/rfc6749#section-4.4
      participant: {instance: client, service: oauth-client}
      parameters:
        tokenUrl: {environmentVariable: TOKEN_URL}
        clientId: {environmentVariable: CLIENT_ID}
        clientSecret: {environmentVariable: CLIENT_SECRET}

Sensitive inputs are references, never secret values. They are scoped to the DOT instance whose selected deployment consumes them:

dots:
  - name: client
    source: repository://d3a00000-0000-4000-8000-000000000003@1.0.0
    dotId: d3a00000-0000-4000-8000-000000000003
    dotVersion: 1.0.0
    deployment: kubernetes
    deploymentInputs:
      environment:
        - name: CLIENT_SECRET
          secretRef:
            store: kubernetes
            name: oauth-client
            key: client-secret

Plans and composition state keep only the reference. Docker deployments can resolve store: environment at final handoff; Kubernetes and Helm preserve store: kubernetes as secretKeyRef without reading the Secret. A CONFIGURED plan proves configuration completeness, not token validity, issuer trust, mTLS, workload identity, or remote attestation.

Exposed Anchors

A composition may re-export a member Anchor under a composition-local name:

exposedAnchors:
  - name: protected-metadata-through-gateway
    target:
      instance: gateway
      anchorId: a4000000-0000-4000-8000-000000000003

At apply time, an operator may request a local forward:

dotx compose apply scenario.yaml \
  --forward protected-metadata-through-gateway=19080

The exposure name belongs to the composition boundary. It does not rename or replace the member Anchor UUID.

Before runtime mutation, follow the validation and lifecycle workflow.
