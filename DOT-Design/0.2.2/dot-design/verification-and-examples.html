Verification and examples

DOT-Design keeps model correctness, resolved planning, deployment dry-runs, and live behavioral acceptance as separate evidence levels. A passing lower level never implies a higher one.

Evidence model

Level Demonstrates Does not demonstrate

Model and schema conformance

dot.json shape, Bean Validation constraints, stable references, selectors, service-port bindings, and generated-model compatibility

Contract payload resolution or multi-DOT topology

Contract resolution and compatibility

Selected operations exist and normalized semantic, interaction, protocol, media, schema, and security facts can be evaluated conservatively

Runtime reachability or valid credentials

Composition validation and plan

Pinned DOTs, wires, endpoints, materializers, parameters, grants, and readiness ordering resolve deterministically

Successful deployment

Lifecycle dry-run

The reference executor accepts the supported profile and renders runtime actions without writing composition state

Workload startup or traffic

Source-adapted E2E

Pinned upstream logic or artifacts execute behind explicit test adapters and satisfy the assertions documented by that scenario

Unmodified partner runtime, production infrastructure, or full PoC acceptance

Live production acceptance

The intended workloads, network, identity, policy, and Contract operations work in the target environment

Nothing beyond the probes and acceptance criteria actually executed

Test asset layout

DOT-Testing/
├── acceptance/        versioned, implementation-neutral consumer profiles
├── conformance/       deterministic valid and invalid DOT fixtures
├── composition/       read-only validate, plan, and dry-run scenarios
├── coverage/          executable code-coverage ratchets
├── e2e/               opt-in deployable behavioral scenarios
├── interoperability/  revision-pinned evidence and remaining-gap ledger
└── runtime/           isolated native-runtime lifecycle harnesses

testing is repository-level infrastructure, not a Maven module and not a deployable DOT. Authoritative test-only definitions live under DOT-Repository/DOTs/testing/ and are selected from compositions with repository://<dot-id>@<version>. Intentionally invalid conformance inputs stay under DOT-Testing/conformance/; they must never be admitted to the repository catalogue. Generated secrets, logs, reports, coverage profiles, and materialized configuration belong under scenario-local target/ directories and must not be committed.

The focused task testing:anchors:acceptance gate verifies the versioned DOT Anchor consumer profile. It resolves pinned test definitions from DOT-Repository, verifies the composition lock, and asserts the complete cross-standard plan without a deployed workload.

The separate task testing:compose:acceptance gate freezes the complete dot.mare6g.eu/v1 production profile. Its machine-readable source is DOT-Testing/acceptance/composition/v1/profile.json; the gate binds that source to CLI help, the tracked schema, repository locks, positive evidence, and negative fail-closed behavior. Runtime rows distinguish underlying single-DOT live lifecycle proof from multi-DOT composition lifecycle proof.

The focused task testing:compose:contract-standards gate complements that API profile with an executable composition matrix. It proves all six supported standard/format representations between the same provider and consumer DOTs; it does not promote planning evidence to live protocol or application acceptance.

The separate task testing:contracts:standards gate validates those payloads outside the DOT resolvers with standards-native tooling. The positive fixtures must pass and deliberately malformed OpenAPI, AsyncAPI, Protobuf, and GraphQL controls must fail. This catches both invalid examples and accidentally permissive validator invocations.

The runtime-configuration gate separately proves that selecting another executable deployment does not discard a service’s declared environment or configuration-file surface. Runtime-native storage, secret, privilege, and device semantics retain dedicated tests rather than being flattened into a misleading universal volume abstraction.

The multi-service live profile is the higher evidence layer for the exact workload bindings. Compose projects and their named volumes are keyed by the composition runtime identity; Kubernetes repetitions use separate namespaces; Helm repetitions use identity-derived release names in one namespace. The profile verifies that destroying one copy leaves the other healthy and that dotx-created ConfigMaps/Secrets are cleaned without deleting referenced operator-owned Secrets. The tracked Helm chart is packaged from the pinned checkout, and its SHA-256 is included in the redacted evidence artifact.

Coverage claims and gates

Coverage is reported by evidence dimension; the project does not collapse different meanings of “covered” into one percentage:

Dimension Gate Interpretation

Repository inventory

dotx validate DOT-Repository, dotx repository audit, and the DOT repository conformance workflow

Must be 100%: every filesystem definition is discovered, parsed, schema-valid, cross-reference-valid, uniquely identified, and stored in a supported category; no deployable copy may remain outside DOT-Repository.

CLI statements

task testing:cli:coverage

The whole CLI and every package containing executable statements must retain 100% statement coverage. The constant-only feature/sources package has no testable statements. This is a code-execution metric, not proof that a workload or security control works.

Java instructions and branches

mvn verify through JaCoCo 0.8.15

The Java domain module must retain 100% instruction and branch coverage. JaCoCo HTML/XML/CSV reports are uploaded with the Java build evidence.

Native runtime lifecycle

WebAssembly and Kubernetes/Helm runtime E2E workflows

Proves real Wasmtime CLI and HTTP behavior plus Minikube manifest/Helm lifecycle. It does not imply that every external DOT workload is accepted.

Composition scenarios

task testing:e2e:all:dry-run

Every listed deterministic scenario must validate, plan, and complete its supported lifecycle dry-run.

PoC interoperability

DOT-Testing/interoperability/pocs.yaml plus scenario-specific live workflows

Each of the eleven PoCs has traceable evidence, while remaining adapters, unavailable partner components, and unproved production behavior stay explicit.

The repository validation gate fails on duplicate identities, mis-scoped definitions, invalid DOTs, invalid Skill/category assets, or unresolved DOT Skill references. The workspace audit separately classifies uncatalogued, identical, divergent, and malformed definitions and fails on every deployable dot.json outside DOT-Repository. DOT-Testing/conformance/ fixtures are reported but exempt because invalid definitions are their purpose. During the staged migration, run:

dotx repository audit --repository DOT-Repository --workspace . --json

The statement report deliberately has no artificial 100% threshold: a high line percentage cannot replace negative tests, lifecycle checks, live probes, or partner acceptance.

Canonical Anchor scenario

DOT-Testing/e2e/api-gateway-oidc/ is the primary tutorial and lifecycle fixture. Its composition resolves three independently valid, test-scoped definitions from DOT-Repository:

  • Keycloak provides OpenID Connect discovery and token operations;

  • APISIX requires discovery information and provides a protected operation; and

  • an OAuth client requires the token and protected operations.

The composition uses three OpenAPI Contracts, three wires, explicit security configuration, Kubernetes Secret references, configuration-file and environment materializers, readiness dependencies, and one exposed Anchor.

Negative evidence is intentional

Rejected fixtures are part of the design evidence. They demonstrate that the model does not invent connectivity where the pinned source lacks a declared consumer input, does not treat stdout or a host path as a portable connection, and does not silently grant privileged runtime access.

Examples include:

  • PoC7 rejects a collector-to-scorer wire when the collector declares no such Anchor or configuration input;

  • PoC8 rejects an undeclared Prometheus-to-NDT handoff; and

  • invalid conformance fixtures cover missing Contracts, selectors, ports, duplicate bindings, and incompatible Anchor pairs.

Failing closed is a successful test outcome when the available evidence cannot support the proposed composition.

Adding or promoting a scenario

  1. Pin the exact external source revision used as evidence.

  2. Document what the source actually produces and consumes.

  3. Add deployable definitions according to ownership: third-party software under DOT-Repository/DOTs/external/, MARE-owned software under DOT-Repository/DOTs/internal/, and only synthetic fixtures under DOT-Repository/DOTs/testing/. Record their evidence and purpose in the applicable test evidence ledger and select them by exact repository://<uuid>@<version> identity.

  4. Define Contracts only for supported, observable interactions.

  5. Use contractless Anchors only when no supported Contract standard applies.

  6. Declare all service ports, configuration targets, privileges, and devices.

  7. Add negative fixtures for tempting but unsupported connections.

  8. Start under DOT-Testing/composition/ with validate and plan assertions.

  9. Add a lifecycle dry-run before any live execution.

  10. Promote to DOT-Testing/e2e/ only with isolated resources, explicit prerequisites, reliable cleanup, and externally observable assertions.

  11. Record what remains unproved in the interoperability ledger.

Interpreting results

A successful plan proves model consistency. A successful apply proves that the supported deployment adapters completed. Only an active scenario probe can prove that traffic, authentication, authorization, policy, or security behavior worked as intended.
