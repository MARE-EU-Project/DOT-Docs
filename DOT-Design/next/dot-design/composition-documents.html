Composition Documents and DOT Instances

A composition document is owned by the composer or operator, not by any member DOT. It selects immutable DOT identities and creates deployment instances whose topology may vary between environments.

Reusable composition catalogue

DOT-Repository/Compositions/ distributes reusable multi-DOT graphs, reviewed locks, READMEs, and non-secret deployment inputs. Start with keycloak-apisix-oauth/ (Keycloak, APISIX, OAuth client) or keycloak-prometheus-openapi-planning/ (official Keycloak and Prometheus OpenAPI operations). Each directory has composition.yaml and composition.lock.json.

From the standalone DOT-Repository checkout root:

dotx validate . --offline
composition=Compositions/keycloak-apisix-oauth/composition.yaml
dotx compose inspect "$composition" --locked --json
dotx compose apply "$composition" --locked --dry-run

Repository-wide composition validation requires the current source-built CLI; the released 0.2.4 binary predates this gate. It recursively checks declarations, semantic plans, adjacent locks, and READMEs without deploying or resolving Secrets. task compositions:render additionally renders every catalogue composition. There is no separate composition inventory or Scenario domain type.

A scenario is the broader use-case narrative and acceptance procedure described by the README. Synthetic matrices, negative controls, source-adapted PoC fixtures, executable harnesses, and evidence remain in DOT-Design’s DOT-Testing/. See Getting started for the gateway’s three Wires and Guided demo for live acceptance. Catalogue inclusion or a valid plan never implies production or live producer acceptance.

Composition documents and DOT instances

A composition is a separate versioned document. It names concrete instances of DOT definitions and pins their identities through the authoritative DOT-Repository catalogue. The repository://<dot-id>@<version> form is stable across checkout locations and prevents a scenario-local copy from drifting away from the reviewed definition:

This structural excerpt omits the required instance inputs and wires. Use DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml for the complete runnable document; Contract paths below are relative to that directory.

apiVersion: dot.mare6g.eu/v1
kind: Composition
id: e3000000-0000-4000-8000-000000000001
name: keycloak-apisix-oauth
version: 1.0.0
dots:
  - name: identity
    source: repository://Keycloak@26.0.7
    dotId: Keycloak@26.0.7
    dotVersion: 26.0.7
    deployment: kubernetes
  - name: gateway
    source: repository://APISIX@3.11.0
    dotId: APISIX@3.11.0
    dotVersion: 3.11.0
    deployment: kubernetes
    dependsOn: [identity]
contracts:
  - id: Keycloak@26.7.3::OpenAPI::Discovery
    source: ../../DOTs/external/Keycloak-DOT/versions/26.7.3/contracts/Keycloak-26.7.3-OpenAPI-Discovery.yaml

name identifies an instance inside this composition. source selects the repository definition by ID and exact version. dotx compose locates the nearest DOT-Repository containing a DOTs/ directory, discovers its definitions recursively, resolves the ID/version to its reviewed bundle, and then verifies that dotId and dotVersion match the loaded dot.json. Neither a repository definition nor a local path can silently substitute a different DOT. deployment selects a deployment by its stable deployment ID or unambiguous manifest alias.

Local discovery is the convenience default. --repository <path-or-Git-URL> selects another authoritative catalogue and --git-ref <revision> selects a Git revision. Locked and runtime-mutating commands require a full 40-character commit SHA for remote repositories; branch and tag names are allowed only for unlocked, read-only exploration. Exact commits are cached in a private user cache by normalized repository identity and commit, so the same plan and lock can be reproduced offline. Plans, locks, and lifecycle state record only the credential-free identity and resolved commit. Credential-bearing URLs are rejected; authentication remains external through Git credential helpers, SSH agents, or environment-backed CI credentials.

Relative paths remain supported for authoring experiments and external Contract documents. Reusable stable, sample, and test-only DOT definitions belong in DOT-Repository, under their corresponding catalogue scope. Contracts remain authoritative protocol documents and are referenced independently; placing a DOT in the repository does not copy OpenAPI, AsyncAPI, Protobuf, or GraphQL facts into its Anchors.

dependsOn is a readiness graph, not a connection graph. A wire does not imply startup order. This distinction permits reciprocal peer wires and brokered topologies without creating false dependency cycles.

Composition field reference

The emitted Draft 2020-12 JSON Schema is normative for the serialized v1 shape. This table is the study guide for its top-level ownership:

Field Required Meaning

apiVersion, kind

Yes

Fixed discriminators: dot.mare6g.eu/v1 and Composition.

id

Yes

Stable UUID of this composition, also used to derive local state and runtime identities.

name, version

Yes

Human-readable identity and version of the composition document.

dots[]

Yes, at least one

Named deployment instances. Every entry pins source, dotId, and dotVersion; published scenarios use an exact repository://<id>@<version> source. deployment, dependsOn, and deploymentInputs refine execution.

contracts[]

When a referenced Contract is needed

Maps an exact Contract ID to a local Contract document. The document’s embedded id must match.

wires[]

No

Connections between one PROVIDES and one REQUIRES Anchor. A composition with no wires can still expose a standalone capability.

exposedAnchors[]

No

Composition-local names for member Anchors that an operator may expose or forward.

Each wire requires name, from, and to. Both ends contain an instance name and Anchor ID. Optional endpoint selects a third-party or otherwise non-default service port; parameters supplies only Contract-declared template values; materializer or materializers writes resolved values; and security binds Contract security requirements to declared participant configuration. Unknown fields are rejected.

Deployment inputs and native workload bindings

deploymentInputs.environment, configFiles, and volumes identify the logical DeploymentService that owns each input. ociRuntime and cdiDevices authorize only requirements already declared by that selected DOT deployment. These fields supply instance values and grants; they do not expand the DOT’s declared configuration surface.

When a Docker Compose, Kubernetes, or Helm deployment contains several logical services with configuration, deploymentInputs.workloads is required for every configured service. The binding is deliberately instance-owned because native service names, labels, and containers can differ between deployment variants or environments:

deploymentInputs:
  workloads:
    - service: api
      compose:
        service: backend

The Kubernetes/Helm form uses exact-match standard labels and may select one container:

deploymentInputs:
  workloads:
    - service: api
      kubernetes:
        matchLabels:
          app.kubernetes.io/component: api
        container: api

Labels are combined with dotx’s instance ownership selector. A live apply must resolve exactly one Deployment, StatefulSet, or DaemonSet, and an omitted container is accepted only when that workload has one container. Two logical services cannot target the same Compose service or the same Kubernetes workload/container pair. Plans expose the binding and secret identifiers, and locks cryptographically pin them; neither contains resolved secret values.

DOT definition versus DOT instance

One pinned DOT definition can appear more than once in a composition. Each entry has a distinct composition-local name, runtime identity, deployment inputs, and wires while retaining the same dotId and dotVersion:

dots:
  - name: site-a
    source: ./federation-agent
    dotId: poc11-federation-agent@0.0.0-source.g303b353
    dotVersion: 0.0.0-source.g303b353
    deployment: docker
    deploymentInputs:
      environment:
        - {service: federation-agent, name: FEDERATION_NODE_ID, value: site-a}
  - name: site-b
    source: ./federation-agent
    dotId: poc11-federation-agent@0.0.0-source.g303b353
    dotVersion: 0.0.0-source.g303b353
    deployment: docker
    deploymentInputs:
      environment:
        - {service: federation-agent, name: FEDERATION_NODE_ID, value: site-b}

Wires reference site-a or site-b, never the source path. Docker Image deployments receive deterministic per-instance container, DNS, network, and named-volume identities. Apply rejects repeated instances for deployment mechanisms whose manifest-owned resource names cannot yet be isolated safely. One native Kubernetes instance may coexist with isolated Docker Image/Compose instances of that same DOT because they occupy separate resource scopes. Two native Kubernetes instances of the same DOT remain rejected, including when a Docker instance separates them in document order. See the Prometheus portability demonstration.

Changing a DOT’s version-specific ID does not isolate fixed resource names or ports. Apply and upgrade retain exact-ID collision checks and also check name-version product families, including fixed-port WASI HTTP instances. This conservative guard is not an identifier alias and does not change locks.

The executable example is DOT-Testing/composition/federation-peers/scenario.yaml.

After defining the participants, wire and configure their selected Anchors.
