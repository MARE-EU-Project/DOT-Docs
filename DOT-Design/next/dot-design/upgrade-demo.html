Stateless configuration upgrades and recovery

This optional technical-demo lane demonstrates native dotx compose upgrade with the existing external OPA DOT’s Kubernetes deployment. The OPA image and DOT ID/version stay unchanged; the composition version and policy input change. This is a configuration revision, not an OPA software-version upgrade. There are no copied product descriptors, persistent volumes or application-data migrations in this example.

The focused test graph lives under DOT-Testing/composition/opa-policy-upgrade/, not the reusable production catalogue: one revision deliberately contains invalid Rego. Its three composition documents and locks resolve the same canonical DOT-Repository/DOTs/external/OPA-DOT bundle. This lane has one DOT and an exposed Anchor, not multiple wired DOTs; use the four-Contract and secure-API lanes for those claims.

Prerequisites and preview

Use the DOT-Design checkout root on Linux amd64, with its exact pinned CLI installed (task cli:install), Task, Bash, jq, curl, GNU coreutils, ss, Docker, kubectl and a Ready local Linux-amd64 Minikube node. Select context minikube. Building that pinned CLI requires Go; follow the contributor installation instructions. Go is not needed by the installed binary during this live lane. The canonical OPA image is digest-pinned; Kubernetes must have it cached or be able to obtain it. Use an isolated demo cluster: this OPA API intentionally has no production authentication policy and must not be exposed publicly.

task testing:demo:upgrade:dry-run

This checks all three locks and renders their native deployment commands without deploying anything. It does not parse Rego or prove upgrade/rollback acceptance: the invalid policy is intentionally a runtime-negative fixture. The native upgrade diff requires an applied baseline, so the live lane runs it after apply.

Run, inspect, and clean up

# Optional overrides; keep them in the same terminal.
export DOTX_UPGRADE_PORT=19081
export DOTX_UPGRADE_NAMESPACE=dotx-opa-upgrade-presentation
task testing:demo:upgrade:present

Choose a fresh namespace and a free port; the harness refuses existing resources and does not adopt them. DOTX_UPGRADE_ROLLOUT_TIMEOUT defaults to 90s per Kubernetes rollout. Allow a few minutes: the broken revision intentionally waits for a rollout failure before native recovery.

The task automatically executes this sequence:

Stage Native lifecycle operation Required observation

Baseline 1.0.0

Locked compose apply

A viewer’s GET authorization decision is HTTP 200, result: true.

Review

compose upgrade --dry-run --json

Exactly one UPDATE for the existing OPA instance, with different input digests.

Target 1.1.0

Locked compose upgrade from 1.0.0 and its exact lock

Viewer decision becomes false; operator decision remains true.

Broken target 1.2.0

Locked compose upgrade from 1.1.0

The exact negative fixture fails parsing with the running OPA binary; its deployment fails rollout and the native command reports automatic rollback.

Recovered 1.1.0

Native status plus fresh API requests

Last-known-good version remains 1.1.0, no upgrade transaction is pending, viewer remains denied and operator remains allowed.

OPA’s decision API returns HTTP 200 for both boolean decisions; false is an authorization decision, not HTTP 403. In the separate secure-API composition, APISIX enforces that decision and returns HTTP 403 to its caller.

Say: "A valid DOT and lock do not guarantee valid application configuration. The runtime rejected this policy, and the CLI restored the last verified configuration before reporting failure. We then tested the recovered service."

The normal lane calls native CLI commands directly. It does not implement a second upgrade or rollback engine. Recovery is to the last successful 1.1.0 revision, not an undo of the previously successful promotion from 1.0.0. The baseline and target locks are required for both changes.

After successful recovery, presenter mode holds the running OPA instance for inspection. It prints the private run directory and a status command using that run’s cache and frozen kubeconfig. Inspect upgrade-diff.json, redacted result.json, API decision receipts and status snapshots. The saved failed-upgrade.log contains the expected failed rollout and native recovery; that failure is not silently treated as a successful upgrade. Routine native apply/upgrade output stays in private apply.log/upgrade.log; the terminal shows ordered progress stages and a final observed-decision table.

Press Enter to clean up. EOF, Ctrl-C and the bounded presenter timeout also invoke owned-resource cleanup. Successful acceptance requires a final cleanup=PASSED receipt. For noninteractive rehearsal use:

task testing:demo:upgrade:live

With Python 3 installed, task testing:demo:upgrade:rehearse uses the existing terminal-driven acceptance driver to verify the pause, inspect native status, send Enter and require verified cleanup. It records a summary and before/after checkout fingerprints; it fails if inputs change during rehearsal.

Boundaries and recovery

This proves one stateless native-Kubernetes configuration update and automatic recovery, not database rollback, zero downtime, all deployment adapters, policy distribution security or production certification. The exposed API Contract is the bundle’s ecosystem-derived PoC1 normalization, not an official comprehensive OPA OpenAPI document. The live checks verify the actual boolean decisions.

Current upgrade admission rejects changed stateful deployments and changed Helm/Vagrant deployments whose storage safety cannot be established. A pending transaction after interruption requires the native --resume or --rollback route documented in Composition lifecycle. Do not rewrite its state file, delete unrelated resources or bypass these checks.

If cleanup is interrupted, inspect the printed run’s evidence and use both its XDG_CACHE_HOME and KUBECONFIG for status/destroy. Never substitute a new cache or a changed global cluster context. Do not force namespace finalizers.

The existing Anchor live E2E workflow offers an explicit opa-policy-upgrade selection with the same harness and private evidence upload. The default PoC all matrix remains the established twelve scenarios; this optional technical lane is selected separately. Dry-run CI checks the fixtures through the existing presentation-validation job.
