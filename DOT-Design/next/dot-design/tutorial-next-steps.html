5. From a working lab to larger systems

You have built a real chain: Node Exporter → your Prometheus → Grafana. You authored a DOT, reused two others, connected required and provided interfaces, supplied configuration and a secret reference, verified actual traffic, and cleaned up. That is the reusable pattern behind larger systems.

Before leaving the Docker lab, destroy both lesson compositions using their original files and binary. Keep the private learning files if useful. Do not publish the exercise copies as additional Prometheus or Grafana catalogue roots.

What you can now do

You have practiced the complete small-system loop:

  1. Describe a release with Skills, verified Contracts and named Anchors.

  2. Select a deployment and declare its service configuration.

  3. Connect provided and required Anchors through reviewed Wires.

  4. Review exact inputs with validation, a lock and a deployment preview.

  5. Verify an actual API result, then clean up the owned resources.

Keep your final topology and the two successful query results as a learning record. This lab established those particular interactions. Production work also needs the security, persistence, operations and interface coverage in the production integration checklist.

Grow deliberately

Your next goal What changes What must be verified

Observe more targets

Select more instances and configure additional targets; keep reusable product definitions shared. Give each materialization its own reviewed configuration location.

Each intended target is actually scraped; labels distinguish producers; interruption and recovery affect only the selected instance.

Use another runtime

Choose a matching deployment from the same tool release. Review its service configuration, native workload selection and required permissions.

Readiness, real API behavior and cleanup on that adapter. The Docker/Kubernetes example is deployment portability, not proof of a cross-runtime Wire.

Cross a runtime boundary

Supply an explicitly provisioned external-gateway host/port using the existing execution profile. The operator retains gateway ownership.

Reachability from the actual consumer and attribution to the exact producer. There is no automatic infrastructure or protocol translation.

Package a multi-service tool

Declare each logical service’s ports, config and Anchor bindings. Bind services to exact native workloads at composition level when needed.

Separate configuration and secrets, same-Pod/container selection, peer isolation and ownership-safe cleanup. See services and inputs.

Use messaging or another API style

Select verified AsyncAPI, GraphQL, Protobuf or SPARQL operations through guided authoring. Broker transport endpoints are separate inputs.

The supported operation/transport profile, authentication and actual exchange. Four-standard test fixtures are not production-producer certification.

Operator capstone: authentication and policy

The next difficulty is controlling who can use an API. The existing Keycloak/APISIX/OPA/SPARQL composition provides a five-DOT exercise:

  • Keycloak provides identity and token operations.

  • APISIX routes a protected capability.

  • OPA decides whether a request is allowed.

  • Oxigraph provides the SPARQL query service.

  • A clearly labelled demo client exercises the authenticated path.

This is a separate advanced graph, not a claim that the preceding Grafana lab has already been secured or connected to it. Keep your tested monitoring system as the small reference while learning native Secret references, policy, multiple Wires and service startup. Only combine graphs after defining and testing the actual additional interfaces and ownership boundaries.

This capstone requires a qualified operator environment, Kubernetes, native Secrets and the matching source toolchain/artifact set. It is not a hidden prerequisite for the Docker tutorial. From the DOT-Design checkout root, after following the contributor setup and the secure-API prerequisites, the existing presenter route is:

task testing:pocs:present:secure-api

Expected: anonymous rejection, authenticated success, the expected RDF result and policy checks, followed by an inspection pause and owned cleanup. The full qualification route also exercises failure and interruption cleanup. Local HTTP defaults, synthetic clients and explicit-interface boundaries remain documented; this is not complete MARE producer acceptance.

Turn a learning result into a contribution

  1. For an existing product release, propose changes to its one canonical definition. For another supported release, use its exact release folder and release-matched artifacts and Contracts; see catalogue layout.

  2. Keep use-case files in a Composition. Document its purpose, prerequisites, selected deployments, topology, expected API results, cleanup and limitations.

  3. Validate against DOT-Domain’s generated schemas, inspect and review changed locks, then rehearse the affected real interactions and failure cleanup.

  4. Keep credentials and runtime state out of Git. Treat official and source-derived specifications honestly; a hash does not establish origin.

For exact CLI options use dotx <command> --help. For deeper explanations use DOT authoring, composition authoring, the complete model reference and production integration limits.

Contributors can rehearse the same included command blocks from DOT-Design with task testing:tutorial (declarations/previews) and task testing:tutorial:live (actual Docker services and cleanup). The test driver applies the documented editor changes, rather than maintaining a second tutorial definition. These are maintainer rehearsals, not independent newcomer-trial results.
