Docker and Kubernetes: four-Contract composition

This next development walkthrough reuses three canonical catalogue definitions: the standards-native provider, consumer, and official Mosquitto broker. Named deployment variants select Kubernetes for provider/broker and Docker for consumer. No product descriptor is duplicated.

The composition is named docker-kubernetes-four-contracts. Its template lives at DOT-Testing/composition/docker-kubernetes-four-contracts/scenario.yaml: this is a synthetic test graph, unlike the reusable catalogue examples keycloak-apisix-oauth and keycloak-prometheus-openapi-planning.

Provider and consumer are explicitly test-only components, not MARE analytics or vendor products. Real HTTP, GraphQL.js, gRPC-js and Mosquitto exchanges demonstrate interoperability mechanics, not producer acceptance, production security, or automatic protocol conversion. Probe clients use the actual consumer’s Docker network namespace; its application process is an inert deployment target. MQTT traffic is generated by the correlated delivery probe, not the GraphQL application. The MQTT runner uses the pinned official mosquitto_rr client in MQTT 3.1.1 mode, subscribing and publishing on the same Contract-selected channel. It waits for SUBACK before publishing, ignores retained messages, uses a clean session, and requires the exact uniquely correlated payload. This proves broker delivery, not an application-level request/response implementation.

Anchors select Contract operations. Wires select participants and materialize resolved endpoints into the consumer’s declared environment. Each wire declares EXTERNAL_GATEWAY: the selected DOT declares the NodePort Service, and Minikube provides the reachable node address. Docker normally isolates its bridge networks: the harness explicitly attaches only its disposable consumer to the existing minikube Docker network. Cross-runtime probes use --network container:<consumer> so they exercise that actual consumer route, not a different runner’s network. The attachment is external to dotx state, and consumer destruction removes it; the harness verifies its removal. No host listener, firewall change, tunnel, or Minikube-container modification is made.

Prepare before presenting

Use the full checkout in Contributor guide, and run commands from its root. Requirements: Linux amd64, Go and Task to install this checkout’s CLI, Git, Bash, jq, curl, GNU coreutils, flock (util-linux), Docker with Compose, kubectl, and a running local Minikube cluster using its Docker driver and minikube Docker network. The Kubernetes context must be minikube. The deterministic demo checks also require ShellCheck and Python 3. On Ubuntu, install the shellcheck package before running task testing:demo:checks. The introductory Prometheus quickstart still needs no Go or Kubernetes.

git submodule update --init --recursive
task ci:prepare
git rev-parse HEAD
git -C DOT-CLI rev-parse HEAD
git -C DOT-Repository rev-parse HEAD
go version -m "$(command -v dotx)"
docker info --format '{{.ServerVersion}}'
docker compose version
kubectl config current-context
kubectl get nodes --request-timeout=10s
minikube ip

dotx 0.2.4 alone is insufficient: this example uses post-release development changes. Install the pinned submodule and keep the checkout fixed. Evidence records revisions, CLI binary SHA-256, root/CLI/catalogue working-tree patch hashes, and provider/consumer image IDs. Non-empty patches mean the commit alone does not describe the tested checkout. Broker/probe images use digest references; the test images are locally built from pinned Dockerfiles/dependency locks, not claimed published immutable images. The provider uses imagePullPolicy: Never after explicit loading; the harness verifies actual running image IDs. Rehearse with network access for metadata/dependency/image downloads; caching does not promise fully offline execution.

Use an isolated demo machine/network. NodePorts are plaintext; MQTT permits anonymous access and disables persistence. Do not expose them to untrusted networks. These are demo defaults, not production authentication, TLS, retention, or availability settings. Never delete an unrelated namespace or Service.

Inspect without deploying

exec bash DOT-Testing/e2e/multi-runtime-demo/test.sh --dry-run

This resolves three DOTs/four wires, writes and verifies a lock, checks both platforms and all four standards, and renders deployment actions in a private directory under DOT-Testing/e2e/target/multi-runtime-demo/. The template uses documentation-only address 192.0.2.1; never manually apply that template.

Run the working example

Presenter mode: inspect before cleanup

task testing:demo:docker-kubernetes-four-contracts:present

Run in a real interactive terminal. The plan-derived Mermaid graph is laid out by the Go mermaid-ascii library embedded in dotx: Unicode boxes, cyan Kubernetes labels, magenta Docker labels and amber connection IDs. Parallel wires share a labelled arrow and each retains its own legend entry. The node inventory shows selected runtimes/deployments/versions; a T4 link identifies the MQTT transport endpoint, not another Anchor wire or an application publisher. Arrows mean logical PROVIDES-to-REQUIRES relationships, not packet direction. The graph is printed again after all four real probes and recorded status checks pass.

Only then does the harness pause. Use the printed, shell-quoted recovery/status command in a second terminal to inspect the exact live composition. plan.json, topology.txt, topology.mmd, probe logs, status.txt and result.json remain in the printed private run directory. The result is a probe summary, not fabricated API data. The graph deliberately omits endpoint hosts, configuration and credential values. topology.mmd can also be rendered in Antora. NO_COLOR=1 disables colours; DOTX_TOPOLOGY_COLOR=auto|always|never controls them (NO_COLOR or TERM=dumb takes precedence). DOTX_TOPOLOGY_WIDTH=80 sets a 40-240-column target; narrower screens use vertical/compact layouts. No connection may disappear to fit. The saved topology.txt is always plain text. Rendering needs only the dotx binary: no Python, Node, browser or separate mermaid-ascii executable. The Go module pins the upstream 1.6.1 source revision and verifies dependencies through go.sum; no renderer is downloaded at runtime.

# Read-only topology preview; Docker/Kubernetes need not be running.
dotx compose topology DOT-Testing/composition/docker-kubernetes-four-contracts/scenario.yaml --locked
dotx compose topology DOT-Testing/composition/docker-kubernetes-four-contracts/scenario.yaml --locked --color always --width 80
dotx compose topology DOT-Testing/composition/docker-kubernetes-four-contracts/scenario.yaml --locked --format mermaid

Press Enter to clean up normally. Ctrl-C exits 130, SIGTERM 143, EOF 1 and timeout 124, all through the existing ownership-checked cleanup path. Inspection defaults to 600 seconds; set DOTX_POC_PRESENT_TIMEOUT to an integer from 1 to 1800 to change it. Headless presenter launches and DOTX_E2E_KEEP=1 are rejected before runtime mutation. CI and the normal live task never pause, even when presenter environment variables are inherited.

task testing:demo:present:rehearse drives all five terminal outcomes against the real composition, verifies status while resources are still running, and requires verified cleanup. It is an acceptance preparation task, not the talk.

Noninteractive acceptance

exec bash DOT-Testing/e2e/multi-runtime-demo/test.sh --live

Equivalent Task: task testing:demo:docker-kubernetes-four-contracts:live. The harness locks the real Minikube address, builds/loads images, creates an isolated namespace and state cache, deploys through dotx compose apply --locked, checks readiness, and probes each wire with a 45-second timeout. It verifies recorded status, destroys the composition, removes its namespace, and checks for owned Docker leftovers.

Expect PASSED lines for rest-alerts, graphql-health, grpc-health, and mqtt-alert-delivery, plus exit zero and cleanup=PASSED. Inspect the printed run directory’s plan.json, render.txt, status.txt, and evidence.json to explain the locked plan, endpoint materialization and observations. Evidence JSON contains no passwords/tokens or response bodies. Each run retains its evidence; the top-level evidence.json is only the latest result, possibly an injected failure.

Rehearse the complete presentation

Present Prometheus first, authenticated Keycloak/APISIX/OAuth second, then the cross-runtime standards example:

task testing:demo:dry-run
task testing:demo:mqtt-suback:live
task testing:demo:rehearse

Rehearsal repeats all three live paths twice. Prometheus covers default/overridden ports and failure cleanup. OAuth verifies HTTP 401 without a token, token acquisition, protected access, native Secret references, status, and cleanup. The separate MQTT regression uses the actual pinned client and a loopback-only fault-injection peer: delayed, denied, or absent SUBACK, stale retained messages, and incorrect correlated payloads must behave correctly. This peer is not a replacement for the full composition’s real Mosquitto acceptance. Its ephemeral credentials and Keycloak development mode are not production defaults. The final mixed-runtime run deliberately fails after deployment: exit 42 and successful cleanup are required. Two further live runs receive actual SIGINT and SIGTERM after deployment and network attachment. They must exit 130/143, record cleanup success, and pass independent namespace/container/network checks. Run those checks separately with task testing:demo:interruption-cleanup.

The rehearsal prints one per-run summary.json under DOT-Testing/e2e/target/rehearsal/run-*/, with a separate log for every step, exit codes, durations, and before/after checkout and CLI fingerprints. Tracked patches and untracked-file content fingerprints are recorded for all three checkouts; no source or credential contents are copied into the receipt. Changed inputs during rehearsal fail acceptance. The convenience latest.json points to that per-run receipt, including failures; it is not a green badge. A dirty checkout remains explicitly labelled by its recorded status.

This is pre-presentation acceptance, not the short live talk itself. A per-user live-run lock rejects overlapping instances before deployment, including across checkouts using the same runtime/cache environment. DOTX_DEMO_LOCK_DIR is an override for isolated lock tests only; do not override it to run concurrent copies of this composition.

Recover safely

Normal failure, Ctrl-C and termination attempt cleanup. Do not use kill -9 or delete state while cleanup runs. After interruption, use the exact printed path:

RUN_DIR=/absolute/path/printed/by/the/failed/run
XDG_CACHE_HOME="$RUN_DIR/cache" dotx compose status "$RUN_DIR/scenario.yaml"
XDG_CACHE_HOME="$RUN_DIR/cache" dotx compose destroy "$RUN_DIR/scenario.yaml"

Inspect the namespace in that run’s render.txt; delete only that test-owned namespace if it remains. An apply failure may already have rolled back with no applied state; independently verify resource absence. Never prune Docker, remove Minikube, or delete unrelated volumes. Find the owner of an occupied NodePort before proceeding. Fix Docker user permissions before rerunning. Gateway timeouts require checking node IP, routing/firewall, readiness and Services; planning does not prove reachability. Contract download failures require repository access or verified bundle-local assets, never bypassing SHA-256 checks.

Catalogue readiness appendix

task testing:contracts:readiness
jq '.dots | group_by(.status) | map({status: .[0].status, count: length})' \
  DOT-Testing/e2e/target/catalogue-contract-readiness.json

Audit baseline: 69 valid definitions, 29 strict interface-profile passes and 40 gaps. Use the generated report for the actual checkout. Broker-only and negative fixtures do not necessarily need a business API. Official/source-derived Contracts, source-adapted PoCs, planning fixtures, stubs and producer doubles remain distinct evidence levels. See catalogue CONTRACT-AUDIT.md and Verification and examples. This demonstration does not promote the entire catalogue to production-ready.
