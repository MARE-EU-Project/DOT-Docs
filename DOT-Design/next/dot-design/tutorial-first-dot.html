1. Run your first DOT

Your first result is a running Prometheus service whose API reports the expected version. Start with reuse; you will author your own definition in Lesson 2.

Read DOTs for Dummies first for the models and project components.

Goal: deploy one existing DOT, verify its real API and remove only your instance. You will learn: tool identity, explicit deployment selection and the difference between a preview and a running service.

You need the prerequisites and isolated development host described in DOTs in Action. Run each Bash block only after the previous one succeeds. Keep the same terminal throughout the lessons. Parenthesized command blocks stop on errors inside their own shell; they do not close your terminal. A failed block is a stopping point, not permission to continue to deployment.

Choose your entry point

Just completed the quickstart? After its cleanup is verified, keep the same Bash terminal, checksummed CLI and pinned catalogue. Skip the installation below and continue at Make a private learning workspace. Do not download or clone the same files again.

Starting here? Follow the installation below from a new setup directory. If an earlier setup was interrupted, use the existing-setup instructions before creating or replacing anything.

Open a Bash terminal

Open a terminal on the Linux machine that will run Docker. If you are using SSH, connect to that machine first. Before setting any lesson variables, type bash and press Enter. Keep this Bash terminal for the commands that follow.

For a fresh setup only, create a new directory under your home directory:

DOT_SETUP="$(mktemp -d "$HOME/dot-setup.XXXXXXXX")" &&
cd "$DOT_SETUP" &&
pwd

pwd prints your current directory. Keep that path. Completed quickstart readers should use the book’s entry-point instructions and reuse their setup.

Check before installing

Run these checks on the machine where you will run the example, as your normal user. If you connect over SSH, run the commands on that remote machine. Stop if a check fails; fix the missing tool or access before continuing.

  • System: uname -sm should show Linux x86_64 for this documented route.

  • Commands: command -v bash git gh curl jq sha256sum should print one executable path for each of the six commands. Install any missing tools first.

  • Docker: docker info must show Docker server details without a permission or connection error.

  • Compose: docker compose version must print a plugin version. The older docker-compose command is not used here.

If a tool is missing, use its installation instructions for your Linux distribution, then repeat the failed check:

  • Git

  • GitHub CLI

  • jq

  • curl

  • Docker Engine

  • Docker Compose plugin

Bash and sha256sum normally come from your distribution’s Bash and coreutils packages. If either is missing, install those packages through your system administrator or distribution package manager. For Docker permission errors, ask the administrator for the intended access and rerun docker info as your normal user. Do not switch the tutorial commands to sudo to bypass that check.

Browser access from an SSH session

The printed localhost and 127.0.0.1 URLs refer to the machine running Docker. If your browser runs on that machine, open the printed URL. If commands run over SSH, the terminal API checks still run on the remote machine. To use a browser on your own computer, open a second terminal there and forward the chosen port through SSH:

ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18909:127.0.0.1:18909 user@host

Replace user@host with the same SSH destination used for the lesson. Replace both 18909 values if you chose another port. Keep this second terminal open and open http://127.0.0.1:18909 in your local browser. Stop the forward with Ctrl-C afterward; keep lesson commands in the original remote Bash terminal. The terminal API checks work without a browser. Keep the host firewall restriction: a tunnel does not change the deployment’s published interfaces.

Sign in and check repository access

You need access to the private MARE-EU-Project/DOT-CLI release assets and MARE-EU-Project/DOT-Repository catalogue. Signing in to GitHub does not grant that access: ask your MARE project contact if you have not been invited. You can read the published books without repository access.

Git handles the catalogue checkout. The GitHub CLI (gh) signs in and downloads the private release assets. Sign in once, then enable Git to use that account. If gh auth status already confirms the intended account and HTTPS Git access works, keep that setup and skip the sign-in block:

gh auth login &&
gh auth setup-git

Check that the account can see both repositories:

gh repo view MARE-EU-Project/DOT-CLI --json nameWithOwner &&
gh repo view MARE-EU-Project/DOT-Repository --json nameWithOwner

Expected: a JSON result naming each repository. If a command reports denied access or cannot find the repository, stop before downloading. Use gh auth status to check the active account, and ask your MARE project contact to resolve repository and release access if needed.

Install the released CLI

Run each block only after the previous block succeeds, in the same Bash terminal. From your fresh setup directory, download the binary and checksum file. For existing files, use Existing or interrupted setup instead of overwriting them.

mkdir -p dot-quickstart-download &&
cd dot-quickstart-download &&
gh release download v0.4.1 --repo MARE-EU-Project/DOT-CLI \
  --pattern dotx-0.4.1-linux-amd64 --pattern SHA256SUMS

Verify the downloaded bytes, then install the matching binary:

set -o pipefail
sha256sum dotx-0.4.1-linux-amd64 |
  grep -Fx -f - SHA256SUMS &&
mkdir bin &&
install -m 0755 dotx-0.4.1-linux-amd64 \
  "$PWD/bin/dotx" &&
export PATH="$PWD/bin:$PATH" &&
dotx version &&
printf 'Keep this CLI directory for recovery: %s/bin\n' "$PWD" &&
cd ..

The checksum must match the downloaded binary’s exact filename and bytes; installation is skipped if its entry is missing or wrong. Stop on any error. Expected version: dotx 0.4.1. This installation belongs to this setup directory. It leaves an existing dotx installation in place and changes PATH only in this terminal. Keep the printed bin path. The book’s saved session restores it in a new terminal; quickstart recovery must select that same directory explicitly. A normal new terminal keeps its usual command selection. After cleanup, close the tutorial terminal when you want to return to that selection; do not delete binaries needed for recovery. The release also provides an SBOM and build/acceptance revision manifest.

Check out the catalogue

Only the independently cloneable catalogue is needed. Pin the acceptance revision recorded in this CLI release’s manifest so it matches the binary:

gh repo clone MARE-EU-Project/DOT-Repository &&
cd DOT-Repository &&
git checkout --detach 6613a995a7406012aed1bc7bde2f1feabc3db935
Existing or interrupted setup

If the download files or DOT-Repository directory already exist, stop: do not add --clobber or delete a checkout to make the next command succeed. Return to the directory that contains your original downloads and catalogue. If another run still owns resources, keep its original binary and finish its cleanup first.

For a completed setup, check the existing download against SHA256SUMS, verify that your selected dotx has those same bytes, and check the catalogue revision. Reuse it only when all checks pass. Otherwise keep those files and begin a separate setup in a fresh directory.

From the existing catalogue root, with the original private bin selected on PATH, run:

(
set -euo pipefail
test "$(dotx version)" = "dotx 0.4.1"
test "$(git rev-parse HEAD)" = "6613a995a7406012aed1bc7bde2f1feabc3db935"
cd ../dot-quickstart-download
sha256sum dotx-0.4.1-linux-amd64 |
  grep -Fx -f - SHA256SUMS
installed="$(sha256sum "$(command -v dotx)")"
downloaded="$(sha256sum dotx-0.4.1-linux-amd64)"
test "${installed%% *}" = "${downloaded%% *}"
printf 'Matching CLI and catalogue verified.\n'
)

Expected: Matching CLI and catalogue verified. The sibling download path is this guide’s layout. For an older/custom layout, use its actual retained download location. Do not move a binary needed for recovery. An empty bin left by a failed install may be inspected and removed with rmdir before retrying; keep any nonempty directory and use the verification above or start in a new setup directory after previous cleanup is verified.

Make a private learning workspace

You are now in the matching DOT-Repository checkout root. The catalogue stays unchanged: exercises go in a new directory under your home directory. Save the printed path. If ports 18909, 19041 or 13000 are occupied, stop and select unused ports before the corresponding live lesson. To use different ports throughout, set DOTX_HTTP_PORT, TUTORIAL_PORT and DASHBOARD_PORT to unused values before the workspace block; it saves your choices. Use those chosen ports in browser links instead of the displayed defaults.

Optional: inspect the default ports

If ss is available (the distribution’s iproute2 package), run:

ss -ltn '( sport = :18909 or sport = :19041 or sport = :13000 )'

Rows below the header identify TCP listeners on those ports. No rows means none were listed only when there was no permission or connection error. This is a check at that moment, not a reservation. If unavailable, ask the administrator for the intended listener check. Use the port-conflict recovery if binding fails.

# Start in the matching DOT-Repository checkout, in Bash.
set -o pipefail
DOT_REPOSITORY="$PWD" &&
PROMETHEUS_JSON="$(dotx repository resolve Prometheus@3.15.1 \
  --repository "$DOT_REPOSITORY")" &&
DOTX_TUTORIAL_CLI="$(command -v dotx)" &&
DOTX_TUTORIAL_CLI_SHA256="$(sha256sum "$DOTX_TUTORIAL_CLI" |
  cut -d ' ' -f 1)" &&
LAB_PARENT="${DOTX_TUTORIAL_WORKSPACE:-$HOME}" &&
LAB="$(mktemp -d "$LAB_PARENT/dot-zero-to-hero.XXXXXXXX")" &&
DOT_BUNDLE="$(dirname -- "$PROMETHEUS_JSON")" &&
DOT_NAME="hero-$RANDOM-$RANDOM" &&
DOTX_HTTP_PORT="${DOTX_HTTP_PORT:-18909}" &&
TUTORIAL_PORT="${TUTORIAL_PORT:-19041}" &&
DASHBOARD_PORT="${DASHBOARD_PORT:-13000}" &&
DOTX_TUTORIAL_DOCKER_ID="" &&
export DOTX_HTTP_PORT \
  XDG_CACHE_HOME="${XDG_CACHE_HOME:-$HOME/.cache}" &&
(umask 077; declare -p DOT_REPOSITORY LAB PROMETHEUS_JSON \
  DOT_BUNDLE DOT_NAME \
  DOTX_HTTP_PORT TUTORIAL_PORT DASHBOARD_PORT XDG_CACHE_HOME \
  DOTX_TUTORIAL_CLI DOTX_TUTORIAL_CLI_SHA256 \
  DOTX_TUTORIAL_DOCKER_ID > "$LAB/session.bash") &&
printf 'Your private workspace: %s\n' "$LAB" &&
printf 'Resume with: source %q\n' "$LAB/session.bash" &&
dotx version --verbose &&
git -C "$DOT_REPOSITORY" rev-parse HEAD

repository resolve finds an exact tool release. LAB holds your private drafts; it is not another catalogue root. DOT_NAME distinguishes this first deployment from someone else’s instance. The saved session.bash contains paths and names, not credentials. After closing the terminal, source your own saved file to restore these variables before cleanup; do not create a new workspace instead.

Inspect before running

(
set -euo pipefail
printf '%s\n' \
  'Checking Prometheus and the selected Docker Compose deployment;' \
  'nothing starts yet...'
dotx validate "$DOT_BUNDLE" \
  --repository "$DOT_REPOSITORY" --profile reusable
dotx inspect "$DOT_BUNDLE"
dotx deploy "$DOT_BUNDLE" --deployment docker-compose \
  --name "$DOT_NAME" \
  --env "DOTX_HTTP_PORT=$DOTX_HTTP_PORT" --dry-run
printf '%s\n' \
  'Preview complete. Next: start this instance and check its API.'
)

Expected: validation succeeds, inspection lists deployment choices, and dry-run shows a Docker Compose command. Nothing has started yet.

The tool is Prometheus; docker-compose is the exact deployment ID. Choosing a different deployment does not create a different tool identity. Its definition already contains the pinned Compose document and image references; a random Compose file beside dot.json is not a deployment source.

Here is what Docker will do in this example. An image is the downloaded package containing Prometheus and what it needs to run. A container is a running instance of that image. The Compose document describes the services, network and storage to create together. This deployment stores its metrics in a named volume, separately from the container. Publishing a port connects Prometheus’s service port 9090 to your chosen host port (18909 by default), so a browser or curl on your machine can reach it. The cleanup step deletes this lab’s metrics volume; the downloaded image stays cached.

Get a real response

If deployment or verification fails, use the cleanup block below before retrying. Keep the original binary, instance name and cache until cleanup is verified. Before the first live deployment, record and save the original Docker daemon:

# First live entry only; an existing recorded target must still match.
if [[ -v DOTX_TUTORIAL_DOCKER_ID ]] &&
  current_docker_id="$(docker info --format '{{.ID}}')" &&
  test -n "$current_docker_id" &&
  { test -z "$DOTX_TUTORIAL_DOCKER_ID" ||
    test "$current_docker_id" = "$DOTX_TUTORIAL_DOCKER_ID"; }; then
  (
  set -euo pipefail
  DOTX_TUTORIAL_DOCKER_ID="$current_docker_id"
  test -f "$LAB/session.bash" &&
  test ! -L "$LAB/session.bash" &&
  session_update="$(mktemp "$LAB/session.bash.XXXXXXXX")" &&
  {
    trap 'rm -f -- "$session_update"' EXIT
    (umask 077; declare -p DOT_REPOSITORY LAB PROMETHEUS_JSON \
    DOT_BUNDLE DOT_NAME DOTX_HTTP_PORT TUTORIAL_PORT DASHBOARD_PORT \
    XDG_CACHE_HOME DOTX_TUTORIAL_CLI DOTX_TUTORIAL_CLI_SHA256 \
    DOTX_TUTORIAL_DOCKER_ID > "$session_update") &&
    chmod 0600 "$session_update" &&
    mv -- "$session_update" "$LAB/session.bash"
  }
  ) &&
  DOTX_TUTORIAL_DOCKER_ID="$current_docker_id" &&
  printf 'Recorded the original Docker daemon for this workspace.\n'
else
  printf '%s\n' \
    'Docker target is missing, changed or unreachable.' \
    'Restore the original session and Docker connection.' \
    'Do not replace its recorded ID.' >&2
  false
fi

The saved ID checks which daemon actually receives lifecycle commands, even if Docker context/environment selection changes. Repeat capture only for this fresh unstarted workspace; an existing recorded ID must match and is never replaced. A failed check requires restoring the original connection.

if test -n "${DOTX_TUTORIAL_DOCKER_ID:-}" &&
  current_docker_id="$(docker info --format '{{.ID}}')" &&
  test -n "$current_docker_id" &&
  test "$current_docker_id" = "$DOTX_TUTORIAL_DOCKER_ID"; then
  printf '%s\n' \
    'Starting Prometheus; Docker may download its pinned image...'
  dotx deploy "$DOT_BUNDLE" --deployment docker-compose \
    --name "$DOT_NAME" \
    --env "DOTX_HTTP_PORT=$DOTX_HTTP_PORT"
else
  printf '%s\n' \
    'Docker target is missing, changed or unreachable.' \
    'Restore the original Docker connection.' \
    'Do not replace its recorded ID.' >&2
  false
fi

Wait for readiness, then check the official build-information operation:

(
set -euo pipefail
ready=false
started=$SECONDS
next_notice=$SECONDS
printf 'Checking Prometheus readiness on port %s...\n' "$DOTX_HTTP_PORT"
for ((attempt=0; attempt<60; attempt++)); do
  if curl --fail --silent --max-time 2 \
    "http://127.0.0.1:$DOTX_HTTP_PORT/-/ready"; then
    ready=true
    break
  fi
  if ((SECONDS >= next_notice)); then
    printf 'Waiting for Prometheus: attempt %s/60, %ss elapsed\n' \
      "$((attempt + 1))" "$((SECONDS - started))"
    next_notice=$((SECONDS + 5))
  fi
  sleep 1
done
if ! $ready; then
  printf '%s\n' \
    'Prometheus readiness timed out.' \
    'Run the cleanup block before retrying.' >&2
  exit 1
fi
curl --fail --silent --show-error --max-time 5 \
  "http://127.0.0.1:$DOTX_HTTP_PORT/api/v1/status/buildinfo" |
  jq -e '.status == "success" and .data.version == "3.15.1"'
printf 'Verified: Prometheus 3.15.1 answered its official API.\n'
printf 'Open http://127.0.0.1:%s/\n' "$DOTX_HTTP_PORT"
)

Expected: Prometheus Server is Ready., true, then a Verified: message confirming Prometheus 3.15.1 and printing its browser URL. The loop is bounded: up to 60 attempts, each with a two-second HTTP timeout and a one-second pause. Open the printed URL (Prometheus with the default port). For a browser on another computer, use Browser access from an SSH session.

You have verified an actual service response, not just a valid definition. The selected Anchor names an operation; its Contract describes that operation; the service binding identifies the listening port.

Stop and verify cleanup

This Compose deployment’s destroy operation removes its named metrics volume. The data is disposable. Do not use another person’s instance name.

 
if test -n "${DOTX_TUTORIAL_DOCKER_ID:-}" &&
  current_docker_id="$(docker info --format '{{.ID}}')" &&
  test -n "$current_docker_id" &&
  test "$current_docker_id" = "$DOTX_TUTORIAL_DOCKER_ID"; then
  dotx destroy "$DOT_BUNDLE" --deployment docker-compose \
    --name "$DOT_NAME" &&
  remaining="$(docker ps -aq \
    --filter "label=com.docker.compose.project=$DOT_NAME")" &&
  test -z "$remaining" &&
  remaining="$(docker network ls -q \
    --filter "label=com.docker.compose.project=$DOT_NAME")" &&
  test -z "$remaining" &&
  remaining="$(docker volume ls -q \
    --filter "label=com.docker.compose.project=$DOT_NAME")" &&
  test -z "$remaining" &&
  printf 'Cleanup verified: %s\n' \
    'Prometheus containers, network and volumes are absent.'
else
  printf '%s\n' \
    'Docker target is missing, changed or unreachable.' \
    'Restore the original Docker connection.' \
    'Do not replace its recorded ID.' >&2
  false
fi

Expected: the instance stops and the three successful leftover queries print Cleanup verified: Prometheus containers, network and volumes are absent. Images remain cached. Keep LAB and the same terminal for the next lesson.

Resume or retry without losing your work

Paste the exact source …​/session.bash command printed by the workspace block. Source only your own saved file. Then verify the original binary and restore its PATH before continuing:

# Source your own saved session.bash first.
# Use the command printed in Lesson 1.
set -o pipefail
if [[ -n "${DOTX_TUTORIAL_CLI:-}" &&
      -n "${DOTX_TUTORIAL_CLI_SHA256:-}" &&
      -n "${LAB:-}" && -n "${DOT_REPOSITORY:-}" &&
      -v DOTX_TUTORIAL_DOCKER_ID ]] &&
  test "$(sha256sum "$DOTX_TUTORIAL_CLI" | cut -d ' ' -f 1)" = \
    "$DOTX_TUTORIAL_CLI_SHA256" &&
  { test -z "$DOTX_TUTORIAL_DOCKER_ID" ||
    { current_docker_id="$(docker info --format '{{.ID}}')" &&
      test -n "$current_docker_id" &&
      test "$current_docker_id" = "$DOTX_TUTORIAL_DOCKER_ID"; }; }; then
  DOTX_TUTORIAL_BIN_DIR="$(dirname -- "$DOTX_TUTORIAL_CLI")" &&
  export PATH="$DOTX_TUTORIAL_BIN_DIR:$PATH" &&
  dotx version --verbose &&
  printf 'Resumed existing workspace: %s\n' "$LAB"
else
  printf '%s\n' \
    'Saved session is incomplete, its CLI changed,' \
    'or Docker targets another daemon.' \
    'Source your own session file and recover the recorded binary' \
    'and Docker connection before managing this workspace.' \
    'Do not replace its recorded ID.' >&2
  false
fi

The saved session restores the repository, ports, instance name and cache location. A recorded Docker ID must also match the current daemon. A fresh session without a recorded runtime target can resume declaration work only; its live blocks require the target-recording step first. A missing ID field is an incomplete older receipt, not permission to adopt the current daemon. If the binary or Docker check fails, stop and recover the original checksummed CLI before managing existing resources. Passwords are never saved: for a running Grafana instance, repeat Lesson 4’s password prompt with the original lab password. Choose a new value only after that instance is cleaned up.

Change a port after cleanup

Keep an existing run’s actual ports until its cleanup is verified. After cleanup, source your own session and run the resume check. Set the replacement port, then save that choice before deploying again. Do not rerun workspace creation or change the instance name, binary, catalogue or cache.

For example, choose the replacement port in the current shell:

DOTX_HTTP_PORT=18919

Then save the current choices atomically in the existing session:

(
set -euo pipefail
test -f "$LAB/session.bash" &&
test ! -L "$LAB/session.bash" &&
session_update="$(mktemp "$LAB/session.bash.XXXXXXXX")" &&
{
  trap 'rm -f -- "$session_update"' EXIT
  (umask 077; declare -p DOT_REPOSITORY LAB PROMETHEUS_JSON \
  DOT_BUNDLE DOT_NAME DOTX_HTTP_PORT TUTORIAL_PORT DASHBOARD_PORT \
  XDG_CACHE_HOME DOTX_TUTORIAL_CLI DOTX_TUTORIAL_CLI_SHA256 \
  DOTX_TUTORIAL_DOCKER_ID > "$session_update") &&
  chmod 0600 "$session_update" &&
  mv -- "$session_update" "$LAB/session.bash"
} &&
printf 'Saved the current ports in your existing session.\n'
)

Expected: Saved the current ports in your existing session. The same step preserves later TUTORIAL_PORT and DASHBOARD_PORT changes when applicable. After resuming, print the chosen port and confirm it matches the retry. Do not save passwords, change the original binary/cache or recapture a Docker ID to bypass a mismatch.

What already exists Safe next action

base/dot.json or prometheus/dot.json

Validate and inspect the existing file. Do not rerun its creation block over your edits. Complete missing edits in your editor, then validate again.

prometheus.yml, Grafana inputs or a candidate

Open and review the existing file. Creation blocks refuse replacement; they do not reset an exercise for you. An incomplete, empty directory may be removed with rmdir before retrying; never delete a directory containing your work.

composition.yaml or dashboard.yaml, with its reviewed lock

Use the original file and dotx compose status with the restored repository. After an interrupted apply, use that lesson’s destroy command before retrying. Do not create another UUID or regenerate a lock to adopt leftover resources.

A successful destroy and verified cleanup

Runtime state is gone; COMPOSITION_STATE_MISSING is expected. That missing record alone does not prove resource absence. Keep the learning files rather than rerunning creation blocks. For compositions, require the native cleanup verification before starting another live graph.

If cleanup fails or Docker cannot be queried, cleanup is unverified. Keep the original files, cache and binary, restore Docker access, and retry the same cleanup command. Do not prune unrelated resources.

If a command failed, use the troubleshooting table and instance-scoped log instructions below. Never change a digest just to get past a validation error.

Troubleshoot this lab

The log block below is for this lesson’s standalone Prometheus instance, using its original DOT_NAME. For a composition, retain that graph’s draft, lock and cache and follow its lesson’s recovery instructions instead.

Symptom Action

Release or clone returns 404/403

Check gh auth status and organization repository access, including SSO authorization if required. Run gh auth setup-git for HTTPS cloning.

CLI missing or wrong version

Check command -v dotx; restore the original recorded private bin first on PATH. Do not install another binary while cleanup is unresolved.

Docker permission denied

Check docker info as your user. Ask the administrator for the intended Docker access, then log in again. Docker group access grants host-level power.

Compose unavailable

Install the Compose plugin/package for your Docker distribution and verify docker compose version. The legacy docker-compose executable is insufficient.

Port already allocated

Clean up the failed example, select a free DOTX_HTTP_PORT, and deploy again with the same name and explicit --env override. Book readers must also save revised ports in the existing session before redeploying. Quickstart readers must update their recorded port.

Docker target is missing, changed or unreachable

Restore the original Docker connection/context and environment, then compare its daemon ID with the recorded one. Do not replace the recorded ID to bypass the check. For an incomplete older receipt, recover the original context with the operator before lifecycle commands; do not adopt an arbitrary current daemon.

Contract download or digest check fails

Check network/proxy access to the declared URL. Never bypass its digest. Private raw GitHub URLs require MARE_READ_ONLY_TOKEN or GITHUB_TOKEN; gh login alone does not supply those to dotx. Use --offline only with matching documents already in the verified local cache.

Readiness or version fails

Use the instance-scoped logs below and dotx ps --all, check the selected image/port, then clean up. No local Compose file is required for this diagnostic.

Interrupted cleanup

Restore the original name and catalogue path, repeat cleanup, and inspect resources carrying com.docker.compose.project=$DOT_NAME.

Read only this instance’s logs

Keep the original DOT_NAME. This block discovers containers by their Compose project label and reads bounded logs. It works from the catalogue checkout: docker compose -p …​ alone would not locate the descriptor’s downloaded Compose document. No resources are changed or removed.

(
set -euo pipefail
containers="$(docker ps -aq \
  --filter "label=com.docker.compose.project=$DOT_NAME")"
if test -z "$containers"; then
  printf 'No containers found for this instance: %s\n' "$DOT_NAME" >&2
  exit 1
fi
while IFS= read -r container; do
  printf '\nLogs for this instance container: %s\n' "$container"
  docker logs --tail=100 "$container"
done <<< "$containers"
)

If Docker access fails or no matching container is found, the block fails; it does not query another instance. Use the same lesson’s cleanup command and retain the original context until cleanup is verified.

Checkpoint

Continue when you have:

  • Seen the official API report Prometheus 3.15.1.

  • Seen the explicit cleanup-verification message.

  • Saved your private workspace path and kept the original CLI and cache.

Explain it back: what did the dry-run prove?

It checked and previewed the selected deployment without starting the service. The later API call established the running service’s response and version. Successful cleanup established that this standalone run’s resources were gone. These are three separate observations.
