1. Run your first DOT

Your first result is a running Prometheus service whose API reports the expected version. Start with reuse; you will author your own definition in Lesson 2. Read DOT-Design 101 first for the models and project components.

Goal: deploy one existing DOT, verify its real API and remove only your instance. You will learn: tool identity, explicit deployment selection and the difference between a preview and a running service.

You need the prerequisites and isolated development host described in Zero to Hero. Run each Bash block only after the previous one succeeds. Keep the same terminal throughout the lessons. Parenthesized command blocks stop on errors inside their own shell; they do not close your terminal. A failed block is a stopping point, not permission to continue to deployment.

Install the released CLI

Authenticate with an account granted access to the private MARE repositories and releases. From a workspace directory:

set -o pipefail
gh auth login &&
gh auth setup-git &&
mkdir -p dot-quickstart-download &&
cd dot-quickstart-download &&
gh release download v0.4.0 --repo MARE-EU-Project/DOT-CLI \
  --pattern dotx-0.4.0-linux-amd64 --pattern SHA256SUMS &&
mkdir -p "$HOME/.local/bin" &&
sha256sum dotx-0.4.0-linux-amd64 |
  grep -Fx -f - SHA256SUMS &&
  install -m 0755 dotx-0.4.0-linux-amd64 "$HOME/.local/bin/dotx" &&
export PATH="$HOME/.local/bin:$PATH" &&
dotx version &&
cd ..

The checksum must match the downloaded binary’s exact filename and bytes; installation is skipped if its entry is missing or wrong. Stop on any error. Expected version: dotx 0.4.0. Add the PATH export to your shell profile for future sessions. The release also provides an SBOM and build/acceptance revision manifest.

Check out the catalogue

Only the independently cloneable catalogue is needed. Pin the acceptance revision recorded in this CLI release’s manifest, then check your Docker access:

gh repo clone MARE-EU-Project/DOT-Repository &&
cd DOT-Repository &&
git checkout --detach 2b17ee681fbe8eed6822834484f87149b32fc772 &&
docker info &&
docker compose version

Make a private learning workspace

You are now in the matching DOT-Repository checkout root. The catalogue stays unchanged: exercises go in a new directory under your home directory. Save the printed path. If ports 18909, 19041 or 13000 are occupied, stop and select unused ports before the corresponding live lesson. To use different ports throughout, set DOTX_HTTP_PORT, TUTORIAL_PORT and DASHBOARD_PORT to unused values before the workspace block; it saves your choices. Use those chosen ports in browser links instead of the displayed defaults.

# Start in the matching DOT-Repository checkout, in Bash.
set -o pipefail
DOT_REPOSITORY="$PWD" &&
PROMETHEUS_JSON="$(dotx repository resolve Prometheus@3.15.1 --repository "$DOT_REPOSITORY")" &&
DOTX_TUTORIAL_CLI="$(command -v dotx)" &&
DOTX_TUTORIAL_CLI_SHA256="$(sha256sum "$DOTX_TUTORIAL_CLI" | cut -d ' ' -f 1)" &&
LAB="$(mktemp -d "${DOTX_TUTORIAL_WORKSPACE:-$HOME}/dot-zero-to-hero.XXXXXXXX")" &&
DOT_BUNDLE="$(dirname -- "$PROMETHEUS_JSON")" &&
DOT_NAME="hero-$RANDOM-$RANDOM" &&
DOTX_HTTP_PORT="${DOTX_HTTP_PORT:-18909}" &&
TUTORIAL_PORT="${TUTORIAL_PORT:-19041}" &&
DASHBOARD_PORT="${DASHBOARD_PORT:-13000}" &&
export DOTX_HTTP_PORT XDG_CACHE_HOME="${XDG_CACHE_HOME:-$HOME/.cache}" &&
(umask 077; declare -p DOT_REPOSITORY LAB PROMETHEUS_JSON DOT_BUNDLE DOT_NAME \
  DOTX_HTTP_PORT TUTORIAL_PORT DASHBOARD_PORT XDG_CACHE_HOME \
  DOTX_TUTORIAL_CLI DOTX_TUTORIAL_CLI_SHA256 > "$LAB/session.bash") &&
printf 'Your private workspace: %s\nResume with: source %q\n' "$LAB" "$LAB/session.bash" &&
dotx version --verbose &&
git -C "$DOT_REPOSITORY" rev-parse HEAD

repository resolve finds an exact tool release. LAB holds your private drafts; it is not another catalogue root. DOT_NAME distinguishes this first deployment from someone else’s instance. The saved session.bash contains paths and names, not credentials. After closing the terminal, source your own saved file to restore these variables before cleanup; do not create a new workspace instead.

Inspect before running

(
set -euo pipefail
dotx validate "$DOT_BUNDLE" --repository "$DOT_REPOSITORY" --profile reusable
dotx inspect "$DOT_BUNDLE"
dotx deploy "$DOT_BUNDLE" --deployment docker-compose --name "$DOT_NAME" \
  --env "DOTX_HTTP_PORT=$DOTX_HTTP_PORT" --dry-run
)

Expected: validation succeeds, inspection lists deployment choices, and dry-run shows a Docker Compose command. Nothing has started yet.

The tool is Prometheus; docker-compose is the exact deployment ID. Choosing a different deployment does not create a different tool identity. Its definition already contains the pinned Compose document and image references; a random Compose file beside dot.json is not a deployment source.

Get a real response

If deployment or verification fails, use the cleanup block below before retrying. Keep the original binary, instance name and cache until cleanup is verified.

dotx deploy "$DOT_BUNDLE" --deployment docker-compose --name "$DOT_NAME" \
  --env "DOTX_HTTP_PORT=$DOTX_HTTP_PORT"

Wait for readiness, then check the official build-information operation:

(
set -euo pipefail
ready=false
started=$SECONDS
printf 'Checking Prometheus readiness on port %s...\n' "$DOTX_HTTP_PORT"
for ((attempt=0; attempt<60; attempt++)); do
  if curl --fail --silent --max-time 2 \
    "http://127.0.0.1:$DOTX_HTTP_PORT/-/ready"; then
    ready=true
    break
  fi
  if ((attempt % 10 == 0)); then
    printf 'Waiting for Prometheus: attempt %s/60, %ss elapsed\n' "$((attempt + 1))" "$((SECONDS - started))"
  fi
  sleep 1
done
if ! $ready; then
  printf 'Prometheus readiness timed out. Run the cleanup block before retrying.\n' >&2
  exit 1
fi
curl --fail --silent --show-error --max-time 5 \
  "http://127.0.0.1:$DOTX_HTTP_PORT/api/v1/status/buildinfo" |
  jq -e '.status == "success" and .data.version == "3.15.1"'
)

Expected: Prometheus Server is Ready. and true. The loop is bounded: up to 60 attempts, each with a two-second HTTP timeout and a one-second pause. Open Prometheus if you kept the default port.

You have verified an actual service response, not just a valid definition. The selected Anchor names an operation; its Contract describes that operation; the service binding identifies the listening port.

Stop and verify cleanup

This Compose deployment’s destroy operation removes its named metrics volume. The data is disposable. Do not use another person’s instance name.

 
dotx destroy "$DOT_BUNDLE" --deployment docker-compose --name "$DOT_NAME" &&
remaining="$(docker ps -aq --filter "label=com.docker.compose.project=$DOT_NAME")" &&
test -z "$remaining" &&
remaining="$(docker network ls -q --filter "label=com.docker.compose.project=$DOT_NAME")" &&
test -z "$remaining" &&
remaining="$(docker volume ls -q --filter "label=com.docker.compose.project=$DOT_NAME")" &&
test -z "$remaining" &&
printf 'Cleanup verified: Prometheus containers, network and volumes are absent.\n'

Expected: the instance stops and the three successful leftover queries print Cleanup verified: Prometheus containers, network and volumes are absent. Images remain cached. Keep LAB and the same terminal for the next lesson.

Resume or retry without losing your work

Paste the exact source …​/session.bash command printed by the workspace block. Source only your own saved file. Then verify the original binary and restore its PATH before continuing:

# Source your own saved session.bash first, using the command printed in Lesson 1.
set -o pipefail
if [[ -n "${DOTX_TUTORIAL_CLI:-}" && -n "${DOTX_TUTORIAL_CLI_SHA256:-}" &&
      -n "${LAB:-}" && -n "${DOT_REPOSITORY:-}" ]] &&
  test "$(sha256sum "$DOTX_TUTORIAL_CLI" | cut -d ' ' -f 1)" = "$DOTX_TUTORIAL_CLI_SHA256"; then
  DOTX_TUTORIAL_BIN_DIR="$(dirname -- "$DOTX_TUTORIAL_CLI")" &&
  export PATH="$DOTX_TUTORIAL_BIN_DIR:$PATH" &&
  dotx version --verbose &&
  printf 'Resumed existing workspace: %s\n' "$LAB"
else
  printf 'Saved session is missing/incomplete, or its CLI changed. Source your own session file and recover the recorded binary before managing this workspace.\n' >&2
  false
fi

The saved session restores the repository, ports, instance name and cache location. If the binary check fails, stop and recover the original checksummed CLI before managing existing resources. Passwords are never saved: for a running Grafana instance, repeat Lesson 4’s password prompt with the original lab password. Choose a new value only after that instance is cleaned up.

What already exists Safe next action

base/dot.json or prometheus/dot.json

Validate and inspect the existing file. Do not rerun its creation block over your edits. Complete missing edits in your editor, then validate again.

prometheus.yml, Grafana inputs or a candidate

Open and review the existing file. Creation blocks refuse replacement; they do not reset an exercise for you. An incomplete, empty directory may be removed with rmdir before retrying; never delete a directory containing your work.

composition.yaml or dashboard.yaml, with its reviewed lock

Use the original file and dotx compose status with the restored repository. After an interrupted apply, use that lesson’s destroy command before retrying. Do not create another UUID or regenerate a lock to adopt leftover resources.

A successful destroy

Runtime state is gone; COMPOSITION_STATE_MISSING is expected. Keep the learning files and continue with the next lesson, rather than rerunning creation blocks.

If cleanup fails or Docker cannot be queried, cleanup is unverified. Keep the original files, cache and binary, restore Docker access, and retry the same cleanup command. Do not prune unrelated resources.

If a command failed, consult quickstart troubleshooting for PATH, access, Docker, ports and download failures. Never change a digest just to get past a validation error.

Checkpoint

Continue when you have:

  • Seen the official API report Prometheus 3.15.1.

  • Seen the explicit cleanup-verification message.

  • Saved your private workspace path and kept the original CLI and cache.

Explain it back: what did the dry-run prove?

It checked and previewed the selected deployment without starting the service. The later API call established the running service’s response and version. Successful cleanup established that this standalone run’s resources were gone. These are three separate observations.
