Compatibility and migration policy

Select one tested artifact set

A product version alone is insufficient to identify the source-built ecosystem. Use either a released CLI with its release manifest and pinned catalogue, or a DOT-Design commit with its exact CLI/catalogue gitlinks. Record dotx version --verbose when reporting a problem. The CLI’s release acceptance manifest identifies its test fixtures; it is not a floating recommendation for current main.

DOT-Domain is the authority for portable models. Its generated schemas and Go bindings must agree. Composition apiVersion: dot.mare6g.eu/v1 identifies the input profile, not every runtime capability or CLI command. Locks and runtime state are executor artifacts, not portable domain models.

Current intentional boundaries

Area Current-source behaviour Upgrade requirement

Contract standard spelling

Only OpenAPI, AsyncAPI, Protobuf, GraphQL are accepted.

Released uppercase values such as OPENAPI are rejected, not normalised. Review an explicit document migration and affected locks.

Identifiers

Legacy textual/UUID DOT, Skill and Contract keys remain readable. Current catalogue coordinates use name@actual-tool-release and origin-DOT.id::standard::name; Anchors use DOT-local keys; Composition UUIDs retain their ownership role.

Renaming a catalogue identity changes references and lock inputs. It does not adopt existing runtime state or establish API compatibility.

Required capabilities

A DOT needs at least one meaningful Skill reference.

Older empty scaffolds need reviewed capability declarations, not guessed IDs.

Anchor identifiers

DOT-local kebab-case IDs and exact legacy UUID strings are accepted. Composition references still pair an instance with its Anchor ID; Composition ownership stays UUID-based.

Java Anchor IDs and references change from UUID to String; recompile callers. Migrate declarations, bindings, wires and exposed interfaces together, then review new locks. Old UUIDs and display names are never lookup aliases.

Contract ownership

Dependency interfaces resolve an explicit originating DOT; owned declarations cannot borrow a different release’s namespace.

Follow the catalogue’s IDENTIFIER-MIGRATION.md and CONTRACT-AUDIT.md. Do not copy a dependency Contract or relabel it as consumer-owned.

CLI commands

dotx compose inspect displays the resolved composition; no separate command or authored document is needed to represent that derived view.

Rebuild the CLI and regenerate reviewed locks using the resolutionDigest field. Clean up running compositions with their original binary before upgrading; saved state is not migrated or adopted.

Java Composition API

Probe protocols/transports/response matching and materializer choices use typed enums instead of Strings; exclusive choices receive Bean Validation.

Recompile Java clients and use, for example, AsyncAPIProtocol.MQTT instead of "MQTT" in builders/setters. Valid v1 JSON spellings and reviewed lock inputs remain unchanged. Validate required-property presence before deserialization.

Reference and collection validation

ID-only views validate identity, root declarations cascade payload validation, and dangling service Contracts/ambiguous logical keys are rejected. Root ID-only Contract JSON remains ID-only on a Java round trip.

Repair invalid references and duplicate keys explicitly; no aliases, deduplication or lock repair is performed. Recompile Java callers of the old setServices(Set) signature for setServices(Collection).

Lifecycle safety

Unsupported stateful and changed Helm/Vagrant upgrades fail before mutation.

A valid historical deployment does not guarantee admission to an upgrade. Never weaken safety checks merely to reproduce an older invocation.

Service configuration keys

Environment/CDI names, config-file paths, and volume names/paths are unique within each service. Java and CLI semantic validation reject ambiguous keys; the generated JSON shapes are unchanged.

Repair duplicates explicitly rather than relying on aggregation to select a winner. The same key in different services remains valid. Schema-only uniqueItems is not property-key uniqueness; use full DOT validation.

The original published CLI v0.2.5 predates these current-source model and authoring changes. These are not a claim of patch-level backward compatibility. The coordinated DOT-Design, DOT-Domain and DOT-CLI baseline is 0.3.0; it promotes the reviewed 0.3.0-rc.1 portable model surface without changing its generated schemas or reviewed compatibility corpora. The quickstart selects that release and its exact catalogue pin; historical documentation retains its historical artifacts. This is a new minor version on the pre-1.0 line, not another 0.2.x patch. Future breaking changes must likewise use a new minor version, rather than silently replacing an existing artifact. Publication does not make arbitrary CLI/catalogue combinations compatible.

From 0.3.0 to the upcoming 0.4.0

0.4.0 remains unreleased. Use the matching source-built CLI, generated schemas and catalogue pinned by one DOT-Design commit to try these changes. A source binary may still print dotx 0.3.0; record dotx version --verbose and its SHA-256, not just that label. Keep the released quickstart on its recorded 0.3.0 catalogue. See the release-readiness checklist.

The approved file-payload migration is an intentional input-format break, not a transparent 0.3.0 update. It changes file-document storage, not the selected tool releases or the meaning of Anchors and Wires.

Java clients must recompile: replace eu.mare6g.dot.domain.contract.ContractPayload with eu.mare6g.dot.domain.Payload, supply Payload values instead of embedded document Strings, and use ConfigFile.payload rather than defaultContent. Regenerate downstream bindings from the matching generated schemas; do not maintain a second hand-written input model.

Sensitive files must omit a default payload. Explicit deployment-instance inputs still override non-sensitive defaults. Scalar environment defaults, descriptions, image/chart references and WASM’s existing module/hash fields are not converted to file-document payloads. Composition instance inputs remain instance inputs; do not rewrite every string into a URL.

For a concrete current definition, inspect the pinned Prometheus DOT. The catalogue’s payload audit records the byte-preserving migration and hosting provenance. Prefer an exact, release-matched official raw file. Approved fallback Gists pin the full revision and filename; secret means unlisted, not confidential. Never upload credentials or private configuration, and obtain the required redistribution/hosting authority.

For a custom DOT, preserve the exact original document bytes (decode Base64 only where the old field actually used that encoding), publish only reviewed non-sensitive bytes, and hash those bytes without normalizing whitespace or line endings. Replace the file field with its URL/hash declaration; move a configuration default to payload and remove defaultContent. Use the generated schema and full validator, not a blanket text replacement. There is no automatic migration command or fallback to neighboring bundle files.

Before switching binaries, stop and destroy old instances with their original CLI, checkout and inputs. Retain application backups separately. Validate the target online to warm verified bytes, then offline; all selected deployment documents, not only Contracts, must be available and rehashed before mutation. A missing entry or digest mismatch fails closed. Do not repair the digest merely to accept changed bytes. Review affected locks explicitly and deploy a fresh test-owned instance; do not copy or edit saved state to adopt old workloads.

Safe migration procedure

  1. Record the current binary, repository revisions, compositions, reviewed locks and application-data recovery instructions. Preserve the original files.

  2. Use a separate checkout for the target artifact set. Read its migration and Contract-ownership notes before changing IDs, enum spellings or dependencies.

  3. Retain stable Anchor IDs for unchanged logical interfaces. dotx new --force creates a replacement scaffold; it is not an incremental editor.

  4. Run online dotx validate against the pinned catalogue once to populate the verified Contract cache outside the DOT bundles, also used for deployment/file payloads in current source. Then use --offline for definition validation, dotx compose validate and dotx compose inspect on the reviewed target inputs. A cold offline cache fails closed; it does not download Contracts or search for a local contracts/ folder. Cached bytes are rehashed, and a digest mismatch requires investigation, not replacing the pin. Generate a new lock separately and review its differences; never repair the old lock to make it appear compatible with a changed graph.

  5. Rehearse the supported lifecycle and actual API behaviour in an isolated, test-owned environment. Do not adopt live resources by renaming identities or editing private state. Stateful application migration remains application-owned.

dotx compose new already creates a template-based draft from a reviewed, adjacent-lock-verified composition, with a fresh ownership UUID. It preserves the selected DOT releases and wires; it does not infer a new graph, isolate fixed ports or shared inputs, migrate state, or create a lock automatically. See Create a composition from a reviewed example for preview, offline-cache requirements and explicit lock review.

Current-source dotx edit is a guided interface editor that writes a separate, validated candidate; it does not replace the canonical DOT, migrate state or repair locks. Current-source dotx compose new --from-dots selects exact DOTs, deployments and Anchors for a fresh draft, with conservative compatibility checks. Neither is present in the released v0.3.0 binary. See Edit an existing DOT and Build from selected DOTs. There is no automatic migration command or schema-version conversion. Retain manual review of interfaces, inputs, publication and locks.

Compatibility gates

task testing:models is the deployment-free local coding gate: Java validation, serialization and coverage; the all-public-model compatibility corpus; generated schema/Go agreement; CLI race tests and coverage; offline catalogue validation and reviewed locks. It starts no runtimes and dispatches no GitHub workflows. Initial tool bootstrap may require network access. Live adapter and presentation qualification remain separate through task ci:live and task testing:demo; coding-only checks do not establish runtime acceptance or publish Antora. Existing workflows remain configured for later verification.

task testing:compatibility runs the historical Contract/identity boundary tests and the existing generated Composition-model compatibility checks. The frozen Contract declaration comes from the exact catalogue pinned by CLI v0.2.5: it is expected to fail the new spelling constraint until an explicit change. Tests preserve its original UUID and payload pin. This is not a claim that the whole historical catalogue is accepted unchanged.

task testing:compose:acceptance additionally exercises current compositions, reviewed locks and tamper rejection. Authoring serialization oracles protect field ordering, omission and payload bytes. None of these gates starts a production producer or proves independent-adopter acceptance.

Before a release, run the full applicable local workflow equivalents, require all mandatory remote jobs to succeed, verify reproducible packages and downloaded binaries, and retain the exact accepted artifact set. Queued, cancelled, skipped or running checks are not passing required gates.

After 1.0, backwards-incompatible portable document changes require a new public model/profile version and a migration path. Before 1.0, breaking product changes require a minor-version increment and explicit compatibility notes; patch releases remain backwards-compatible except documented fail-closed security/correctness fixes. Deprecation notes must identify the old behaviour, replacement and removal release before removal, unless an immediate safety fix requires rejecting the operation.
