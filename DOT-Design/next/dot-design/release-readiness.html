0.4.0 release qualification and limits

The 0.4.0 release baseline targets Linux amd64 and the existing single-host execution profiles. The owner authorized direct stable publication on 2026-11-03, without requiring a public candidate first. Three unfamiliar-developer trials and licensing/redistribution/hosting reviews remain pending follow-up; they are not reported as complete. Publication in the existing private repositories does not establish independent adoption or blanket production certification.

Use the selected release’s actual assets and release-manifest.json for final source identities. The CLI acceptance manifest names immutable test fixtures; the Design manifest separately names its CLI/catalogue gitlinks. These are separate coordinates, not a circular chain of floating latest revisions.

Evidence Result and boundary

Local deterministic checks

Full CLI CI and Design deterministic CI passed: 163 Java tests, generated schemas/bindings, race tests, exact Go coverage, catalogue/locks, all 12 E2E dry-runs and Antora HTML/PDF/publication guards. No production model, CLI, catalogue definition or lock changed in this qualification increment.

Fresh clean-source demo and presenter qualification

All five task testing:demo phases passed in 32.9 minutes. All 19 qualification steps passed: seven live paths twice, failure and SIGINT/SIGTERM cleanup, and four terminal-driven presenter chapters. A separate short-guide rehearsal passed full flow, early finish, EOF, timeout and both signals. Sources and installed binary were unchanged before/after; owned cleanup was verified. Source-adapted and standards-native fixtures retain their labels; this is not full producer certification.

GitHub checks

The preceding refactor’s 17 validation/publication workflows and separate badge workflow succeeded, as did CLI CI. Its optional external linux-stress job was skipped, not passed. Those results belong to the preceding revisions, not the new source set above; fresh remote checks remain required. See Design runs and CLI CI.

Published documentation

The preceding Next publication and contributor guide were verified online. This updated audit still requires publication. Publication proves document availability, not live API acceptance.

Catalogue declarations, refreshed on the audit date

67 DOTs and five reusable compositions validate. 27 DOTs pass the strict interface-declaration profile; 40 report INTERFACE_GAP. The report explicitly sets liveProducerAcceptance: false. These counts apply to this catalogue SHA, not a permanent readiness percentage.

An earlier clean run, demo/run-s5qzi8m7/summary.json, remains failed: its SIGTERM case stopped at Kubernetes API preflight before workload adoption. The API was subsequently Ready and the entire fresh run above passed, but the transient failure’s cause is not proven. No timeout was weakened or cluster restarted; the failed receipt is not replaced by the later success.

Source-packaging checks produced byte-identical model archives and CLI packages; the packaged binary passed catalogue/interface acceptance. Full package verification nevertheless failed the SBOM/version identity gate: the untagged source still declares 0.3.0 while SBOM generation derives a pseudo-version. These are diagnostic source builds, not qualified 0.4.0 assets. Matching release metadata, exact tags and fresh artifact verification remain necessary; do not rewrite SBOM identities to turn that failure into a pass.

A subsequent private local tagged rehearsal aligned Design and CLI at 0.4.0 and passed version/SBOM verification without changing those identities by hand. The complete Design package was also reproduced byte-for-byte after a second clean Java verification build. This demonstrates the packaging procedure, not publication or acceptance of future release tags: the real repositories' versions and published tags are unchanged. A discovered incomplete-checksum inventory gap is covered by shared package checks and pre-execution regression tests; see the contributor guide. Versioned documentation also checks that its installation instructions select the aligned CLI release; private packaging alone does not qualify documentation.

Guided four-standard authoring, separate-candidate editing and from-DOT composition creation are implemented in source. Start with authoring or composition creation. The URL/hash payload migration and the explicitly approved removal of Anchor.semanticTypes are exceptions to 0.3.0 model compatibility. Contract-backed Anchors use verified operation selectors; undeclared Anchor keys are rejected without an alias. Affected locks require review. Clean existing workloads with their original CLI and inputs before switching; unrelated model changes remain out of scope.

Recheck from one checkout

From a clean DOT-Design checkout root, with its pinned submodules initialized and the contributor prerequisites installed:

task ci:deterministic
task ci:live
task testing:demo

These are full qualification commands, not presentation commands. Live gates start workloads, take substantially longer than coding tests and must verify test-owned cleanup. Do not run other rehearsals against the same owned profile concurrently. task demo is the short interactive presentation; it does not replace this qualification. See the full demo procedure for receipts, recovery and fallback selection.

To refresh only the catalogue evidence, follow the readiness report procedure. Keep official specifications, source-derived interfaces, runtime-only brokers, planning entries and fixtures distinguishable. Imported Protobuf graphs, complete Loki/OTLP coverage, stateful recovery, distributed orchestration and independent production-producer acceptance remain separate follow-up work.

See From a working demo to a production integration for per-gap review actions, selected-producer qualification, stateful/import acceptance criteria and the pending human/owner handoff. These are explicit follow-up boundaries, not additional capabilities claimed by this release.
