Contributor guide

This page covers building DOT-Design and running its shared local/GitHub gates. To use an existing DOT without installing development toolchains, start with Getting started.

Prerequisites

Tool Required for Project baseline

Java and Maven

DOT-Domain, schema generation, and Java tests

Java 27 (27.0.0+35-open in .sdkmanrc); Maven 3.10.0 from PATH

Go

Building and testing dotx

Go 1.27.2

Graphviz and fonts

Reproducing the legacy full-Maven-build SVG export, not running services

Local baseline: Graphviz 14.1.2 and Ubuntu fonts-noto-core / fonts-croscore 20201225-2build1. Missing tools or different font fallbacks can change the SVG even when the generated model source is identical.

Task

Repository command aliases

Optional but recommended

ShellCheck, Python 3, jq, Bash, and Git

Deterministic authoring, conformance, and demo-harness checks

Commands must be available on PATH, including to the self-hosted runner service user. ShellCheck is required; lint checks are not silently skipped.

Docker, Kubernetes tools, Helm, or Vagrant with libvirt/KVM

Only the matching deployment adapters and live scenarios

Install only what you intend to execute. The Vagrant workflow uses the runner service user’s existing KVM/libvirt permissions, without sg or sudo.

Antora, the Antora PDF extension, Asciidoctor PDF, and Mermaid CLI

Building the HTML/PDF documentation site, Mermaid diagrams and Ruby script syntax checks

CI uses Node.js 26 and Ruby 4.0; task docs:check reports the locally installed tool versions; see Build the documentation

Temporary storage

Keep the checkout and generated build outputs on a disk with sufficient free space. Full Go race/coverage builds and Contract-tool installation can exhaust a small memory-backed /tmp, even when individual tests need no deployment.

If a gate reports disk quota exceeded or no space left on device, check both the checkout filesystem and temporary storage. Set TMPDIR to a private, disk-backed directory outside every Git checkout, then rerun the failed gate. Negative Git-discovery tests deliberately remove fixture metadata; a parent checkout must not become an accidental fallback. Changing TMPDIR alone does not relocate generated files under the checkout’s target directories.

Retain failed logs and verify the rerun; a storage failure is not a passed test. Do not delete shared temporary files, other runs' resources or user caches.

Check out the repository

git clone https://github.com/MARE-EU-Project/DOT-Design.git
cd DOT-Design
git submodule update --init --recursive

The source repository and its two submodules may require access granted by the MARE-EU-Project organization. DOT-CLI and DOT-Repository remain separately cloneable; the generated Schema and high-level Skill classifications are tracked inside DOT-Repository and require no additional checkout.

When updating submodules, commit and push the child repositories first, then push the parent branch with a missing-submodule-commit check:

git -c push.recurseSubmodules=check -c push.followTags=false push

This refuses to publish a parent whose child commits are unavailable remotely. Release tags are published separately after qualification; a branch push must not publish prepared tags implicitly.

Verify the domain model

The domain module uses plain JUnit tests and does not start a service:

mvn -pl DOT-Domain test

Run the complete Java build with:

mvn clean install
# equivalent Task alias
task mci

The build generates CycloneDX JSON and XML software bills of materials during the Maven verify phase.

The full Maven build also regenerates diagram exports. Release packaging requires clean committed sources, including those exports. If rendering changes a tracked SVG, diagnose the source, renderer and fonts; do not discard the difference blindly or weaken the provenance guard to make packaging pass.

Install and test dotx

DOT-CLI is an independent Go module and is not part of the Maven reactor:

DOT-Design VERSION, its Maven artifacts and the pinned DOT-CLI/VERSION share the same version number. Run task testing:version:alignment to verify the checkout. Independent repositories and publication jobs do not imply independent version numbers; source revisions still identify unreleased changes. Antora keeps current development content under Next, preserving stable tags.

Install the standalone release with Go 1.27 or later. For the private module, authenticate Git first as described in Getting started and bypass the public Go proxy for this organization in this command only:

GOPRIVATE='github.com/MARE-EU-Project/*' go install github.com/MARE-EU-Project/DOT-CLI/cmd/dotx@v0.3.0
dotx version

The GitHub release also provides a checksummed Linux-amd64 binary, build metadata, and a manifest that pins the exact DOT-CLI source plus the DOT-Design and DOT-Repository acceptance revisions. For source development or the complete cross-repository suite, build the checked-out submodule instead:

task cli:build
task cli:test
task cli:install
dotx --version

task cli:install installs the pinned checkout into GOBIN or GOPATH/bin and installs Bash completion. Keep that directory on PATH; project tasks, test harnesses, examples, and CI all invoke the same dotx command rather than a repository-local binary.

Run GitHub workflow gates locally

For quick feedback while editing, from the DOT-Design checkout root:

task check

This source-read-only check uses existing authorities for version alignment, generated Go/schema drift, Go formatting and go vet, and syntax-checks maintained Python, Bash, Node and Ruby scripts without executing their bodies. It includes staged, unstaged and untracked sources, but excludes generated outputs, negative fixture sources and user presentation files. Have the documented toolchains and pinned quicktype/dependency caches prepared first: offline mode fails on a cold cache instead of downloading or installing tools. Temporary files and compiler caches may be used; tracked files are not repaired. This is not Java/Go test acceptance, full CI, live rehearsal or release proof.

For focused model/code iterations, start with the deployment-free gate:

task testing:models

It checks Java validation/serialization and coverage, all public-model corpus examples against generated schemas, Go bindings, CLI race tests and coverage, offline catalogue validation and reviewed locks. It starts no workloads or GitHub workflows. First-use setup may download pinned test tools. A coding-only push does not qualify a release or necessarily publish Antora; [skip ci] remains an explicit option for an authorized, locally tested batch, not a replacement for required release checks.

GitHub Actions and local pre-push validation share the root Taskfile test bodies. Actions still provisions clean toolchains and publishes artifacts, but the build, validation, conformance, coverage, runtime, and documentation commands are not CI-only shell fragments.

Ordinary test/report archives are best-effort. If an optional upload fails (including exhausted GitHub storage quota), the workflow emits a warning and job summary; tests, security checks and cleanup retain their original results. This covers any optional upload failure, not just quota errors. A green test run does not guarantee a downloadable archive or release qualification. Release evidence and artifacts consumed by another job or Pages remain mandatory. The optional dot-docs-site archive is not used for publication: the documentation workflow publishes the locally verified site directly to the publication branch, and publication failures still fail the job. Run task testing:ci:artifacts to check this boundary, including negative regressions. The check also runs in the deterministic workflow gate.

After the Contract-tool bootstrap, inspect the one source/acceptance pin report:

task testing:acceptance:pins
# Before pushing repositories that depend on unpublished acceptance commits:
task testing:acceptance:pins -- --remote

The report checks bootstrap copies against DOT-CLI/release/acceptance.json and the catalogue workflow’s CLI authority. It distinguishes current source revisions and dirty state from acceptance snapshot revisions. The optional read-only gh check requires repository access and fails if any dependency commit is unavailable on GitHub; it does not publish it. Publish acceptance foundation commits on explicit branches first when necessary, then CLI, catalogue and Design. Before each dependent push, rerun the remote check and retain the missing-submodule-commit push guard above. Equal version labels, available commits and successful declaration checks do not qualify live APIs.

task testing:ci:tools audits existing workflow action pins and tool-version authorities, including missing/late Node setup regressions. It uses the pinned Contract-tool Python environment; bootstrap it through the ordinary conformance gate, not an implicit runner-global package. These checks are included in task ci:contract-conformance and the full deterministic gate.

task ci:prepare
task ci:deterministic
task ci:compatibility-matrix

ci:prepare installs the pinned DOT-CLI checkout and verifies that dotx version matches the root VERSION. ci:deterministic runs every deterministic non-live release workflow gate, including Java and Go tests, schema drift, official Contract validation, repository and Anchor conformance, Composition v1, lifecycle recovery, upgrade, all PoC dry-runs, external-DOT rendering, coverage, Antora, and PDF generation. Individual equivalents are available as ci:build, ci:contract-conformance, ci:repository-conformance, ci:coverage, and ci:docs.

Publication regressions can also run alone:

bash DOT-Docs/scripts/test-publication.sh

These tests create their own release-history fixtures and verify a shallow, tag-free checkout, including concurrent site/badge updates against disposable local Git remotes. Actual versioned-site publication still requires complete release-tag history; its audit rejects missing history rather than silently omitting stable documentation. No runner reconfiguration is needed for these tests.

On push and pull-request events, the live workflows compare the exact Design and pinned child-repository Git trees. Only allowlisted, non-executable documentation changes can deliberately skip their live suites; these are reported as skipped, never as successful runtime acceptance. Documentation and conformance remain required. Missing history, changed definitions, schemas, locks, code, workflows, tool configuration, or unknown paths keep full live gates. Manual and scheduled executions always keep those gates. The classifier does not change which local checks you must run for a code change.

Run its deployment-free regressions with:

python3 scripts/test-ci-change-scope.py
ruby DOT-Docs/scripts/test-workflow-impact.rb

On a Linux host with all runtime prerequisites, run the mutable workflows too:

task ci:live
task ci:all

The live gate requires Docker, Minikube, Kubernetes, Helm, Wasmtime, Vagrant/libvirt, writable KVM access, Rust 1.98.1 with the wasm32-wasip2 target, and network access for the first official WASI HTTP sample build. The shared task fetches the exact pinned sample-wasi-http-rust revision into an ignored test cache, builds it with Cargo, and passes it to the runtime test, so local and GitHub executions cannot silently omit the WASI HTTP assertions. Set WASI_HTTP_COMPONENT only to reuse an already built component. The live gate performs runtime mutation and cleanup; ci:deterministic is the normal pre-push default.

Each self-hosted runner account needs its own working local Minikube profile and tool permissions. The multi-service rehearsal can initialize/select Minikube when no context is selected; it rejects a foreign context or unreadable configuration before starting anything. Missing tools and unavailable profiles remain failures, not skipped acceptance. Use the documented runner-selection variables to route runtime jobs to a properly provisioned account; do not copy another user’s kubeconfig or silently adopt its workloads.

For a Vagrant runtime on Ubuntu, install or reconcile the complete provider boundary and then open a new login session so the libvirt and kvm groups are active:

dotx tool install vagrant
dotx tool check vagrant

The installer selects qemu-kvm when the distribution provides it and falls back to qemu-system-x86 on releases such as Ubuntu 26.04. The readiness check also verifies the pinned vagrant-libvirt plugin, the qemu:///system connection, the default libvirt network, and /dev/kvm access.

Select GitHub Actions runners

The repository variable DOT_DESIGN_RUNNER defaults to self-hosted for build, validation, documentation and WebAssembly jobs. Set it to ubuntu-latest to use GitHub-hosted runners for those jobs.

  • DOT_DESIGN_CONTAINER_RUNNER optionally selects a Docker/Compose/Minikube runner; otherwise these jobs inherit DOT_DESIGN_RUNNER.

  • DOT_DESIGN_VM_RUNNER selects the Vagrant/libvirt runner. Configure it only for a label with verified KVM/libvirt access. When unset, the Vagrant job is skipped, not passed; required release acceptance still needs a qualified run.

Restrict access to self-hosted runners, keep their software current, and never expose privileged runners to untrusted forks. Runner administration and service permissions are infrastructure concerns, not a reason to weaken test assertions.

Maintain dependencies

Dependency versions are managed by the root pom.xml. GitHub Actions use immutable commit pins with release comments. Dependabot proposes Maven/Actions updates weekly; updates retain the applicable build, conformance and live gates.

task mci       # complete Maven build
task update    # propose latest non-prerelease dependencies

Use task --list for the available aliases. Dependency updates are intentional source changes, not prerequisites for running an existing DOT.

Editor assistance from the domain schemas

After changing DOT-Domain, generate schemas with the Java build, then run these from the DOT-Design checkout:

task cli:domain:generate
task cli:domain:check
task cli:domain:generation:test

The read-only check covers all generated Go domain bindings, embedded validation schemas, the authoring output projection and Composition artifacts. It reports changed, missing or orphaned generated files without repairing the checkout. Fix drift by regenerating and reviewing it, not by editing generated Go files. The authoring projection derives field names, types and order from the domain schemas/generated bindings; frozen outputs protect readable JSON and existing omission behavior. Node and quicktype remain build-time tools, not dependencies of the installed CLI.

Core model and field descriptions are generated from DOT-Domain’s Jackson annotations. Editors can show these descriptions alongside the same types, required fields and exact enum spellings used by validation. Do not edit generated schemas to change model documentation.

For a DOT-Design workspace, a VS Code JSON association can be configured in your local user/workspace settings (not in dot.json):

{
  "json.schemas": [
    {
      "fileMatch": ["**/dot.json"],
      "url": "./DOT-Repository/Schema/schema.json"
    }
  ],
  "yaml.schemas": {
    "./DOT-Repository/Schema/composition-v1.schema.json": "**/composition.yaml"
  }
}

The YAML association requires an editor YAML language extension. In a standalone DOT-Repository checkout, use ./Schema/ instead. Keep associations editor-side: adding $schema to a portable Composition is not supported. Editor hints do not replace dotx validate, semantic validation, reviewed locks or live acceptance.

Validate a DOT

dotx validate reads dot.json at the project root, falling back to dot/dot.json. The selected file is the unique DOT deployment definition; unreferenced Dockerfiles, Compose files, Kubernetes manifests, Helm charts, and scripts are not inferred.

dotx validate DOT-Repository/DOTs/testing/contract-standards/provider \
  --schema DOT-Repository/Schema/schema.json
dotx validate DOT-Repository/DOTs/external/Keycloak-DOT \
  --schema DOT-Repository/Schema/schema.json --profile reusable
dotx inspect DOT-Repository/DOTs/testing/contract-standards/provider --json

Base validation checks the JSON Schema and DOT-level Anchor, Contract, service-port, CDI, and sensitive-default relationships. Every declared Contract must be a complete URL/SHA-256 declaration in the owning dot.json. The validator never searches repository-level Contract directories or sibling DOTs. A bundle can therefore be copied and validated independently with an explicit schema path. A URL-backed definition declares one structured payload:

"payload": {
  "url": "https://raw.githubusercontent.com/vendor/project/v1.2.3/openapi.yaml",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}

Raw Contract text and the former flat payloadUrl/payloadSha256 shape are rejected. Validation downloads the exact bytes, rejects non-HTTPS or mutable raw-GitHub branch URLs, verifies the digest, parses the declared standard/format, and resolves Anchor selectors. Missing IDs, incomplete declarations, digest mismatches, and unresolved selectors always fail validation. Use --profile reusable before publishing a stable reusable DOT. That profile additionally requires at least one pinned Contract, rejects unused Contracts, and requires every deployment to bind each Contract-backed provided Anchor exactly once through a service that declares the same Contract. Explicit contractless Anchors retain base-validation evidence only; they are never silently promoted to Contract-backed interoperability.

For an external product, prefer a complete root Contract declaration pointing to an official versioned vendor raw file. A full Git commit or release-version tag is accepted for raw.githubusercontent.com; main, master, and other mutable branch names are rejected. When no official usable raw machine-readable Contract exists, catalogue declarations may point to a clearly attributed derived/adapter document hosted in a secret GitHub Gist. Use the HTTPS host gist.githubusercontent.com with path owner/gist-id/raw/40-character-revision/filename and the SHA-256 of the exact raw bytes. Unversioned Gist URLs, HTML Gist pages and Gist query parameters are rejected. A secret Gist is unlisted, not private; anyone with its URL can read it without authentication. The CLI does not send GitHub tokens to Gist downloads. Keep the original source, license and authority in the Gist’s PROVENANCE.json; hosting does not make a derived document official or prove live acceptance. Existing unresolved license notices remain unresolved.

All current catalogue declarations now include their URL-backed metadata. No local Contract directory is required or used. Compositions select the exact owning DOT with source: repository://name@release, retaining the originating Contract ID. Run dotx validate DOT-Repository online once, then use dotx validate DOT-Repository --offline. The shared digest cache lives under $XDG_CACHE_HOME/dotx/contracts/sha256/ (normally ~/.cache/ on Linux). Every cache read rechecks SHA-256; a cold offline cache fails without downloads or writes, and corruption is never silently repaired. Payload availability is not producer acceptance. Shared Contract IDs still require identical metadata and bytes; root ID-only declarations cannot fall back to local or sibling files. For private raw GitHub URLs, dotx reads MARE_READ_ONLY_TOKEN, falling back to GITHUB_TOKEN, and sends it only to raw.githubusercontent.com; credentials must never appear in payload.url. Inspection provides a normalized, machine-readable view without deploying anything.

Validate and inspect a composition

The canonical example connects Keycloak, APISIX, and an OAuth client:

dotx compose lock \
  DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml --check

dotx compose validate \
  DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml

dotx compose inspect \
  DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml

dotx compose inspect \
  DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml --json

dotx compose apply \
  DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml --dry-run

All five commands above are non-mutating. lock --check verifies the committed content-addressed input graph; validate answers whether references and compatibility can be resolved; inspect shows the exact instances, endpoints, security status, and materializers; apply --dry-run renders supported runtime actions without writing composition state.

Read Validation, resolution, and lifecycle before a live apply.

Verify the authoritative repository

Recursively discover and validate every definition. External/internal paths record ownership; Contract-backed external/internal bundles receive the strict reusable profile:

dotx validate DOT-Repository
dotx repository inspect \
  contract-standards-provider@1.3.0 \
  --repository DOT-Repository --json

The same command is the required DOT-Repository GitHub Actions gate for every change below DOTs/ or .gitmodules. The filesystem is authoritative; no separate inventory or validation wrapper is maintained.

Run task testing:contracts:portability to copy every bundle into an isolated temporary directory and validate it offline against the explicit catalogue schema. This is also part of ci:repository-conformance; it prevents a valid repository checkout from concealing a dependency on sibling files. Each owned Contract must carry its complete URL/hash declaration; offline verification uses the digest cache outside the bundle, never local Contract assets.

Run the composition conformance gate

task testing:conformance

This gate combines Java domain tests, Go tests, repository-wide schema validation, Contract checks, composition validation/resolution, and dry-run scenario checks. It does not claim that external partner systems or production networks were exercised.

Run only the versioned composition production profile with:

task testing:compose:acceptance

This gate writes revision-pinned, secret-free JSON evidence below DOT-Testing/e2e/target/.

Build the documentation

Install the documentation toolchain once:

task docs:setup

Then generate the Antora HTML site and PDF export:

task docs:check
task docs:build

Generated artifacts are written under DOT-Docs/build/site and are intentionally ignored by Git. To build and serve the site locally:

task docs:run

Open http://localhost:8000. Do not edit files under DOT-Docs/build; update the AsciiDoc sources instead.

Mermaid sources are stored as Antora attachments and rendered locally by task docs:diagrams. The renderer produces SVG for the HTML site and high-resolution PNG for PDF export; both outputs are committed so a clean checkout can resolve every Antora resource. Each source includes an accessible title and description, and each AsciiDoc image macro supplies alternative text.

task docs:build regenerates the diagrams before building either output. The toolchain is version-pinned and does not send architecture content to an external rendering service. Edit the .mmd source, never the generated SVG or PNG, then run the full documentation build to verify both renderers.
