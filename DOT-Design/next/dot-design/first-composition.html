Run your first composition

Run two tools together on Docker. The catalogue’s monitoring composition connects Node Exporter’s node-metrics Anchor to Prometheus’s scrape-target Anchor through the node-metrics-to-prometheus Edge. Prometheus runs the scrape. You verify it through the exposed prometheus-query Anchor.

Before you start

  • Use Bash, Git, curl, ss (from iproute2), and Docker Engine on Linux amd64. Run the commands on the Docker host. This graph uses Docker images.

  • Reuse the installed release of dotx and the matching GitHub catalogue checkout from the quickstart. For a fresh setup, follow that guide through cloning DOT-Repository from GitHub. You can start here once setup succeeds.

  • Use an isolated development Docker host. Released dotx 0.4.1 leaves the host bind address to Docker, and this example’s HTTP API has no authentication. Run one copy at a time and allow for initial image and document downloads.

Check your installation

Run these commands from the standalone DOT-Repository checkout root. Keep this shell and Docker context through cleanup.

dotx version &&
git rev-parse HEAD &&
dotx tool check docker

Check the CLI version and catalogue revision against the quickstart’s selected release and pin. Continue when Docker reports ready.

Validate, see the Edge, and preview

GRAPH=Compositions/node-exporter-prometheus-monitoring/composition.yaml
PORT="${PORT:-19040}"

dotx compose validate "$GRAPH" --locked &&
dotx compose topology "$GRAPH" --locked &&
dotx compose apply "$GRAPH" --locked --dry-run \
  --forward "prometheus-query=$PORT"

Expect two Docker image deployments and the node-metrics-to-prometheus Edge. With released dotx 0.4.1 and the default port, the preview shows -p 19040:9090 for Prometheus. A matching source build with loopback forwarding shows -p 127.0.0.1:19040:9090 instead. The preview creates no workloads and writes no lifecycle state. Validation and preview can populate the cache with verified inputs.

Save the cleanup command and check the port

Keep this cleanup command handy before you apply. After your apply attempt, run it if your run created state, even if the query fails. If apply reports a previously applied composition, leave that run to its owner.

dotx compose destroy "$GRAPH"

Before deploying, check the selected port from the same host:

ss -H -ltn "sport = :$PORT"

No output means no TCP listener was found at the time of the check. If it shows a listener or Docker reports the port is occupied during apply, leave that listener alone. Clean up any state created by your attempt, choose another unused port with PORT=19041 (for example), then repeat the port check and preview. Use that same PORT for apply and the query.

Apply and verify

Run apply after reviewing the preview for your chosen port on the isolated development host.

dotx compose apply "$GRAPH" --locked \
  --forward "prometheus-query=$PORT"

After apply succeeds, ask Prometheus whether it can scrape Node Exporter.

curl -fsSG --max-time 5 \
  "http://127.0.0.1:$PORT/api/v1/query" \
  --data-urlencode 'query=up{job="node-exporter"}'

Expect "status":"success" and a sample whose job is node-exporter and whose value is "1". An empty result or a connection error immediately after apply can mean Prometheus is still starting or waiting for the first scrape. Retry the query for up to 90 seconds. If it still fails, inspect status and then clean up. This example observes the Node Exporter container.

Inspect and clean up

dotx compose status "$GRAPH"
dotx compose destroy "$GRAPH"

Expect destroy to report verified cleanup of both Docker deployments and their managed network and disposable volumes. You can repeat the port check to confirm the demo listener is gone.
