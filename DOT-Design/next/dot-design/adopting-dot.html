Adopting DOT

DOT connects reusable component descriptions, authoritative API Contracts, deployment choices and explicit composition wires. It does not replace OpenAPI, AsyncAPI, Protobuf, GraphQL, Docker Compose, Helm or Kubernetes. Start by reusing a complete catalogue bundle, not by inventing a new descriptor.

Choose a compatible set

The site opens Next: documentation for the current source checkout, not a promise that every command exists in the latest published binary. Use the version selector for historical release documentation.

Artifact Compatibility rule

Published CLI binary

Use its immutable release tag, checksum, acceptance manifest and matching catalogue revision. The released quickstart pins that catalogue explicitly; do not substitute current main.

Source-built CLI

Use the exact DOT-CLI and DOT-Repository submodules pinned by the DOT-Design checkout. dotx version --verbose identifies the revision and modified state. The source version label alone does not identify its capabilities.

DOT definition and Contract versions

These describe the component and interface, not the CLI release. Keep stable IDs, select exact DOT versions and review changed payload hashes and locks.

Composition v1

apiVersion: dot.mare6g.eu/v1 selects the portable Composition input model. It does not imply support for every adapter, probe or future extension.

Current source supports textual Skill/Contract IDs and exact Contract standard spellings OpenAPI, AsyncAPI, Protobuf, GraphQL; format retains its separate uppercase vocabulary. The original published CLI v0.2.5 predates these changes and the bundle-aware prerequisite check below. Do not silently rewrite IDs, spelling, manifests or reviewed locks to make mismatched artifacts appear compatible. Follow the pinned source route in the contributor guide for current catalogue work.

Edit with the actual model schema

Opening the DOT-Design root in VS Code associates dot.json with DOT-Repository/Schema/schema.json; opening the standalone DOT-Repository root uses Schema/schema.json. Both checkouts include workspace associations. JSON editing uses the built-in language service. For YAML compositions, enable the recommended Red Hat YAML extension; its workspace association uses the generated composition-v1.schema.json. No DOT-specific editor plugin is needed.

For other editors, associate those same local files with dot.json and composition.yaml, respectively. Use a matching pinned catalogue rather than a mutable remote schema. The generated schemas provide field descriptions, allowed values and structural validation without a Java runtime. Do not add an editor-only $schema property to DOT definitions: use editor configuration instead, preserving the portable document shape.

Editor validation is only the first check. It cannot replace bundle-local Contract integrity, Anchor selector resolution, catalogue identity checks or locked composition validation. Run dotx validate and the applicable local CI Tasks before committing. There is no automatic migration or lock repair.

Check the selected deployment without starting it

Current source only. From a DOT-Design checkout with its source CLI installed:

dotx version --verbose
dotx inspect DOT-Repository/DOTs/external/Prometheus-DOT
dotx tool check --dot DOT-Repository/DOTs/external/Prometheus-DOT --deployment docker-compose
dotx tool check --dot DOT-Repository/DOTs/external/Prometheus-DOT --deployment docker-compose --json

From a standalone catalogue checkout use DOTs/external/Prometheus-DOT instead. For a standalone bundle outside a catalogue add --schema /path/to/matching/Schema/schema.json.

The command requires an exact deployment ID, validates the bundle offline with the ordinary validator, and checks only that adapter’s prerequisites:

Manifest Prerequisites checked

DOCKER_IMAGE

Docker CLI and daemon

DOCKER_COMPOSE

Docker CLI/daemon and Compose plugin

KUBERNETES_MANIFEST

kubectl and selected cluster

HELM_CHART

kubectl/cluster and Helm cluster access

VAGRANTFILE

Existing Vagrant/libvirt/KVM readiness checks

WASM_MODULE

Wasmtime installation

Expected Compose output includes Definition: validated offline, docker: ready=true and compose: ready=true. Every applicable tool is checked even when another fails. No downloads, installation, cluster startup, workload mutation or cleanup occur. Missing or tampered local Contracts fail before tool checks. Warm a bundle’s verified Contract assets through the ordinary online validation path separately if necessary; do not bypass a digest mismatch.

JSON has formatVersion: 1, ready, validated, selected deployment and manifestType, ordered checks, shared validator diagnostics and an explicit evidence scope. Check exit status as well as the report: 0 means checks passed, 1 means validation/tool failure, 2 means usage error. Ordinary JSON failures leave stderr empty; raw subprocess output and configuration values are withheld.

ready applies only to these checks. Instance inputs and permissions, available images, free ports, artifact reachability, storage and live API behavior still need their own checks. This is neither deployment authorization nor production certification. Continue with the first DOT or composition demo using that walkthrough’s compatible artifact set.

Integrate without duplicating the model

All portable inputs are owned by DOT-Domain: consume its generated Schema/schema.json, Schema/composition-v1.schema.json and Schema/models/*.schema.json. Do not maintain a competing schema, struct model or copied Contract operation catalogue. Executor plans, locks and runtime state are CLI concerns rather than portable domain inputs.

DOT, Skill and Contract identities are case-sensitive textual IDs; legacy UUID-shaped strings remain accepted. Catalogue DOT IDs use <name>@<tool-release>; Contract IDs use <origin-DOT.id>::<standard>::<name> with canonical standard spelling. Every DOT must reference at least one meaningful Skill. Anchor and Composition identities remain UUIDs. A DOT name or version change therefore changes its catalogue identity; update composition pins and regenerate reviewed locks. IDs are not a replacement for the raw Contract URL plus SHA-256. The integration handoff and executable acceptance profiles document cross-reference, conservative compatibility and runtime boundaries.

Independent onboarding trial

Use this checklist with three developers who did not implement DOT. The targets below are proposed usability goals, not measured results or acceptance claims.

  1. Give each participant only repository access, a compatible Linux-amd64 host, Docker/Compose and the documentation entry point. Record exact revisions and whether images/Contracts were already cached.

  2. Ask them to follow the released quickstart: install, find the DOT, validate, deploy, obtain the expected API response and clean up. Target: ten minutes of hands-on work, recording cold-download time separately.

  3. Using the current-source route, ask them to inspect another deployment, explain one Contract/Anchor/wire, introduce an invalid reference, interpret the diagnostic and repair it. Record every undocumented intervention.

  4. Check cleanup removed only their test-owned resources. Never remove another participant’s workloads, volumes or forwards.

  5. Keep redacted receipts, timings, failed commands and documentation gaps. Turn reproducible defects into regression tests; do not count coaching as independent success. No participants have been enrolled or trials performed by adding this checklist.

An independent implementation/conformance exercise is a separate next step: internal test coverage and a successful CLI demo do not establish adoption by another team. Licensing, governance and security-response decisions also need the project owners' approval; this guide does not grant new reuse rights.
