From a working demo to a production integration

Qualify the integration you will operate. A successful release qualifies its recorded tests and artifact set, not every DOT, API, environment or data store. The supported execution boundary remains Linux amd64 and existing single-host profiles. No new portable-model fields or managed multi-host runtime are needed to use those profiles.

Choose the evidence you need

Evidence Meaning

Definition validation

Structure, exact references, verified payloads and applicable bindings pass.

Strict interface profile

Declared Anchors and exposed ports have the required machine-readable coverage. This still does not establish live behavior or authorization.

Actual producer acceptance

The selected real tools, versions, configuration and interactions passed. Protocol fixtures and producer doubles remain labelled separately.

Operational acceptance

The operator has verified access controls, storage/retention, upgrade/recovery, monitoring and ownership-safe cleanup in the intended environment.

Use the release record for exact 0.4.0 identities. The manifest-pinned released catalogue retains its original tool versions. Current Next may update a product without changing the models: the post-release Loki definition selects 3.7.9 and chart 20.2.2. Do not attribute a new catalogue deployment to an older receipt or silently upgrade an existing data store.

Triage a catalogue gap

From the DOT-Design checkout root, run the existing report procedure in Verification and examples. Each strict result now carries its diagnostic code, definition hash and review category. Categories describe declarations and paths; they are not a new validator or an exemption from the strict profile.

  • Partial interface: inspect the reported Anchor or port. Complete a real supported operation and its service binding. Keep UI, native-protocol and provider-neutral boundaries explicit when they cannot be represented completely.

  • Missing exposed Contract: inspect the actual implementation and prefer its release-matched official raw specification. A source-derived subset must say which operations were verified and which remain outside it.

  • Client or broker: a consumed API or application message does not become the client’s or broker’s owned API. Verify real configuration and transport behavior; do not invent an HTTP endpoint or arbitrary application message schema.

  • Planning or fixture: require the actual producer and deployment before claiming producer readiness. Automated doubles remain useful test evidence.

For example, Loki’s HTTP subset can verify real JSON log ingestion and querying while the native gRPC port remains a strict-profile gap. Similarly, a successfully composed OIDC requirement does not create an APISIX-owned Keycloak Contract.

Record one production acceptance

Record the exact binary, catalogue, DOT/deployment IDs, payload/image/chart pins, reviewed lock, environment and operator. Use private state and inputs, reserve names/ports/namespaces, and reject collisions. Keep real credentials out of commands, documents and evidence; use the supported Secret/input mechanisms.

Verify the actual consumer reaches the intended producer. Include the normal application result, unauthorized/invalid requests, version identity, a bounded failure/recovery case and absence of test-owned leftovers. Preserve unrelated resources and externally owned gateways. A running Pod or matching protocol name is insufficient evidence.

Retain the original binary, source hashes, frozen kubeconfig and private resource receipts until cleanup is verified. The external harness persists the actual namespace creation response with owner-only permissions. Recovery checks its recorded name/UID against the current API object; replacement objects are rejected. A missing or partial response remains unconfirmed and requires operator review. Do not reconstruct ownership from a later matching name. Namespace removal alone also does not prove persistent-volume reclamation. The shared harness waits for PVs referencing that namespace to disappear and reports cleanup failure if storage remains or discovery is unavailable. It performs no forced PV deletion or provisioner-identity adoption. In particular, a restarted Minikube host-path provisioner can refuse its earlier volumes; retire confirmed test data through a separately reviewed operator action.

A post-release Helm fix removes the automatically injected rolloutToken chart value. Strict chart schemas must remain enabled; a CLI must not invent a chart option to request a restart. This source fix is separate from the immutable released v0.4.0 binary. A second fix makes path-based Docker start/stop honour --name; the restart acceptance checks the selected container actually stops and retains its identity and original log after restart. Explicit Docker container names retain their exact case, matching deployment and destruction; Compose project names retain Docker Compose’s normalization. Keep the original binary and recorded context when operating existing resources. Kubernetes/Helm path start/stop reject --name rather than silently targeting a product peer; use reviewed native workload lifecycle commands with an explicit namespace.

The Loki external harness now asserts its selected build version, an initially empty uniquely labelled stream, accepted JSON ingestion, the exact correlated log result and rejection of numeric timestamps on Helm and Compose. Its source-derived OpenAPI subset does not claim every LogQL query, metric query, gRPC method, OTLP signal or authorization policy. The shared external lifecycle harness owns deployment and cleanup; the HTTP assertion helper does neither. The Compose configuration points filesystem data at its named /loki volume. A separate owned-container recreation check requires a different container ID, the original volume and the original log without a replacement push. Unrelated network/volume changes are rejected. This is local retained-storage evidence, not a consistent backup, restore, migration or HA claim.

Remaining implementation boundaries

Work Current boundary Acceptance before extending it

External Protobuf import graphs

Embedded standard imports are supported. Arbitrary producer imports are not resolved by fetching mutable adjacent files.

Preserve a cryptographically closed root and dependency graph, official package and operation names, deterministic selection and byte limits. Compare a complete descriptor-set artifact with an explicitly pinned source bundle. Reject missing, conflicting, cyclic, ambiguous or path-escaping dependencies. A new format/profile requires a separately reviewed design; no new model fields are added here.

Complete Loki and OTLP interfaces

The Loki HTTP log subset is separate from imported native gRPC/OTLP schemas.

Use the selected release’s official graph and actual receiving implementation. Test real ingestion and retrieval/export, authentication and malformed input for each claimed signal. A successful HTTP push or broker fixture cannot qualify it.

Stateful recovery

Existing lifecycle controls and stateless rollback do not restore application data.

In an isolated owned deployment, write identifiable data, verify persistence across stop/start, create a native consistent backup, restore into a separate owned target and compare application results. Inject interruption and preserve the original data and unrelated peers. Record RPO/RTO and storage/version limits; do not treat restarting a container as backup/restore or infer schema rollback.

Distributed orchestration

Operator-owned external gateways support explicit connections; they are not managed multi-host networking or automatic infrastructure provisioning.

First demonstrate the actual consumer route and selected-producer attribution, denial/failure/recovery, credentials and independent resource ownership. Record the required infrastructure and failure model before proposing a new execution profile. Keep the present single-host boundary unchanged.

Until these criteria are met, retain the specific limitation. Do not make an unsupported path look successful through a placeholder Contract, automatic state adoption, a weaker timeout or a test double described as the producer.

Human trials and owner handoff

Three actual unfamiliar developers must still follow the complete onboarding protocol. Start from one verified binary/catalogue kit; retain first failures, assistance, timing, Contract selection, safe edit/cancel, composition/lock review, live results and cleanup. Automated terminal tests and maintainer rehearsals do not count as participants. Use the existing evaluation kit; no Java or Go is required for the first participant monitoring path.

The kit’s asset-inventory.json supplies source declarations and pending owner questions. The owner must record terms, permitted distribution, custodian, hosting/recovery responsibility and access policy for each relevant asset. Unlisted Gist URLs are anonymously readable and currently use a personal account; hashes verify bytes but do not grant rights or guarantee future availability. Do not change custody, publish participant records or infer approvals on the owner’s behalf. These decisions and consent/retention remain pending.
