4. Grow the system with Grafana

You now have a useful two-tool system. Add a dashboard without rewriting either tool. This lesson extends your existing graph: Node Exporter → your Prometheus → Grafana. It adds one DOT instance, one Wire and a browser-facing exposure.

Continue in the same Bash shell. First complete Lesson 3’s destroy step. The new graph gets another ownership UUID; it does not adopt the stopped graph’s resources or inherit its live state.

Goal: see the same labelled scrape through Grafana. You will learn: extending a graph, provisioning a datasource and supplying a password through a reference. The result is three DOTs and two Wires; the original scrape relationship stays intact.

Prepare the next real tool

Reuse Grafana’s exact catalogue release in a private exercise copy. Add a service-scoped declaration for its supported admin-password environment option:

(
set -euo pipefail
set -o noclobber
GRAFANA_JSON="$(dotx repository resolve Grafana@13.3.0 \
  --repository "$DOT_REPOSITORY")"
mkdir "$LAB/grafana"
jq '.runtimes[0].deployments[0].services[0].config.environment +=
  [{"name":"GF_SECURITY_ADMIN_PASSWORD",
    "required":true,"sensitive":true}]' \
  "$GRAFANA_JSON" > "$LAB/grafana/dot.json"
dotx validate "$LAB/grafana/dot.json" \
  --repository "$DOT_REPOSITORY" --profile reusable

cat > "$LAB/grafana-prometheus.yml" <<'YAML'
apiVersion: 1
datasources:
  - name: Prometheus
    uid: hero-prometheus
    type: prometheus
    access: proxy
    url: http://replaced-by-the-wire.invalid
    isDefault: true
YAML
cat > "$LAB/grafana-empty.yml" <<'YAML'
apiVersion: 1
datasources: []
YAML
chmod 0644 "$LAB/grafana-prometheus.yml" "$LAB/grafana-empty.yml"

dotx compose new --from "$LAB/composition.yaml" \
  --repository "$DOT_REPOSITORY" --name hero-dashboard \
  --output "$LAB/dashboard.yaml" --yes
)

Expected: the Grafana candidate validates and dashboard.yaml retains the earlier monitoring graph with a fresh UUID. The catalogue remains unchanged. The copied product already carries its official pinned OpenAPI declaration, required Prometheus Anchor, provided dashboard Anchor and service bindings. You extended its configuration surface, not its API identity.

The datasource file is an instance input. uid: hero-prometheus makes it easy to select and test. access: proxy makes Grafana’s backend query Prometheus over the composition network; the browser does not need to reach an internal container address. The Wire replaces the .invalid URL before deployment.

This catalogue release also requires an Elasticsearch provisioning file. The empty, valid grafana-empty.yml deliberately provisions no Elasticsearch datasource: that integration is outside this lab. Do not draw a fictitious Wire or claim that it has been tested.

Extend the existing graph

Open $LAB/dashboard.yaml. Before editing, it has two DOTs and one Wire. You will add one item to each of three existing lists. Keep the earlier items, Contract inputs and ownership UUID; do not paste another root dots: or wires: key. Each snippet below is a list item, beginning with - name, at the same indentation as the existing items. Keep the four leading spaces shown before each - name in the CLI-created draft.

Add Grafana under dots

Append this after the existing prometheus instance:

    - name: grafana
      source: ./grafana
      dotId: Grafana@13.3.0
      dotVersion: 13.3.0
      deployment: docker
      dependsOn: [prometheus]
      deploymentInputs:
        environment:
          - name: GF_SECURITY_ADMIN_PASSWORD
            secretRef: {store: environment, name: HERO_GRAFANA_PASSWORD}
        configFiles:
          - source: grafana-empty.yml
            target: /etc/grafana/provisioning/datasources/elasticsearch.yml

Add the second connection under wires

Append this after node-metrics-to-prometheus:

    - name: prometheus-to-grafana
      from: {instance: prometheus, anchorId: promql-query-api}
      to: {instance: grafana, anchorId: promql-query-api}
      materializer:
        type: CONFIG_FILE
        source: grafana-prometheus.yml
        valueFrom: ENDPOINT_URL
        target:
          instance: grafana
          service: grafana
          path: /etc/grafana/provisioning/datasources/prometheus.yml
          jsonPointer: /datasources/0/url

Add the browser endpoint under exposedAnchors

Append this after prometheus-query:

    - name: dashboard
      target: {instance: grafana, anchorId: monitoring-dashboard}

The new Wire connects a provided PromQL operation to Grafana’s required operation. Its materializer writes the selected Prometheus base URL into /datasources/0/url. The two Wires have different jobs: the first configures scraping; the second configures querying.

Here /datasources/0/url selects url in the first datasource entry. It replaces the .invalid placeholder URL you created in grafana-prometheus.yml with this graph’s Prometheus base URL.

secretRef names a host environment variable; it contains no password. The executor resolves it at apply time. Do not paste a sensitive value into the composition. Docker environment delivery is still visible to an authorized Docker administrator; it is not a vault or native Kubernetes Secret.

(
set -euo pipefail
dotx compose validate "$LAB/dashboard.yaml" \
  --repository "$DOT_REPOSITORY"
dotx compose lock "$LAB/dashboard.yaml" --repository "$DOT_REPOSITORY"
dotx compose topology "$LAB/dashboard.yaml" \
  --repository "$DOT_REPOSITORY" --locked
printf 'Extended graph verified: three DOTs, two Wires.\n'
printf 'Next: supply a lab password, then preview and apply.\n'
)

Expected: three DOTs, two Wires. Open $LAB/dashboard.lock.json and use Lesson 3’s lock-field checklist. Keep the local Prometheus and catalogue Node Exporter selections. The additional dots[] entry must have instance: "grafana", source: "./grafana", dotId: "Grafana@13.3.0", deploymentId: "docker" and a definition digest. The inputs[] now also pin grafana-prometheus.yml and grafana-empty.yml. Creating or inspecting the lock does not require the password; never paste a secret value into it.

Set a password and start the extended system

On the pinned CLI 0.4.0 route, stop before the live apply block below. The composition completion gate remains open. Read the launch and checks as a preview; do not switch binaries in an existing lab.

Use a new lab-only password. The prompt does not echo it or put it in shell history. Keep this environment and the same binary for the lifecycle:

if read -r -s -p 'Choose a lab-only Grafana admin password: ' \
  HERO_GRAFANA_PASSWORD &&
  test -n "$HERO_GRAFANA_PASSWORD"; then
  printf '\n'
  export HERO_GRAFANA_PASSWORD
else
  unset HERO_GRAFANA_PASSWORD
  printf '\nNo password set. Repeat this prompt before applying.\n' >&2
  false
fi

Ports 19041 and 13000 must be free. Use only the isolated development host and network described at the start. Keep the cleanup command below available before applying; use it after a failure as well. The next block previews both exposures first; a failed preview prevents its apply command from running. Runtime preflight, including the dry-run, needs the referenced password available.

printf '%s\n' \
  'Previewing, then starting Node Exporter, Prometheus and Grafana;' \
  'pinned images may need downloading...'
dotx compose apply "$LAB/dashboard.yaml" \
  --repository "$DOT_REPOSITORY" --locked --dry-run \
  --forward "prometheus-query=$TUTORIAL_PORT" \
  --forward "dashboard=$DASHBOARD_PORT" &&
dotx compose apply "$LAB/dashboard.yaml" \
  --repository "$DOT_REPOSITORY" --locked \
  --forward "prometheus-query=$TUTORIAL_PORT" \
  --forward "dashboard=$DASHBOARD_PORT"

Verify the whole chain

Grafana health is the first check. The datasource query is the second: it exercises the connection to Prometheus and the labelled scrape from Node Exporter. Complete both before calling the chain successful.

Wait for Grafana’s actual health/version response:

(
set -euo pipefail
set -o pipefail
dashboard_ready=false
started=$SECONDS
next_notice=$SECONDS
printf 'Checking Grafana 13.3.0 health on port %s...\n' \
  "$DASHBOARD_PORT"
for ((attempt=0; attempt<90; attempt++)); do
  if curl --fail --silent --max-time 3 \
    "http://127.0.0.1:$DASHBOARD_PORT/api/health" |
    jq -e '.database == "ok" and .version == "13.3.0"' >/dev/null; then
    dashboard_ready=true
    break
  fi
  if ((SECONDS >= next_notice)); then
    printf 'Waiting for Grafana: attempt %s/90, %ss elapsed\n' \
      "$((attempt + 1))" "$((SECONDS - started))"
    next_notice=$((SECONDS + 5))
  fi
  sleep 1
done
if ! $dashboard_ready; then
  printf '%s\n' \
    'Grafana health check timed out. Inspect compose status, then run' \
    'the Lesson 4 cleanup block before retrying.' >&2
  exit 1
fi
printf 'Ready: Grafana 13.3.0 at http://127.0.0.1:%s/\n' \
  "$DASHBOARD_PORT"
)

Expected: named waiting messages include elapsed time, followed by Ready: Grafana 13.3.0 and the browser URL. Its loop permits up to 90 attempts, with three-second HTTP timeouts and one-second pauses.

Open Grafana, sign in as admin with your chosen password, and open Explore. Choose the provisioned Prometheus datasource and run:

up{job="node-exporter",tutorial="zero-to-hero"}

Expect a sample with value 1. Grafana UI labels can vary by release; the backend check below provides a reproducible alternative. You have extended one running use case without putting a use-case-specific datasource or password into the shared product definitions.

Verify the same query without a browser

Make Grafana’s backend query the provisioned datasource. The temporary curl credentials file is private and removed when the check finishes, including a failed query. Neither the password nor its value enters YAML or the lock.

(
set -euo pipefail
set -o pipefail
# curl reads credentials from a private file, not command-line arguments.
credentials="$(mktemp "$LAB/grafana.curl.XXXXXXXX")"
trap 'rm -f -- "$credentials"' EXIT
(umask 077; jq -nr '
  "user = " + ("admin:" + env.HERO_GRAFANA_PASSWORD | tojson)
' > "$credentials")
dashboard_queried=false
started=$SECONDS
next_notice=$SECONDS
printf 'Querying the labelled scrape through Grafana...\n'
for ((attempt=0; attempt<90; attempt++)); do
  if curl --config "$credentials" --fail --silent --max-time 5 \
    --header 'Content-Type: application/json' \
    --data '{
      "from":"now-5m", "to":"now",
      "queries":[{
        "refId":"A",
        "expr":"up{job=\"node-exporter\",tutorial=\"zero-to-hero\"}",
        "instant":true,
        "datasource":{"type":"prometheus","uid":"hero-prometheus"}
      }]
    }' \
    "http://127.0.0.1:$DASHBOARD_PORT/api/ds/query" |
    jq -e '.results.A.status == 200 and
      any(.results.A.frames[]?.data.values[]?[]?; . == 1)' \
      >/dev/null; then
    dashboard_queried=true
    break
  fi
  if ((SECONDS >= next_notice)); then
    printf 'Waiting for the Grafana query: attempt %s/90, %ss\n' \
      "$((attempt + 1))" "$((SECONDS - started))"
    next_notice=$((SECONDS + 5))
  fi
  sleep 1
done
if ! $dashboard_queried; then
  printf '%s\n' \
    'Grafana query timed out. Check the password and datasource;' \
    'run the Lesson 4 cleanup block before retrying.' >&2
  exit 1
fi
printf 'Verified: Grafana queried the labelled scrape (value 1).\n'
)

Expected: Verified: Grafana queried the labelled scrape (value 1). The bounded loop allows 90 attempts with five-second HTTP timeouts and one-second pauses. The native request selects datasource UID hero-prometheus and runs an instant query. This verifies Grafana → Prometheus → Node Exporter; the diagram alone could not establish it.

Clean up the complete graph

dotx compose destroy "$LAB/dashboard.yaml" \
  --repository "$DOT_REPOSITORY" &&
unset HERO_GRAFANA_PASSWORD &&
{
  if test -f "$LAB/grafana.curl"; then
    rm -- "$LAB/grafana.curl"
  fi
} &&
printf 'Destroy succeeded: keep the workspace files for reference.\n'

Expected: all three owned instances stop. This is disposable storage; downloaded images remain cached. Keep your authored files as a learning reference, but retain the original cache and lock if cleanup did not finish. Do not remove unrelated resources or change a lock to adopt an existing instance. The final message and password removal happen only after destroy succeeds. Composition destroyed: and the final message do not independently prove resource absence, and neither does removing the password from this shell. The pinned 0.4.0 lacks the required native audit: keep the original binary, draft, lock and cache while cleanup is unverified. A missing lifecycle record alone does not close that gate. If it fails, retain the current environment and use the recovery steps before retrying.

Checkpoint

Finish when Grafana reports version 13.3.0, its datasource query returns the labelled sample with value 1, and cleanup has established absence of the complete graph’s owned resources. The pinned 0.4.0 route cannot satisfy that last condition using the native audit; do not mark the full lab complete. Either Explore or the documented backend query can verify that sample; the health response alone cannot.

If sign-in or the backend query fails, check that you used the lab password prompt, datasource UID hero-prometheus and the chosen dashboard port. A resumed running instance needs its original password. Use the recovery guide before retrying an interrupted run.

Explain it back: what stays reusable when you add a dashboard?

Prometheus keeps its product identity, Contract and Anchors. Grafana’s datasource, the selected Prometheus instance, the password reference and both Wires belong to this composition. The private Grafana copy adds a supported sensitive configuration declaration; it contains no password value. Live addresses and resolved credentials remain execution concerns.
