2. Create an interface-aware DOT

Now build the definition yourself. You will keep the real product identity Prometheus@3.15.1, use its official OpenAPI document and bind two named Integration Points to a real service port. This is a private learning copy, not a second catalogue entry or a renamed fork of Prometheus.

Continue in the same Bash shell from Lesson 1, with LAB and DOT_REPOSITORY set. No runtime is started in this lesson.

Goal: create $LAB/prometheus/dot.json with verified interfaces and two deployment choices. You will learn: Contract ownership, provided/required Anchors and service-scoped configuration. Keep the generated scaffold so you can review exactly what the enrichment changes.

Author the provided interfaces

Reuse the catalogue’s reviewed image digest and official Contract URL/hash. The CLI creates identifiers and the complete generated-model document:

(
set -euo pipefail
IMAGE="$(jq -r '.runtimes[].deployments[] |
  select(.id == "docker") | .manifest.image' "$PROMETHEUS_JSON")"
CONTRACT_URL="$(jq -r '.contracts[0].payload.url' "$PROMETHEUS_JSON")"
CONTRACT_SHA256="$(jq -r '.contracts[0].payload.sha256' "$PROMETHEUS_JSON")"

dotx new --from docker-image "$IMAGE" \
  --name Prometheus --version 3.15.1 --skill Metrics-Scraping \
  --service prometheus --port http:9090 \
  --contract-url "$CONTRACT_URL" --contract-sha256 "$CONTRACT_SHA256" \
  --contract-name HTTP --contract-standard OpenAPI --contract-format YAML \
  --operation 'build-information=#/paths/~1status~1buildinfo/get' \
  --operation 'promql-query-api=#/paths/~1query/get' --bind http \
  --output "$LAB/base/dot.json"

dotx validate "$LAB/base/dot.json" --repository "$DOT_REPOSITORY" --profile reusable
dotx inspect "$LAB/base/dot.json" --verbose
)

Expected: an owned interface is verified, the output is saved, and reusable validation succeeds. Open $LAB/base/dot.json in your editor.

What you see What it means here

id, name, version

One real tool release: Prometheus@3.15.1. This is not the CLI version.

skills

Metrics-Scraping is a capability reference, not an API operation.

contracts

A complete owned declaration. payload.url points to raw official bytes; sha256 pins them. Contract version 3.1.0 is the OpenAPI standard version.

anchors

build-information and promql-query-api provide selected operations from that Contract. Their selectors are JSON Pointers, separate from Contract IDs.

runtimes[].platform

The DOCKER engine: where this deployment runs.

deployments[].id and manifest

docker-image selects a DOCKER_IMAGE mechanism and exact image bytes.

services, ports, anchorBindings

Service prometheus materializes both Anchors on the named http port, 9090. The flag http:9090 supplies a name and number. Native authoring binds TCP listeners; the name http alone does not change that protocol label.

metadata

Definition audit timestamps. Live endpoints and lifecycle state are elsewhere.

For example, one generated Anchor looks like this:

{
  "id": "build-information",
  "name": "build-information",
  "role": "PROVIDES",
  "contract": {
    "id": "Prometheus@3.15.1::OpenAPI::HTTP",
    "selector": "#/paths/~1status~1buildinfo/get"
  }
}

~1 encodes / inside a JSON Pointer segment. It selects the operation from verified Contract bytes; a documentation hyperlink would not establish an API match. The image pin and document pin establish identity and integrity, not publisher authenticity by themselves: the catalogue’s provenance still matters.

Describe what Prometheus needs

An API provider can also be a consumer. Prometheus needs an exporter endpoint and a scrape configuration file. Its catalogue definition already documents that requirement and the real configuration path. Reuse those release-matched parts instead of inventing another interface. Also add its existing Compose deployment to see how one DOT supports more than one mechanism:

(
set -euo pipefail
set -o noclobber
mkdir "$LAB/prometheus"
jq --slurpfile product "$PROMETHEUS_JSON" '
  .anchors += [$product[0].anchors[] | select(.id == "scrape-target")]
  | .runtimes[0].deployments[0].services[0].ports[0].protocol = "HTTP"
  | .runtimes[0].deployments[0].services[0].config =
      ($product[0].runtimes[].deployments[] | select(.id == "docker")
       | .services[] | select(.id == "prometheus") | .config)
  | .runtimes[0].deployments +=
      [$product[0].runtimes[].deployments[] | select(.id == "docker-compose")]
' "$LAB/base/dot.json" > "$LAB/prometheus/dot.json"

dotx validate "$LAB/prometheus/dot.json" --repository "$DOT_REPOSITORY" --profile reusable
dotx inspect "$LAB/prometheus/dot.json" --verbose
diff -u "$LAB/base/dot.json" "$LAB/prometheus/dot.json" || test "$?" -eq 1
)

Read the diff. There are four intentional changes:

  1. scrape-target is a REQUIRES Anchor referencing Node Exporter’s exact Contract and originating DOT. Prometheus does not copy or own that Contract.

  2. The named service port is labelled HTTP, the actual application protocol. This matters when deriving an HTTP URL for another tool; the network transport still uses TCP. The initial native scaffold uses a TCP label.

  3. The image deployment declares /etc/prometheus/prometheus.yml as a required service configuration file. The composition will supply its contents.

  4. The same Docker Runtime gains the catalogue’s docker-compose deployment, including its verified URL payload and declared defaults.

The final $LAB/prometheus/dot.json has three Anchors and two deployments. It is complete for the interfaces taught here; it is not a copy of every capability Prometheus could have. DOCKER_IMAGE and DOCKER_COMPOSE are mechanisms on the same engine. A Kubernetes deployment would belong in another Runtime.

config is service-scoped. File defaults, when declared, use payload.url and sha256; actual instance overrides belong outside the reusable definition. Ordinary environment defaults are scalars, not encoded file documents. Each service in a multi-service deployment owns its own configuration and bindings.

Try the guided editor

This optional exercise changes declarations only. From the same shell:

dotx edit "$LAB/prometheus/dot.json" --interactive \
  --output "$LAB/prometheus.candidate.json" --repository "$DOT_REPOSITORY"

Choose Skills, then Add catalogue capability. Filter for Observability, select it, then choose Review and save. Review the summary and explicitly choose Write draft. Arrows browse, typing filters, Enter selects, Ctrl-U clears a text field and Ctrl-C cancels. ACCESSIBLE=1 selects line menus. The default publication choice is Cancel. In that fallback, /text filters, the displayed number selects, and q cancels.

Compare the candidate to the original. Unchanged Anchor IDs, manifests and configuration stay intact. The candidate is not automatically promoted; the remaining lessons deliberately use $LAB/prometheus/dot.json. Try another edit with an unused output path and cancel: no second candidate should appear.

The editor handles interfaces and Skills; it is not a manifest/configuration editor. The explicit JSON enrichment above is therefore a reviewed model edit, followed by validation, not an implied editor feature. For a genuinely new tool, use its own release, image and interfaces rather than relabelling these ones.

If a creation block says the destination exists, your earlier work is protected. Inspect that existing file and follow the resume/retry guidance; do not remove an edited definition just to make the block run again.

Checkpoint

Continue when reusable validation passes for $LAB/prometheus/dot.json and inspection shows three Anchors and both docker-image and docker-compose. The optional editor candidate is separate; the next lesson uses the enriched prometheus/dot.json you just validated.

Explain it back: where does the future scrape target belong?

The DOT declares the required interface and the supported configuration path. The composition selects a concrete exporter and supplies the scrape file. Its Wire materializes that exporter’s address into the execution copy of the file. Changing the monitoring use case does not require another product identity.
