Guided demo

This guided demo explains how a reusable DOT becomes part of a checked composition. Start with the official ecosystem demo, choose the shorter 10-15-minute standards route, or the five-minute read-only stages later on this page. These paths connect authoritative Contracts, Anchors, deployment choices and explicit wires; they prove different things.

The read-only core path takes about five minutes on an existing checkout. It is read-only apart from temporary files created and removed by the CLI. The live presenter route uses Docker and Kubernetes and performs deployment, protocol probes, inspection and cleanup.

Run the commands from the DOT-Design repository root. Keep evidence levels separate: a valid resolved composition proves deterministic resolution, a dry-run proves that the executor can render supported runtime actions, and only a live probe proves the observed protocol exchange.

Choose a path

For MARE use cases, start with the PoC composition walkthroughs: real PoC4 monitoring, PoC10 authenticated policy enforcement, then a labelled PoC6 CACAO/OpenC2 rehearsal using an NWDAF double. Its presenter tasks add a bounded post-verification inspection pause and automatic cleanup, with the same live assertions used by acceptance.

For a fully executable local presentation spanning Docker, Kubernetes, and OpenAPI/GraphQL/Protobuf/AsyncAPI wires, follow Docker/Kubernetes four-Contract composition. It includes the rehearsal, real probe outcomes, cleanup, and evidence boundaries.

Official ecosystem demo: reuse, compose, enforce, recover

Use this as the recommended presentation route. Budget 15-20 minutes of explanation for the first three chapters; provisioning, readiness and the intentional failed rollout add runtime-dependent waiting. The fourth chapter is an optional standards deep dive. For a short slot, show chapters 1 and 2. The shorter standards-focused route remains available below.

The story is: one authoritative definition → explicit composition → observed behaviour → controlled recovery. DOT-Domain and its generated Schemas define the portable models; dotx resolves and executes them. Docker/Kubernetes remain the workload engines. A wire connects declared Anchors; it does not magically translate protocols or implement missing producer functionality.

Prepare and qualify one exact checkout

Run from the DOT-Design checkout root on Linux amd64, with repository access, Git, Go, Task, Python 3, Bash, jq, curl, ss, Docker/Compose, kubectl and a Ready local Docker-runtime Minikube node. Select context minikube. This advanced developer rehearsal installs the pinned source CLI. The published candidate v0.3.0-rc.1 includes these model and authoring features, unlike the original v0.2.5. Nevertheless, do not replace the source-built binary after qualification, even with the same version: the exact checkout revisions and binary SHA-256 identify the frozen, qualified source set. A release candidate is not a final stable release. Put Go’s executable install directory (GOBIN, or $(go env GOPATH)/bin when unset) on PATH; the installation phase verifies that plain dotx resolves to the aligned version and records any PATH warning in its printed install log. The simpler Getting started path still needs neither Go, Task nor Kubernetes.

Commit reviewed source changes before using these qualification commands. Choose unused namespaces and ports; keep the same overrides for preflight, rehearsal and presentation:

export DOTX_PORTABILITY_NAMESPACE=dotx-demo-portability
export DOTX_PORTABILITY_KUBERNETES_PORT=19083
export DOTX_POC10_NAMESPACE=dotx-demo-secure-api
export DOTX_POC10_FORWARD_PORT=19010
export DOTX_UPGRADE_NAMESPACE=dotx-demo-upgrade
export DOTX_UPGRADE_PORT=19081
task testing:demo

task testing:demo is the complete off-stage readiness command. Sequentially, it installs and verifies the aligned source CLI, runs the existing demo guards and locked validation/rendering, prepares all image caches with preflight, qualifies all seven live paths twice plus the four official presenter chapters, and exports sanitized fallback evidence from that exact successful receipt. It stops at the first failure; an older successful receipt is never substituted. Every lane is included regardless of a focused DEMO selector; namespace and port overrides still apply. Allow substantial runtime for builds, rollouts and cleanup; this is not a command to start during the talk. It needs the tools and already Ready Minikube listed above; it does not install system prerequisites. Successful qualification cleans up its test-owned workloads rather than leaving the presentation running. Start the chapter-specific presenter commands below when ready to show them. Keep sources and dotx unchanged throughout the run. The console explains five numbered phases and each live lane’s purpose, reports elapsed time and outcome, and finishes with a results table, exact evidence and fallback paths, and the next presenter commands. Detailed tool output stays in per-step logs rather than flooding the terminal. The umbrella’s own report and table live under DOT-Testing/e2e/target/demo/run-*/; preparation and live qualification retain their separate evidence scopes below. A failed or interrupted phase stops the run and names its logs; it never prints demo-ready success or exports a fallback from an older run.

After qualification, use dotx version --verbose and the exact root summary.json printed by this run to show the three checkout SHAs and binary SHA-256. Expect Modified worktree: false. Do not replace this identity evidence with the version label alone, an older receipt, or a newer unrehearsed checkout. Changes after qualification require a fresh rehearsal and fallback export.

The granular commands remain available for investigation:

prepare explicitly pulls only selected digest-pinned official images, builds and tests the standards fixtures from this checkout, and imports their provider image. It may start disposable image-test containers, but never applies a composition or provisions credentials. Fixture preparation shares the live harness’s concurrency guard and label-scoped failure cleanup. Image caches and build cache intentionally persist. Registry access is needed; preparation does not promise offline operation. The command ends with read-only preflight. Use DEMO=portability, upgrade, secure-api, monitoring or four-contracts with either preparation or preflight for a focused lane; the default is all five.

preflight does not pull, build, deploy, adopt or delete resources. It checks the installed CLI provenance, local Contracts/locks, Ready Minikube, selected image caches and relevant namespace/port/runtime conflicts. It reserves nothing. The Compose comparison also needs the descriptor-declared port 18919 free.

rehearse runs the quickstart, monitoring, portability, secure API, upgrade/rollback, OAuth gateway and four-Contract paths twice each, followed by injected-failure and signal cleanup controls. It preserves every existing live assertion rather than replacing tests with a summary. All three checkouts must be clean; before/after revisions, tracked/untracked fingerprints and the binary SHA-256 must remain identical. Do not edit sources or reinstall dotx during it. This is qualification before the talk, not a command to start on stage.

qualify runs that same complete live rehearsal, then drives all four official chapters through a real terminal: wait for the verified inspection pause, inspect native status and topology, press Enter, and verify cleanup. It reuses the existing live harnesses and terminal driver rather than another deployment implementation. Application-result expectations are shared by both paths. Interrupted, timed-out and rejected-evidence steps remain visible as failures, even when the child command itself exited zero. The existing standalone rehearse Task remains useful when only noninteractive acceptance is wanted.

For the optional four-Contract chapter, use the prepared fixture path on stage:

export DOTX_DEMO_PREPARED=1

Preparation records source fingerprints, the installed binary hash, both Docker fixture image IDs and the imported Minikube provider image ID. qualify enables this mode automatically. With this variable set, the four-Contract live/presenter harness verifies that receipt before deploying and does not build, pull, import images or start Minikube. Missing preparation or changed sources/binary/images fail closed: re-run explicit preparation off stage and qualify again. Official digest-pinned images and probe-runner caches must still be available; this is not an air-gapped operation guarantee or a promise against registry outages. Do not retag images or switch Docker/Minikube contexts during the talk. Without this opt-in, the existing source-building live test path remains available; builds now have bounded five-minute timeouts.

The printed summary.json and adjacent results.txt consolidate step exits, logs and hash-linked child receipts/results. Receipt-backed live lanes require successful assertions, exact CLI identity and cleanup=PASSED; prerequisite, cleanup-control and log-only quickstart evidence stay separately labelled. Preparation has its own report under DOT-Testing/e2e/target/preparation/ and explicitly claims no live API acceptance. Qualification reports live under DOT-Testing/e2e/target/rehearsal/. A missing/failed receipt or source change fails the complete rehearsal. These local evidence directories are not published as though they were current online service health.

Close with evidence, not a blanket readiness claim

At every pause, the Mermaid graph is the locked composition. The new runtime table is a timestamped observation; a running container or available controller is not API acceptance. Historical probe records keep their own timestamps and age. The final application tables come from the separately completed live assertions. Use the printed cache/Kubernetes context for further inspection. Never substitute a fresh cache when recovering an interrupted run. Enter, Ctrl-C, EOF and timeout take the ownership-safe cleanup path; never delete unrelated resources or force namespace finalizers. Require the cleanup receipt, not just an empty terminal.

Keep matching rehearsal reports as a clearly labelled fallback. The umbrella task testing:demo automatically exports the sanitized audience summary and prints its path. When using the granular testing:demo:qualify task instead, export it manually using the exact printed receipt path:

task testing:demo:fallback RECEIPT=/absolute/path/to/summary.json

The exporter requires complete, clean-source live and presenter qualification and checks linked artifact hashes. It writes only fallback/summary.json and fallback/README.md beside that receipt: fixed step outcomes, source revisions and binary/receipt hashes. It does not copy logs, arbitrary API fields, host paths, runtime state, tokens or kubeconfig. Keep the parent run directory private. The exported result is historical rehearsal evidence, not live service health or an independent adopter/producer certification. Do not replay it as a claimed live result. For the catalogue-wide appendix, run task testing:contracts:readiness and consult the verification boundaries. Interface declarations, source-derived Contracts, runtime-only brokers, validation-only fixtures, stubs and producer doubles do not become production-certified through this demo. DOT-Registry and partner/SFC acceptance remain separate integration work.

The existing Kubernetes and Helm runtime E2E workflow accepts the optional full_demo_readiness=true manual input to run the same task testing:demo entry point. Ordinary pushes retain their focused runtime matrix; the long full-demo qualification is explicit. Uploaded reports are redacted evidence, not automatically a public live-service dashboard.

10-15-minute live presenter route

Use this route for an audience new to DOTs. The detailed stages below remain the reference walkthrough; this section is the talk track, not another harness. For a ten-minute slot, shorten the wire inspection and show the MARE graph as the closing example rather than starting a second deployment.

The three messages to leave with the audience:

  • Reuse a product definition; put PoC-specific configuration in the composition.

  • Keep existing interface standards authoritative; wires are not protocol translators.

  • Distinguish a compatible resolved composition from a verified live exchange and production acceptance.

For technical Q&A, add the five-minute developer extension: inspect a real product’s deployment choices and official Contract provenance, demonstrate rejection of an invalid wire, and show where a PoC contribution belongs.

Minutes 0-2: the problem and the six concepts

Say: "We want to describe a component once and reuse it across deployments and MARE use cases. DOT-Design connects existing interface standards to explicit deployment and composition choices; it does not replace those standards."

Concept Audience meaning In this demonstration

DOT

Reusable software component description

Provider, consumer and Mosquitto use canonical catalogue definitions.

Contract

Authoritative description of an interface

OpenAPI, GraphQL SDL, Protobuf and AsyncAPI describe different interactions.

Anchor

Named provided or required interaction

The provider and consumer select the REST alerts operation from its Contract.

Wire

Connection between compatible Anchors

rest-alerts connects the provider’s Anchor to the consumer’s Anchor.

Deployment

How a DOT runs on a selected platform

Provider and broker run on Kubernetes; consumer runs on Docker.

Composition

Participants, connections and deployment-instance inputs

One locked graph selects those DOTs, deployments, wires and configuration.

Point out the ownership: DOT-Repository stores reusable DOT bundles and compositions; dotx in DOT-CLI validates, resolves and executes them; DOT-Domain defines the shared model. DOT-Design brings together documentation and executable acceptance harnesses. The synthetic demo graph stays in DOT-Testing; it is not a new production product.

Show: three DOTs and four logical wires. Match the diagram’s N and W identifiers to the aligned DOT and connection tables. CONTRACT names the interface standard; the separate PROTOCOL column names the transport protocol. Explain provider versus consumer and the selected runtime, rather than reading UUIDs aloud. Say: "The OpenAPI Contract owns GET /alerts. The Anchors select that operation; the wire names the two participants. The materializer puts the resolved operation URL into the consumer’s declared OPENAPI_YAML_URL environment variable. We are not copying the API definition into the wire."

Expected observation: OpenAPI, the selected operation, provider/consumer Anchor references, COMPATIBLE and the environment-variable materializer. For an applied composition, run the following from the same private cache and Kubernetes configuration printed by its harness (do not use another run’s state):

Explain the layers separately: APPLIED is a recorded lifecycle phase; RUNNING describes a process, container or VM; CONTROLLERS_AVAILABLE describes selected Kubernetes controller status, not rollout or API acceptance. The consumer now executes the REST exchange and derives a synthetic review decision; explicit probes exercise GraphQL, gRPC and MQTT from its network namespace. The MQTT probe subscribes and publishes to prove broker delivery, not a provider application’s business-event publication. This verifies interoperability mechanics across runtimes, not a production application or the whole MARE stack.

Audience FAQ

Why not just use Docker Compose, Kubernetes or Helm?

Those tools remain the native deployment mechanisms. DOT adds a reusable component description, authoritative interface references, named interactions, explicit cross-component wiring and a checked resolved composition. dotx delegates supported deployment actions rather than replacing those platforms. If an existing Compose file is all a use case needs, DOT’s additional value is the shared catalogue and interoperability description, not a different container scheduler.

What is reused, and what changes between PoCs?

The product’s canonical dot.json, Contracts and Anchor identities are reused. A composition selects participants and deployments and supplies use-case-specific configuration: routes, policies, scrape targets and credential references. There is no need to create another Keycloak DOT for every PoC. Runtime platform means where it runs; deployment mechanism means how it is deployed.

Does connecting two Anchors make incompatible APIs work together?

No. Wires connect declared compatible interactions; they do not translate OpenAPI, GraphQL, gRPC or MQTT automatically. An application-specific adapter, if required, must be implemented and described explicitly. The four-Contract demo verifies four separate standards-native exchanges, not one message automatically converted through four protocols.

Is a Contract the same as a protocol? Are all Contracts official?

No. OpenAPI is an interface-description standard; HTTP is a protocol used by the selected operation. Protobuf describes messages/services used by the gRPC profile; AsyncAPI describes messaging interactions and transport bindings. The topology table separates CONTRACT from PROTOCOL for that reason. Use vendor/project-official documents when available. Source-derived Contracts and test-fixture Contracts must be labelled, not advertised as official. An explicit protocol interface is not an invented official Contract; the topology labels that case explicit interface. A - on a transport-only T link does not create another Contract-backed Anchor wire.

Does validation mean a DOT is production-ready?

No. Base validation checks definitions and declared references; stricter interface checks assess declaration completeness. A locked compatible resolved composition checks the selected graph. A successful deployment establishes a runtime state. A live probe verifies a particular observed exchange. None alone proves full business functionality, resilience, security hardening, scale or acceptance of an unmodified PoC producer. Read the declared scope with each result.

What does the lock file guarantee?

It pins the composition’s portable definition inputs and resolved composition so that unreviewed definition changes are detected. It does not freeze runtime health, network addresses, credentials or upstream service behavior. Contract payload digests verify the referenced bytes; a downloadable URL is not itself evidence that the live implementation conforms to the whole Contract.

Where do credentials and configuration belong?

DOTs declare supported service configuration. Compositions provide deployment inputs and secret references; secret values and concrete runtime state are not part of a reusable public interface description. The PoC10 rehearsal uses native Kubernetes Secret references. Do not display Secret contents, tokens, raw deployment state or private diagnostic logs during the talk. The four-Contract fixture uses plaintext/anonymous demo settings and is not an example of production security hardening.

What did this presentation actually demonstrate?

The official route verifies one Prometheus DOT on two runtimes, a source-adapted secure API with policy denial/restoration and unchanged stored RDF, and native stateless OPA upgrade/recovery. The optional standards chapter uses test-only provider/consumer components and real Mosquitto to verify four exchanges from the consumer’s network namespace. The shorter standards-focused route shows the PoC10 graph only unless its separate live task is run; a topology alone never accepts it. Producer doubles, stubs, validation-only fixtures and source adaptations remain labelled. DOT-Registry REST API, complete producer/PoC acceptance and joint SFC/partner acceptance are not claimed by these demonstrations.

How can an attendee try this afterwards?

Start with the real Prometheus quickstart, which needs neither a Java/Go development toolchain nor Kubernetes when using the supported released binary. Then explore reusable compositions and the authoring guide. The new topology and presenter features require the installed development checkout described above; do not assume an older release contains them.

Stage 1: validate the authoritative catalogue

dotx validate DOT-Repository

This recursively discovers every dot.json; there is no separate inventory. The command validates schema shape, identities, Skills, Contract payload integrity, selectors, service ports, Anchor bindings, repository placement, and catalogue-wide uniqueness. Contract-backed external and internal bundles also receive the strict reusable profile.

What this proves

The checked-out catalogue is internally consistent and every declared reference resolves. It does not deploy a workload or claim that a third-party service is reachable.

Follow one AsyncAPI wire

Inspect the Kafka wire to see how standard-derived facts and deployment facts remain separate:

dotx compose inspect \
  DOT-Testing/composition/contract-standards/scenario.yaml --locked --json |
  jq '.wires[] | select(.name == "asyncapi-kafka") |
      {name, compatibility, contractStandard, contractFormat,
       providerInteraction, consumerInteraction, channelAddress,
       connectionEndpoint, materializers, probe}'

The AsyncAPI Contract supplies the complementary send/receive operations, channel, message schema, Kafka binding, and correlation field. The composition selects the broker instance and materializes its resolved address and topic for the consumer. A resolved composition still does not claim that a message was delivered.

Stage 4: render a lifecycle without mutating it

The APISIX, Keycloak, and OAuth-client scenario demonstrates dependency order, configuration materialization, native Kubernetes Secret references, rollout readiness, and an exposed Anchor:

dotx compose lock \
  DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml --check

dotx compose apply \
  DOT-Repository/Compositions/keycloak-apisix-oauth/composition.yaml \
  --locked \
  --namespace dot-guided-demo \
  --dry-run \
  --forward protected-metadata-through-gateway=19080

The rendering ends with:

Dry run complete; composition state was not written.

The command may create bounded temporary rendering files and removes them when it exits. It does not create Kubernetes resources, start a port forward, or write composition state. The rendered order is Keycloak, APISIX, then the OAuth client, matching the declared readiness dependencies.

What this proves

The reference executor accepts the locked inputs and can derive the exact platform-native actions. It does not prove rollout success, credentials, or HTTP behavior; those require the live acceptance layer.

Optional: run the live Contract probes

This path builds images, starts disposable Docker workloads, and downloads pinned images when absent. Use the presenter path when time, network, or host capacity is uncertain.

 
task testing:compose:contract-probes:live

The harness builds a standards-native GraphQL/gRPC producer and an independent consumer, then deploys the canonical Mosquitto, NATS, Kafka, and RabbitMQ DOTs. It proves GraphQL query, mutation verification/cleanup, and GraphQL-over-SSE; all four finite Proto3 NO_SIDE_EFFECTS gRPC shapes through reflection; and correlated MQTT, NATS, Kafka, and AMQP 0-9-1 delivery. It records redacted evidence and destroys composition-owned resources on success, failure, or interruption.

Five-minute presenter script

  1. Show the Contract-to-Anchor-to-wire diagram and explain the four ownership boundaries.

  2. Run dotx validate DOT-Repository to establish that the catalogue is the checked source of truth.

  3. Inspect Keycloak to demonstrate one reusable product identity with several deployment choices.

  4. Print the 21-wire resolved composition summary and highlight the four Contract standards and eight interaction forms.

  5. Inspect the Kafka wire to distinguish Contract semantics from its resolved broker endpoint.

  6. Render the APISIX/Keycloak/OAuth lifecycle with --dry-run.

  7. Finish on the evidence table and state the supported boundary explicitly.

Keep the published release notes and verification matrix open as fallback evidence if a local network or runtime is unavailable.

Supported boundary

The stable profile supports Linux amd64 and private single-host composition state. Multi-host orchestration, automatic cross-platform gateway provisioning, general stateful-data migration, AMQPS, AMQP 1.0, native arm64 and non-Linux executables, the DOT-Registry REST API, and joint SFC or partner acceptance are separate activities. Unsupported combinations fail closed rather than being silently approximated.

All eleven MARE PoCs have resolution or source-adapted evidence. That evidence is not presented as acceptance of every unmodified partner workload. Continue with Architecture for system boundaries or DOT Anchors and Composition for authoring and lifecycle details.
