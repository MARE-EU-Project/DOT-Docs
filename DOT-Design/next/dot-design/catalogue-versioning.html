Catalogue products and releases

Select a tool release explicitly. A product folder groups its supported releases; a release folder contains one complete DOT definition and its quickstart.

DOTs/external/Prometheus-DOT/
  README.md
  3.15.1/
    dot.json
    README.md

The product README lists available releases. Each release’s dot.json contains all its supported deployment mechanisms; there is no parent dot.json, versions/ wrapper or mutable latest copy. The initial migration moves the existing 67 definitions without qualifying any additional historical releases.

Find and select a release

From the matching DOT-Repository checkout root, with its matching CLI installed:

dotx repository list --repository .
dotx repository inspect Prometheus@3.15.1 --repository .
dotx repository resolve Prometheus@3.15.1 --repository .

Expected: the exact selected definition, its deployments and its dot.json path. These commands create no workloads; no runtime cleanup is needed. Current-source menus group product releases in descending SemVer order. Ordering is navigation, not a support recommendation or automatic selection.

Compositions keep logical coordinates, independent of folder spelling:

source: repository://Prometheus@3.15.1
dotId: Prometheus@3.15.1
dotVersion: 3.15.1
deployment: docker-compose

A missing release or a mismatched coordinate fails. Choose a deployment from that exact release. Contract IDs retain the provider’s release, so a consumer for one release is not automatically compatible with another. Fixed Kubernetes workload names or WASI HTTP ports may also prevent two releases from sharing an execution context; the existing isolation checks still apply.

Keep the version meanings separate

Identity Meaning

DOT version

Actual upstream tool/component release, used in folder and DOT ID.

Definition revision

Git commit and definition digest; corrections do not invent a new tool release.

Contract version

The specification standard version, such as OpenAPI 3.1.0; GraphQL omits it.

CLI/format compatibility

The matching binary, generated model package and catalogue snapshot.

Add or update a release

Add an exact release leaf in the existing product folder. Include every supported deployment for that release, release-matched official Contracts where available, pinned artifact bytes and a readiness/cleanup README. Validate the catalogue and rehearse affected deployments before claiming support. Keep composition-specific inputs outside product definitions. Generated product navigation is maintained by the existing Contract-inventory documentation task.

Updating a composition’s release selection requires explicit review and a new reviewed lock. The folder-only migration preserves existing logical references and locks; do not regenerate unchanged locks. Operate existing state using its original binary and context before changing checkouts; no adoption is implied.

Released walkthroughs use their manifest-pinned catalogue, which may retain the historical single-root layout. Generic readers retain that support. Current catalogue publication requires exact release leaves. Stable tags and their docs remain unchanged. See Compatibility and migration and Production-readiness limits.
