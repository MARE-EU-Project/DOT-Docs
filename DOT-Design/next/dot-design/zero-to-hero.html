DOT-Design from Zero to Hero

Understand the models, then build a monitoring system you can explain, change and run yourself. Begin with DOT-Design 101: learn the core building blocks and how the ecosystem uses them. Then create a reusable tool definition, connect a metrics producer and add Grafana. The practical lessons turn those concepts into files and verified API responses.

Your first visible result is small: Prometheus answers its real API. Next, your own DOT passes validation. Then a two-tool query returns 1, and Grafana returns that same sample through a third tool. Each result has a separate check, so you know what worked before adding the next piece.

Start with DOT-Design 101

DOT-Domain defines the portable models used throughout the project. A DOT describes one reusable tool release; a Composition selects tool instances and connects their Anchors through Wires. The CLI uses their generated schemas and input types to work with those declarations.

Read DOT-Design 101 first. It explains Skills, Contracts, URL/hash Payloads, Runtime and deployment choices, service configuration, connections, locks, probes and lifecycle safety in simple terms. It also maps the roles of Domain, CLI, Repository, Docs and Testing. No installation is needed.

Build on those concepts

Figure 1. The system you will build: actual HTTP request direction

Mermaid source

Grafana sends queries to Prometheus; Prometheus pulls metrics from Node Exporter. The CLI’s topology uses a different, logical direction: a Wire points from the Anchor that provides an interface to the Anchor that requires it. Both views describe the same system. A Wire does not determine which tool sends a request.

The reusable DOT says what a tool can do and how it runs. Your composition says which instances work together for this particular monitoring use case. Scrape targets, datasource configuration and credentials belong to that use case.

Choose your pace. Read DOT-Design 101, then finish Lesson 1 for a first API response. Continue through Lesson 3 for your first authored integration, then Lesson 4 for the complete monitoring chain. Lesson 5 is an optional operator path with additional setup. Every live lesson ends with cleanup; stop there whenever you need a break. Downloads and startup depend on your machine and cache; take the time needed to review each result.

If you want to watch before authoring, use the guided demo instead. This tutorial is the hands-on route: you create and inspect the files rather than run an unattended installer.

Before you start

Use Linux amd64, Bash, Git, GitHub CLI, curl, jq, SHA-256 utilities and Docker with Compose. You need authorized access to the MARE repositories and release assets. The main four lessons need no Java, Go, Task or Kubernetes.

Use the released CLI v0.4.0 with its manifest-pinned catalogue 2b17ee681fbe8eed6822834484f87149b32fc772 throughout. Lesson 1 includes installation. Do not switch to floating main halfway through: a version string alone does not identify later source changes. The catalogue may use the older single-root layout; identity-based lookups make these commands work without guessing paths.

Use an isolated development machine. The lab exposes disposable HTTP services; Docker publication can listen beyond localhost. Restrict access with your host firewall and use a lab-only Grafana password. This is not a hardened monitoring deployment. Node Exporter observes its container, not your physical host.

Validation establishes declared constraints and resolved interfaces. Only the API checks establish the particular live behavior exercised here. Neither result certifies every catalogue definition or every API of the selected tools.

Follow a repeatable rhythm

  1. Read the goal, then run one complete Bash block at a time. Copy commands without adding a shell-prompt character. Keep one terminal and the matching CLI/catalogue throughout; variables carry your workspace into later lessons.

  2. Inspect your work. Open the named file when a lesson asks for an edit. Keep YAML indentation exactly as shown. The longer shell blocks perform checked setup and verification; you do not need to memorize them.

  3. Check the result. Validation checks declarations; a dry-run previews deployment. Continue to live execution only after those steps succeed.

  4. Clean up before moving on. Use the lesson’s original draft, lock, binary and cache. If a step fails, stop and use the resume and recovery guide.

Know where your work lives

Lesson 1 prints a private workspace path, referred to as $LAB throughout. The catalogue is a separate, pinned checkout; exercises do not edit it.

Inside your workspace Purpose

session.bash

Your paths, ports and original CLI identity for resuming. It stores no password.

base/dot.json, then prometheus/dot.json

The generated scaffold and your enriched reusable tool definition from Lesson 2.

composition.yaml, prometheus.yml

Your two-tool graph and its scrape configuration from Lesson 3.

dashboard.yaml, grafana/, grafana-*.yml

Your extended graph, private Grafana definition and provisioning inputs from Lesson 4.

Adjacent *.lock.json files

Reviewed exact inputs created explicitly for each graph. Keep them for recovery.
