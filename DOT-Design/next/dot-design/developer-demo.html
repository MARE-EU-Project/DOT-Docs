Developer demo: reuse, inspect and extend

Use this optional five-minute extension after the 10-15-minute presenter route, or during technical Q&A. It adds no new live deployment. Run from the DOT-Design checkout root with its installed dotx, initialized catalogue, Bash and jq.

The developer takeaway is: reuse the product definition, describe the real interface, configure a composition, then prove the intended exchange.

1. One real product, several deployment choices

Ask the audience: "If two PoCs use Keycloak with different realms and deployment platforms, which parts should they share?"

dotx validate DOT-Repository/DOTs/external/Keycloak-DOT \
  --schema DOT-Repository/Schema/schema.json --profile reusable --offline

dotx inspect DOT-Repository/DOTs/external/Keycloak-DOT --json |
  jq -e '{name, version,
          deployments: [.deployments[] |
            {id, platformEngine, type, supported}],
          anchor: (.anchors[] | select(.name == "admin-realm-read") |
            {name, role, contract})} |
         select(([.deployments[].platformEngine] | unique) ==
           ["DOCKER", "KUBERNETES"])'

sed -n '1,12p' \
  DOT-Repository/DOTs/external/Keycloak-DOT/contracts/keycloak-admin-rest.yaml

Show: one Keycloak-DOT identity with Docker image, Docker Compose and Kubernetes/Helm deployment choices. A PoC-specific image is a named deployment variant, not a new product identity. The same selected admin-realm-read Anchor refers to the Admin REST Contract and its GET selector. The adjacent Contract metadata identifies the official release archive, extracted payload, revision and SHA-256; no API definition is copied into the Anchor.

This existing bundle uses ID-only root references resolved from its local contracts/ assets. Those are migration-compatible catalogue references, not permission to publish an unresolved UUID. New complete Contract declarations use the model’s structured payload.url pointing directly to a raw Contract document, plus its SHA-256; bundle-local verified assets remain supported. The archive URL shown here is provenance, not a raw-document payload URL. Prefer official documents and label derived ones.

Explain the boundary: an inspector reporting a supported deployment is not live acceptance of every deployment variant. The PoC10 rehearsal selects pinned source-adapted bundles, including keycloak-oidc-provider; do not equate its DOT identity with this inspected Keycloak-DOT or claim that the rehearsal certifies all variants. Compare each plan’s dotId, dotVersion and deploymentId when explaining provenance.

2. Show the guardrail, not just the happy path

task testing:demo:developer-tour

The task repeats the short inspection, validates the existing two-DOT PoC7 planning graph, then attempts its existing deliberately rejected wire. Expect:

EXPECTED REJECTION (exit=1): scoring-api-to-collector mixes Contract-backed and contractless Anchors.
The valid two-DOT graph has zero wires; no runtime was deployed by either validation command.

The task itself exits zero only when the positive graph resolves and the negative graph returns that specific compatibility diagnostic. Missing credentials, a broken checkout, a missing CLI or an unrelated validation error are not counted as a successful negative test.

Say: "Putting two boxes on a diagram is not an implemented integration. We cannot make an undeclared collector interface compatible by drawing a wire." At the pinned source boundary, the collector prints flow data rather than calling the scorer. This control demonstrates interface admission, not a live trust-scoring result or a runtime security test.

The first current rejection is Contract-backed/contractless incompatibility; it does not prove that a later undeclared-configuration check ran. After implementing a real consumer, declare its supported endpoint configuration, Anchor and binding, then validate the resulting wire and test the actual call.

3. What a PoC developer changes, and what stays shared

Concern Owning artifact Developer action

Product capability and interfaces

The existing DOT bundle, root Skills/Contracts, Anchors and service bindings

Reuse it. Extend the shared definition only when the software genuinely supports an additional capability or interface.

API or messaging semantics

Official Contract, or an explicitly labelled source-derived Contract

Select an existing operation. Do not redefine request/response schemas or invent a consumer implementation in a wire.

Deployment choice

A selected runtime/deployment already declared by the DOT

Choose a supported deployment ID. Add a reusable variant to the product root if a new mechanism is genuinely needed; test that variant.

Realm, route, policy, scrape target or configuration file

Composition inputs and endpoint materializers

Configure the use case without copying or hard-coding the product definition.

Credentials and concrete runtime state

Secret references and the deployment instance

Keep secret values outside reusable public descriptors and presentation output.

Reproducibility and proof

Reviewed composition lock and executable acceptance harness

Inspect the plan, review changed lock inputs, run dry-run checks, then verify the real workload and its cleanup. Commit definitions, not local runtime state.

The practical contribution sequence is:

  1. Find the product under DOT-Repository/DOTs/external/ or DOTs/internal/; check its README, source revision and declared gaps.

  2. Use official interface documents where available. For MARE-owned code, export or derive the Contract from the implementation and review its limits.

  3. Declare the provided/required Anchor and the selected deployment’s service binding. Ensure the application really reads the declared configuration.

  4. Add or update a reusable graph under DOT-Repository/Compositions/, with its README, non-secret inputs and reviewed lock. Put synthetic fixtures and live test drivers under DOT-Testing, not beside a new duplicate product.

  5. Run dotx validate DOT-Repository, inspect the locked plan and deployment dry-run, then add a far-end behavioral assertion and success/failure cleanup.

Skill is an optional high-level capability classification; it is not an API operation or a command executor. Anchors and authoritative Contracts describe the concrete interoperability boundary.

Choose one row in response to a technical question rather than reading the entire test matrix aloud. The examples demonstrate extension points and tested profiles, not automatic protocol conversion, arbitrary networking, complete PoC production readiness, a DOT-Registry REST API or joint SFC acceptance.
