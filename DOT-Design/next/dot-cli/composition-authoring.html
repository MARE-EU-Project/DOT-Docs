Create a composition from a reviewed example

A DOT describes one component. A Composition chooses concrete deployments of several DOTs and connects their Anchors through Wires. Start from a catalogue example whose README describes your intended use case and its acceptance limits. The current source-built CLI provides dotx compose new; the original released v0.2.5 binary does not. Use the matching source CLI and catalogue.

Choose, preview and create

From your pinned DOT-Repository checkout, warm its verified Contract cache once:

dotx validate .
dotx compose new

In a terminal, choose a numbered local template, enter a name and an unused YAML path in an existing directory, then confirm the exact deployment preview. Nested template paths remain distinguishable. Entering n, an empty confirmation, or Ctrl-D does not publish a file. Noninteractive execution requires all choices and --yes, so a CI job cannot hang waiting for input.

For a repeatable exercise using the existing Node Exporter/Prometheus graph:

dotx compose new \
  --from Compositions/node-exporter-prometheus-monitoring/composition.yaml \
  --name my-monitoring --output my-monitoring.yaml --offline --yes
dotx compose lock my-monitoring.yaml --offline
dotx compose inspect my-monitoring.yaml --offline --locked
dotx compose topology my-monitoring.yaml --locked

Expected: a preview of two DOTs and one wire, a fresh ownership UUID, and a new YAML file with the same exact tool releases, deployment choices, Contract and Anchor IDs. The reviewed template and its lock are unchanged. The new lock is created only by your explicit lock command; review it before committing. The Composition graph version is retained; it is not another tool release.

The command verifies its input byte snapshot against the template’s adjacent lock, applies changes to the Java-generated Composition model, preserves ordinary YAML shape/comments, then checks the rendered values exactly and validates the candidate with the same generated schema and planner. YAML merge keys are expanded by the YAML parser where necessary: inherited IDs, names and file sources must receive the intended new values too. Authoring uses a fresh model of the verified input bytes, separate from inferred execution-plan services and probes. It does not infer compatibility, invent wires, copy product definitions, download templates from Git, change secret values or start a runtime. Offline creation requires a warm verified Contract cache. Without --offline, bounded Contract downloads and cache writes may occur even when no draft is published. The suggested follow-up commands retain --offline when creation used it.

Review shared inputs before customization

Filesystem sources are rebased to the template’s existing inputs, not copied. This avoids silent configuration duplication, but editing a referenced file would affect both compositions. Copy an input to your intended directory and change the new composition’s source before customizing it. Repository DOT and Contract sources, absolute host bind grants and Secret references retain their identities. Host bind paths are not rebased as if they were relative configuration documents.

A fresh UUID prevents lifecycle-state adoption; it does not isolate fixed ports, application/workload names, named storage or externally owned gateways. Review these, Kubernetes namespaces and credentials before any real deployment. Existing collision, ownership, configuration and probe safety checks still apply. A checked plan or generated topology is not live producer acceptance, security hardening or independent adopter acceptance. The template README’s limitations continue to apply; creation does not qualify an untested producer.

Recover and clean up

Creator failures now include a stable diagnostic code and a specific recovery hint, without printing raw parser, filesystem or download errors:

  • CONTRACT_CACHE_MISS: warm the pinned owner/catalogue online, then retry offline.

  • COMPOSITION_NEW_TEMPLATE_SCHEMA: validate the template against the generated schema.

  • COMPOSITION_NEW_TEMPLATE_LOCK: inspect and explicitly review an intentional template-lock update.

  • COMPOSITION_NEW_OUTPUT_PARENT: choose an existing real directory without directory symlinks.

  • COMPOSITION_NEW_OUTPUT_LOCK or COMPOSITION_NEW_PUBLISH: choose an unused destination; there is no force mode.

  • COMPOSITION_NEW_RESOLUTION: validate exact releases, Contract origins and deployment choices using the same repository/offline options.

Failure never automatically repairs inputs or locks, starts a runtime, or publishes a partial draft. Diagnostic wording is executor output, not a new model.

  • Missing or stale template lock: inspect the original inputs and lock diff. Fix an intentional change in the template separately; creation never repairs it.

  • Existing output or adjacent lock: choose a new path. There is no --force.

  • Missing or symlinked output parent: create/select a real directory first.

  • Cold offline cache: run online validation of the pinned catalogue first. Digest mismatches require investigation, not changing a pin to bypass checks.

  • Need diagnostic detail: run dotx compose validate <template> --locked --json. Creator failure messages withhold raw parser values, URLs and credentials.

Complete private bytes are published without overwriting a concurrently created file. Non-overwriting publication needs hard-link support; unsupported filesystems fail closed. No lifecycle state, workloads, networks or volumes are created. Remove only the exercise’s my-monitoring.yaml and my-monitoring.lock.json when finished. For a reusable catalogue contribution, choose its final directory before creating it, add a README, review its lock and use dotx compose topology <composition.yaml> --write to generate its topology docs.
