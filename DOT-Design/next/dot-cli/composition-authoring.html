Create a composition

A DOT describes one component. A Composition chooses concrete deployments of several DOTs and connects their Anchors through Wires. Start from a catalogue example whose README describes your intended use case and its acceptance limits. The selected release v0.3.0 and its matching source CLI provide template-based dotx compose new. Selecting DOTs with --from-dots requires current 0.4.0 source, not the published v0.3.0 binary. Use a matching CLI and pinned catalogue.

Choose, preview and create

From your pinned DOT-Repository checkout, warm its verified Contract cache once:

dotx validate .
dotx compose new

Current source uses native forms: arrows browse, typing filters, Enter selects, and Ctrl-C cancels. Choose a template, accept or edit its suggested name/output, review the preview, then explicitly choose Write draft. Ctrl-U clears a text field before replacement. The published v0.3.0 flow uses numbered prompts and requires an unused output path in an existing directory. Neither cancellation nor EOF publishes a file. Noninteractive creation requires all choices and --yes; no CI job needs to wait for input.

For a repeatable exercise using the existing Node Exporter/Prometheus graph:

dotx compose new \
  --from Compositions/node-exporter-prometheus-monitoring/composition.yaml \
  --name my-monitoring --output my-monitoring.yaml --offline --yes
dotx compose lock my-monitoring.yaml --offline
dotx compose inspect my-monitoring.yaml --offline --locked
dotx compose topology my-monitoring.yaml --locked

Expected: a preview of two DOTs and one wire, a fresh ownership UUID, and a new YAML file with the same exact tool releases, deployment choices, Contract and Anchor IDs. The reviewed template and its lock are unchanged. The new lock is created only by your explicit lock command; review it before committing. The Composition graph version is retained; it is not another tool release.

No workloads are started. Offline creation needs a warm verified Contract cache; without --offline, bounded downloads and cache writes may occur even if no draft is published. Printed follow-up commands retain --offline when selected.

How draft validation works

The command verifies its input byte snapshot against the template’s adjacent lock, applies changes to the Java-generated Composition model, preserves ordinary YAML shape/comments, then checks the rendered values exactly and validates the candidate with the same generated schema and resolver. YAML merge keys are expanded by the YAML parser where necessary: inherited IDs, names and file sources must receive the intended new values too. Authoring uses a fresh model of the verified input bytes, separate from inferred execution services and probes. It does not infer compatibility, invent wires, copy product definitions, download templates from Git, change secret values or start a runtime.

Review shared inputs before customization

Filesystem sources are rebased to the template’s existing inputs, not copied. This avoids silent configuration duplication, but editing a referenced file would affect both compositions. Copy an input to your intended directory and change the new composition’s source before customizing it. Repository DOT and Contract sources, absolute host bind grants and Secret references retain their identities. Host bind paths are not rebased as if they were relative configuration documents.

A fresh UUID prevents lifecycle-state adoption; it does not isolate fixed ports, application/workload names, named storage or externally owned gateways. Review these, Kubernetes namespaces and credentials before any real deployment. Existing collision, ownership, configuration and probe safety checks still apply. A checked resolved composition or generated topology is not live producer acceptance, security hardening or independent adopter acceptance. The template README’s limitations continue to apply; creation does not qualify an untested producer.

Recover and clean up

Creator failures now include a stable diagnostic code and a specific recovery hint, without printing raw parser, filesystem or download errors:

  • CONTRACT_CACHE_MISS: warm the pinned owner/catalogue online, then retry offline.

  • COMPOSITION_NEW_TEMPLATE_SCHEMA: validate the template against the generated schema.

  • COMPOSITION_NEW_TEMPLATE_LOCK: inspect and explicitly review an intentional template-lock update.

  • COMPOSITION_NEW_OUTPUT_PARENT: choose an existing real directory without directory symlinks.

  • COMPOSITION_NEW_OUTPUT_LOCK or COMPOSITION_NEW_PUBLISH: choose an unused destination; there is no force mode.

  • COMPOSITION_NEW_RESOLUTION: validate exact releases, Contract origins and deployment choices using the same repository/offline options.

Failure never automatically repairs inputs or locks, starts a runtime, or publishes a partial draft. Diagnostic wording is executor output, not a new model.

  • Missing or stale template lock: inspect the original inputs and lock diff. Fix an intentional change in the template separately; creation never repairs it.

  • Existing output or adjacent lock: choose a new path. There is no --force.

  • Missing or symlinked output parent: create/select a real directory first.

  • Cold offline cache: run online validation of the pinned catalogue first. Digest mismatches require investigation, not changing a pin to bypass checks.

  • Need diagnostic detail: run dotx compose validate <template> --locked --json. Creator failure messages withhold raw parser values, URLs and credentials.

Complete private bytes are published without overwriting a concurrently created file. Non-overwriting publication needs hard-link support; unsupported filesystems fail closed. No lifecycle state, workloads, networks or volumes are created. Remove only the exercise’s my-monitoring.yaml and my-monitoring.lock.json when finished. For a reusable catalogue contribution, choose its final directory before creating it, add a README, review its lock and use dotx compose topology <composition.yaml> --write to generate its topology docs.

Current-source alternative: build from selected DOTs

The selection table shows the exact DOT release, catalogue origin and declared interfaces. The following deployment table groups that DOT’s choices by engine, type and profile. Origin comes from the same ownership/evidence paths used by catalogue validation. testing can include fixtures or planning definitions; Contracts and Anchors describe declarations, not live compatibility or production readiness. No entries are silently hidden.

After publication, the summary names the saved file, declaration-validation boundary and unchanged runtime state. It prints copyable commands to inspect the draft, explicitly create its lock and inspect it locked, retaining the selected repository and offline mode. None of these actions runs automatically. Review shared inputs and the newly created lock before any deployment.

This 0.4.0 work requires a matching source CLI; it is not in the published v0.3.0 binary. From the matching DOT-Repository checkout, with verified cached Contracts:

dotx compose new --from-dots --repository . --offline --name my-monitoring

Omit --name to open a native Huh Composition name field prefilled with a random, readable suggestion such as calm-otter. Enter accepts it; Ctrl-U clears the field so you can type a replacement. Names, paths, selections and confirmations all use the shared form interface, not just the choice menus.

The adjective–animal suggestion varies each run; compound animal names are hyphenated too (for example calm-guinea-pig). Ctrl-C cancels a native form; the line fallback also supports q. EOF or an incomplete form aborts without publishing or accepting defaults. The same field is used by current-source template creation. Existing catalogue folder/file names are skipped, but a suggestion does not reserve a destination: final publication checks still reject concurrent collisions. An explicit --name is retained exactly and skips the prompt; noninteractive --yes still requires it. This friendly label is separate from the fresh ownership UUID and is not a secret or security identifier.

Select exact releases and explicit deployments. The native Instance name field is prefilled with a lowercase, hyphenated label derived from the selected tool’s name, such as prometheus.

Press Enter to use it, or Ctrl-U and type a unique label such as metrics-primary. Suggestions skip aliases already used in this composition: prometheus, then prometheus-2, prometheus-3, and so on. Explicit duplicate names are rejected; custom names are never silently rewritten. Cancel or EOF never accepts an unanswered default. This label does not change the selected DOT’s identity or tool release, and does not isolate fixed workload names, ports or storage. Existing compositions and locks are not renamed or regenerated.

Deployment choices put the platform first, followed by the manifest type and the exact profile ID:

ENGINE      | DEPLOYMENT TYPE  | PROFILE
DOCKER      | DOCKER_COMPOSE   | docker-compose
DOCKER      | DOCKER_IMAGE     | docker
KUBERNETES  | HELM_CHART       | helm-chart

Options are grouped by engine, then manifest type, retaining the declared profile order within each group. Only the selected DOT’s deployments are listed; the menu is not filtered by locally installed tools because authoring does not deploy. The profile ID distinguishes alternatives with the same engine and type. Headers and columns stay aligned while filtering, in both scrolling and numbered menus. Untrusted display text is escaped rather than interpreted by the terminal.

The native scrolling selector lets you browse all catalogue DOTs with ↑/↓, type initial letters such as Pro or Key to filter immediately, select with Enter and cancel with Ctrl-C. Backspace edits the case-insensitive substring query; no / prefix is needed. New and edit use this same TUI. Deployment, Anchor and connection choices use the same UI. No DOT, Contract or Anchor ID needs to be constructed manually.

For a screen reader or the numbered interface, set DOTX_NO_TUI=1 or ACCESSIBLE=1 before the command. Redirected output, small and TERM=dumb terminals also use this non-redrawing fallback: /text filters, n/p pages, a displayed number selects and q cancels. The header states the visible range and total; the first 12 rows are not the whole catalogue. The UI does not change validation or perform any deployment. Input must still be a terminal; piped input is rejected. The native Go interface uses Bubble Tea through Huh form components. Views share navigation and cancellation behavior without owning model validation, deployment or cleanup logic. Draft publication uses Write draft / Cancel buttons, initially selecting Cancel: Enter alone does not authorize a write. Existing defaults containing control characters use an explained escaped line fallback when a single-line form cannot preserve them losslessly. Original bytes remain authoritative. If you omit --output, press Enter to accept Compositions/my-monitoring/composition.yaml inside the selected catalogue. From DOT-Design, --repository DOT-Repository instead suggests DOT-Repository/Compositions/my-monitoring/composition.yaml. This is a draft’s storage location, not a deployment destination. The same default applies to the current-source interactive template flow. Missing default folders are created only after validation and explicit write confirmation; cancellation creates no folders. A composition name used as a folder must be one path component, not ./.. or a path; other valid display names can use an explicit output path.

A relative --repository path is relative to your current working directory, not the draft’s directory. The current-source resolver retains an absolute execution location, so a draft saved elsewhere still deploys the selected catalogue bundle. Portable sources and lock identities remain repository:// references; no machine-local path is written into the authored YAML or lock.

To save elsewhere, enter another path at the prompt or supply --output. An explicit output’s parent must already exist. Existing files, adjacent locks and directory symlinks are refused; there is no overwrite mode. Publication failure removes only still-identical empty folders created by this operation, never pre-existing folders or concurrent contents. Creating the catalogue draft does not add a README, topology artifacts or a lock; review and complete those before contributing the composition. For the real monitoring example choose Node Exporter and Prometheus, then connect node-metrics to scrape-target. Select a config-file materializer deriving ENDPOINT_HOST_PORT, targeting Prometheus’s declared configuration file and the existing scrape-target JSON Pointer. Input paths are relative to the new YAML; review the existing monitoring README rather than inventing a producer interface.

The menu labels connections accepted, incompatible or UNKNOWN using the ordinary compatibility authority. UNKNOWN is not verified; required authentication must be explicitly bound and checked. Required operation parameters and service configuration are separate from identifiers. Enter native Secret references, never their values. A reviewed optional DeploymentInputs YAML/JSON fragment uses the exact generated model for advanced workload selectors, volumes and OCI/CDI grants; paths resolve beside the new composition, not beside the fragment. Missing, ambiguous, unsupported or unsafe inputs fail closed without output.

Brokered AsyncAPI send/receive pairs require a separately selected broker service/port, including existing MQTT, NATS, Kafka and AMQP profiles. This endpoint is not another Anchor wire. Cross-runtime pairs require an explicit, already provisioned EXTERNAL_GATEWAY host/port. The operator owns that gateway and its cleanup; the CLI neither creates networking infrastructure nor uses host-network fallbacks. The complete graph still passes the existing resolver’s constraints.

Expected: exact deployment choices and a topology preview, then explicit write confirmation. A fresh ownership UUID and generated-model round-trip check precede non-overwriting publication. No lock is created, no existing state is adopted and nothing is deployed. --from-dots cannot be combined with --from or --yes, and requires a terminal. A complete validated draft is not live API acceptance.

After reviewing the YAML and every referenced input, explicitly create and review its lock using the same catalogue/offline options, then follow the real monitoring or authenticated secure-API acceptance route. Declaration validation does not qualify a catalogue gap, producer double or fixture for production use.
