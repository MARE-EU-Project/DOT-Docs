Author an interface-aware DOT

Start by reusing a complete catalogue DOT. Author a new definition only for a genuinely new component or a local exercise; do not publish another root for an existing product. Add deployment alternatives to its canonical bundle instead.

These commands require the current source-built CLI, jq, catalogue access and network access to the pinned raw Contract. The original published v0.2.5 binary predates this flow. Follow the compatible-source installation route. No Java, Jsonnet, Docker daemon or Kubernetes cluster is needed for the commands below; the last command renders a deployment without starting it.

Confirm the actual component release

--version is required for noninteractive authoring. Interactive mode asks for the actual tool release without inventing 0.0.0. Image packaging tags and Helm chart versions are not reliable substitutes: confirm the tool release yourself. Explicit source/test versions remain available for unreleased components.

Declare at least one meaningful --skill; repeat it for multiple capabilities. Use an existing catalogue capability where appropriate and document a genuinely new capability in Skills/. Creation does not infer Skills from an image.

Rehearse with the existing Prometheus Contract

This temporary exercise reuses Prometheus’s existing authoritative declaration; it creates no second catalogue entry and copies no dependency interface. From DOT-Design, prepare an empty exercise directory:

# Run from DOT-Design; set DOT_REPOSITORY=$PWD from a standalone catalogue.
DOT_REPOSITORY="${DOT_REPOSITORY:-$PWD/DOT-Repository}"
AUTHORING_DIR="$(mktemp -d -t dotx-authoring.XXXXXXXX)"
jq '.contracts[0]' "$DOT_REPOSITORY/DOTs/external/Prometheus-DOT/dot.json" \
  >"$AUTHORING_DIR/contract.json"

contract.json is one complete Contract in the generated DOT-Domain model, not a raw OpenAPI document or catalogue wrapper. It contains the owned ID, name, interface version, standard, format and HTTPS payload.url/sha256. For your own tool, provide its own declaration with a release-matched official specification where available. Never relabel another component’s Contract.

dotx new --from docker-image prom/prometheus:v3.15.0 \
  --name Prometheus --version 3.15.0 --skill Metrics-Scraping \
  --service prometheus --port http:9090 \
  --contract "$AUTHORING_DIR/contract.json" \
  --operation 'build-information=#/paths/~1status~1buildinfo/get' --bind http \
  --output "$AUTHORING_DIR/bundle/dot.json"

Expected: Owned OpenAPI interface verified. The command validates the declaration against the generated schema, checks exact ownership, downloads and verifies the payload using the ordinary bounded HTTPS/SHA-256 verifier, and resolves the selected operation using the composition resolver. It writes the complete Contract, a fresh Anchor UUID, its service Contract reference and the named-port binding into dot.json only after verification succeeds.

The UUID remains the stable wire identity; build-information is its readable name. The selector remains separate from the Contract ID. Repeat --operation for additional provided operations on the same declared TCP port. --bind requires an exact service port name and never guesses a listener.

For a menu of operations and port choices, use --interactive --contract "$AUTHORING_DIR/contract.json" with the same source/name/version/Skill/port arguments and a new output path. Without an imported Contract, interactive mode offers an optional declaration-file prompt; leave it empty for a runtime-only scaffold. Do not overwrite this exercise’s output unintentionally.

Validate, inspect and render

dotx validate "$AUTHORING_DIR/bundle" \
  --schema "$DOT_REPOSITORY/Schema/schema.json" --profile reusable
dotx inspect "$AUTHORING_DIR/bundle"
dotx deploy "$AUTHORING_DIR/bundle" --deployment docker-image --dry-run

Expected: the reusable profile passes, inspection shows one owned Contract and one provided Anchor, and dry-run renders the Docker command. This checks the declared interface and binding, not a running API. The flow does not establish that a URL is vendor-owned or that its release metadata is truthful; review provenance. For live acceptance with this source CLI/catalogue pair, follow the current-source guided demo. The released quickstart uses its own pinned artifact set; do not replace only one component of this source-built pair with the original published v0.2.5 binary.

This first guided interface profile covers owned OpenAPI provided operations only. AsyncAPI, GraphQL, Protobuf, external dependency references and provider-neutral requirements remain supported by the domain and composition commands, but require explicit authoring. No protocol metadata is duplicated from the Contract and no compatibility or live-readiness claim is inferred.

Recover from errors and clean up

  • Missing release: supply --version; no output is created.

  • Ownership mismatch: use the actual originating product/release, or an external Anchor reference for a dependency. Do not rename a dependency into ownership.

  • Download or digest failure: check access, the official raw URL and expected bytes. Never change a hash solely to bypass a failure.

  • Invalid selector: choose an operation from the verified specification. Encode OpenAPI selectors as URI-fragment JSON Pointers, including ~1 for /.

  • Binding failure: declare --port http:9090 and use --bind http.

  • Existing output: choose a new path. --force permits replacement only after verification. Complete bytes are staged and published atomically; a concurrently created output is not overwritten without --force. Forced replacement preserves existing Unix file mode bits and does not follow a destination symlink into another file. Staging failures preserve the old file.

Non-overwriting publication requires hard-link support in the output filesystem; unsupported filesystems fail closed rather than falling back to truncation.

new creates a fresh definition; it is not an incremental editor or migration command. --force replaces the whole scaffold and generates fresh Anchor UUIDs. For an existing integrated DOT, edit its definition while retaining stable Anchor identities and review affected composition locks instead of regenerating the scaffold.

# Only the files created by this exercise; unexpected extra files are retained.
rm -- "$AUTHORING_DIR/bundle/dot.json" "$AUTHORING_DIR/contract.json"
rmdir -- "$AUTHORING_DIR/bundle" "$AUTHORING_DIR"

Only exercise files are removed. No containers, networks, volumes or cluster resources were created. Developers can run the same documented commands and ownership-negative control with task testing:authoring from DOT-Design.
