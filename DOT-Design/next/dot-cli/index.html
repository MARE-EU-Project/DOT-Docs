DOT-CLI

dotx is the Go command-line application provided by the independent DOT-CLI repository. It operates on DOT definitions and compositions; it is not a catalogue server or a replacement for Docker, Kubernetes, Helm, Vagrant or Wasmtime.

Start with a working DOT

Follow Getting started for checksummed Linux-amd64 installation and the Prometheus Docker Compose quickstart: validate, deploy, verify an API response, inspect status and clean up. Running the released binary does not require a Java or Go development toolchain.

Use the guided demo to see a topology and a multi-DOT composition. The MARE PoC walkthroughs include a presenter pause for inspecting verified live results before cleanup.

Find the right command

Task Command family

Check a definition, bundle or complete catalogue

dotx validate

Read a DOT’s declared interfaces and deployment choices

dotx inspect

Discover and inspect catalogue entries

dotx repository

Operate one selected DOT deployment

dotx deploy, status, start, stop, destroy, ps

Validate, lock, inspect and display a multi-DOT graph

dotx compose validate, lock, inspect, topology

Operate and verify a composition

dotx compose apply, status, probe, destroy

Relate a locked graph to observed runtimes and historical probes

dotx compose topology --status (use the applied run’s cache/configuration)

Check deployment tools and runtime prerequisites

dotx tool

Ask the installed binary for its exact options:

dotx version
dotx help
dotx compose --help
dotx compose inspect --help

Composition subcommand help includes only that operation’s flags, an example, a suggested next step and its safety boundary. For example, compose inspect resolves declared inputs without deployment, apply --dry-run previews commands, and status reads recorded runtime state. The complete production profile remains available through dotx compose --help.

Understand validation failures

The current source CLI reports a diagnostic code, the affected file, an RFC 6901 JSON Pointer, a short explanation and a repair hint. Schema diagnostics use the selected generated schema to show expected types and exact enum spellings; there is no separate hand-maintained model definition. Input values, manifest contents and raw download errors are withheld to protect credentials. An empty pointer means a document-root or file-level failure. Some catalogue metadata failures identify a directory rather than an individual file.

For editors, scripts and CI, request one JSON report on stdout, including failures:

dotx validate DOT-Repository --offline --json

Run this example from a DOT-Design checkout with its pinned catalogue and source-built CLI; from a standalone catalogue checkout use . instead of DOT-Repository. The report has formatVersion: 1, valid, target, kind, completed dots/compositions counts, and diagnostics containing code, file, pointer, message, hint and optional keyword/expected fields. Exit codes remain 0 (valid), 1 (invalid or unavailable), and 2 (usage error). Normal JSON-mode validation failures leave stderr empty. Validation stops at the first failing definition or phase, although a schema failure can report multiple constraints. It never repairs inputs or rewrites reviewed locks automatically.

For reusable catalogue examples and explicit deployment selection, see Deployments and examples. For Anchor selectors, Wires, native Secret references, locks and lifecycle safety, use the composition guide.

Validation and planning are not live acceptance. Active probes run only for supported, explicitly configured Contract operations and transports. The walkthroughs state which endpoints are actually exercised and distinguish real producers, source-adapted integrations and synthetic fixtures.

Versions and model authority

DOT-Design and its pinned DOT-CLI source versions are kept aligned. Release installation instructions use the published binary; development demos and the diagnostics above may require the exact source revision pinned by the DOT-Design checkout, even when its version label matches a release. See Development and testing for source installation, Bash completion, local CI-equivalent Tasks and prerequisites.

All portable models belong to DOT-Domain. The CLI consumes its generated JSON Schemas and Go bindings; it does not define a competing DOT or Composition input model. Resolved execution plans, lock fingerprints and private runtime state are executor concerns. DOT definitions and reusable composition inputs live in DOT-Repository.
