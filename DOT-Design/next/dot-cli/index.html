DOT-CLI

dotx is the Go command-line application provided by the independent DOT-CLI repository. It operates on DOT definitions and compositions; it is not a catalogue server or a replacement for Docker, Kubernetes, Helm, Vagrant or Wasmtime.

Start with a working DOT

Follow Getting started for checksummed Linux-amd64 installation and the Prometheus Docker Compose quickstart: validate, deploy, verify an API response, inspect status and clean up. Running the released binary does not require a Java or Go development toolchain.

Use the guided demo to see a topology and a multi-DOT composition. The MARE PoC walkthroughs include a presenter pause for inspecting verified live results before cleanup.

Find the right command

Task Command family

Check a definition, bundle or complete catalogue

dotx validate

Read a DOT’s declared interfaces and deployment choices

dotx inspect

Discover and inspect catalogue entries

dotx repository

Author a DOT; create a separate editing candidate in current 0.4.0 source

dotx new; current source: dotx edit

Operate one selected DOT deployment

dotx deploy, status, start, stop, destroy, ps

Validate, lock, inspect and display a multi-DOT graph

dotx compose validate, lock, inspect, topology

Operate and verify a composition

dotx compose apply, status, probe, destroy

Relate a locked graph to observed runtimes and historical probes

dotx compose topology --status (use the applied run’s cache/configuration)

Refresh or check composition README diagrams and Mermaid files

dotx compose topology Compositions --write / --check

Check deployment tools and runtime prerequisites

dotx tool

Ask the installed binary for its exact options:

dotx version
dotx version --verbose
dotx help
dotx compose --help
dotx compose inspect --help

version --verbose adds the source revision, modified-worktree status, Go version and OS/architecture without contacting a server. Missing build metadata is shown as unknown. Plain version remains a single line; the version number alone does not identify the exact source build used for a rehearsal.

Composition subcommand help includes only that operation’s flags, an example, a suggested next step and its safety boundary. For example, compose inspect resolves declared inputs without deployment, apply --dry-run previews commands, and status reads recorded runtime state. The complete production profile remains available through dotx compose --help.

Maintain composition topology documentation

From a standalone catalogue checkout, the selected release or matching source CLI can update every composition’s existing README topology block and adjacent topology.mmd:

dotx compose topology Compositions --write
dotx compose topology Compositions --check

From DOT-Design, use DOT-Repository/Compositions instead. A single composition file is also accepted. Both modes require verified locks; no lock is repaired automatically. The command checks every graph and destination before writing, preserves authored text outside the marked block, and rejects symlinked files and malformed markers. --check writes nothing and exits nonzero on drift. Individual files are replaced atomically, not as a multi-file transaction; resolve any I/O failure and rerun. Display options such as --format, --color and --status cannot be combined with documentation modes.

Only dotx is needed: the former Bash generator and its jq/awk dependencies are not required. The optional task compositions:topology:generate and :check wrappers remain available in both checkouts. A generated diagram is a locked resolved composition view, not proof of live interoperability.

Find a DOT by its readable release coordinate

The current source-built CLI discovers the catalogue from your working directory. At each level, starting in the current directory and walking toward the filesystem root, it checks for DOTs/ first, then DOT-Repository/DOTs/. Commands therefore work from DOT-Design, DOT-CLI, a standalone catalogue checkout, or a directory inside one of its DOTs/compositions. A renamed catalogue is recognized by its DOTs/ directory, not by its Git remote or directory name.

dotx repository list --skill Metrics-Scraping
dotx repository list --verbose
dotx repository inspect Prometheus@3.15.1 --json
dotx repository resolve Prometheus@3.15.1

The default catalogue table starts with names, versions and scopes, followed by up to three Skill names. Every matching DOT remains visible; +N more indicates additional Skills. --verbose shows IDs, groups and categories. --json retains the complete structured report and takes precedence over --verbose. Listing definitions does not prove live readiness.

inspect and resolve accept an exact, case-sensitive DOT name@version, as well as the authoritative ID/version selector. The version is exact: no fuzzy name matching, automatic latest-version choice or identity migration is performed. The last @ separates the version; quote names containing spaces. Ambiguous matches fail, and ID matches take precedence over coincidentally matching names. JSON output reports the authoritative case-sensitive ID and definition.

Explicit --repository <path-or-git-url> overrides discovery. If the selected catalogue is malformed, unreadable or missing, the command fails rather than switching to a different catalogue. Without a discoverable catalogue, provide that flag explicitly. Composition sources remain repository://<id>@<version>; display-name lookup does not replace source identities, locks or runtime ownership checks. No separate catalogue inventory is required.

Author a runtime-only scaffold

To connect existing DOTs without assembling identifiers manually, follow Create a composition from a reviewed example. That flow verifies a template’s lock and creates a fresh ownership identity; it does not create new product definitions or deploy workloads.

Native authoring writes dot.json without Git, Jsonnet or template downloads. From the DOT-Design checkout:

dotx new --from docker-image prom/prometheus:v3.15.1 --name Prometheus --version 3.15.1 --skill Metrics-Scraping --port http:9090 --output ./my-dot/dot.json
dotx validate ./my-dot --schema DOT-Repository/Schema/schema.json
dotx inspect ./my-dot
# Alternatively: dotx new --interactive

This does not infer Contracts or Anchors and does not prove interoperability or live readiness. Reuse complete catalogue bundles where available; native authoring is a starting point for a genuinely new DOT. Add authoritative Contracts and explicit Anchors/bindings before integration. The positional dotx new <name> mode remains a template-based project workflow requiring Git, Jsonnet and network access. See dotx new --help for both modes.

Native authoring derives <name>@<version> as the DOT ID and requires at least one explicit --skill <id> (repeat the flag for multiple capabilities). Interactive authoring asks for a Skill when none was supplied. Declare the capability’s meaning in the selected catalogue’s Skills/; do not infer capabilities, interoperability or live readiness from the image alone. The actual tool release must be supplied explicitly; no 0.0.0 default is invented and Helm chart versions do not determine application versions.

For an owned OpenAPI interface, native authoring can also verify a generated-model Contract declaration, select operations and generate Anchor IDs and named-port bindings. See the executable interface-authoring exercise. Published v0.3.0 requires explicit authoring for other standards and dependency references. The matching 0.4.0 source adds guided imports for all four standards and separate editing candidates; the authoring guide states their supported profiles and review boundaries.

Inspect deployment choices

From the DOT-Design checkout, use the current source-built CLI:

dotx inspect DOT-Repository/DOTs/external/Prometheus-DOT
dotx inspect DOT-Repository/DOTs/external/Prometheus-DOT --verbose
dotx inspect DOT-Repository/DOTs/external/Prometheus-DOT --json

The default overview lists every deployment’s ID, platform, manifest type, service count and required inputs, followed by short Contract, Anchor and Skill previews. It never automatically chooses a deployment. INPUTS* counts required environment/config-file declarations without defaults for each service; it is not a readiness result. Storage and host/device declarations are flagged separately so you can review persistence and permissions before deploying.

Use --verbose for IDs, all interfaces/selectors, service bindings and detailed configuration declarations. --json preserves the complete structured report and overrides --verbose when combined. Invalid sensitive defaults are rejected in every mode; provide secrets through deployment-instance inputs instead. Inspection does not start workloads, test runtime availability or prove live API acceptance. It does not replace dotx validate.

Root Contract metadata comes directly from complete dot.json declarations; ID-only roots fail rather than importing metadata from local files. JSON keeps the existing report structure, IDs and ordering. Inspection never downloads or verifies payload bytes; use dotx validate for that separate check. Validation caches digest-verified bytes outside the DOT. Warm it online once before --offline; a cold cache fails without requests or writes. Deployment support uses the same capability list as deploy/lifecycle, including WebAssembly.

Human output provides a validation command and a dry-run template. Choose an exact deployment ID from the displayed choices and replace <deployment-id>; inspection never selects one automatically. Remote Git targets instead require a persistent checkout for these next steps, since their inspection clone is temporary.

Understand validation failures

The current source CLI reports a diagnostic code, the affected file, an RFC 6901 JSON Pointer, a short explanation and a repair hint. Schema diagnostics use the selected generated schema to show expected types and exact enum spellings; there is no separate hand-maintained model definition. Input values, manifest contents and raw download errors are withheld to protect credentials. An empty pointer means a document-root or file-level failure. Some catalogue metadata failures identify a directory rather than an individual file.

For editors, scripts and CI, request one JSON report on stdout, including failures:

dotx validate DOT-Repository --offline --json

Run this example from a DOT-Design checkout with its pinned catalogue and source-built CLI; from a standalone catalogue checkout use . instead of DOT-Repository. The report has formatVersion: 1, valid, target, kind, completed dots/compositions counts, and diagnostics containing code, file, pointer, message, hint and optional keyword/expected fields. Exit codes remain 0 (valid), 1 (invalid or unavailable), and 2 (usage error). Normal JSON-mode validation failures leave stderr empty. Validation stops at the first failing definition or phase, although a schema failure can report multiple constraints. It never repairs inputs or rewrites reviewed locks automatically.

The same source CLI also reports failures from dotx compose validate <composition.yaml> --json and dotx compose inspect <composition.yaml> --json as one secret-safe JSON document on stdout, including usage errors. These failure reports have formatVersion: 1, valid: false, kind: composition, target, shared diagnostics and evidence: composition-validation-not-live-acceptance. Normal JSON failures leave stderr empty; output-write failures use stderr. Schema diagnostics retain exact field pointers, while resolution failures without finer context identify the composition file. Raw parser, document and transport values are withheld.

Successful composition validation still returns its existing valid, compositionId and unknownWires summary, and successful inspection still returns resolved execution details. Check the exit code and result, not merely whether stdout contains JSON. These failure-report guarantees do not extend to runtime apply, upgrade, probe or status commands. No lock is regenerated automatically, and an unknown wire remains an explicit limitation rather than live acceptance.

Recover from a composition runtime failure

The matching 0.4.0 source also gives compose apply, upgrade, probe, status and destroy secret-safe diagnostic codes and recovery hints on stderr. This is not a new runtime JSON failure envelope: successful JSON shapes and existing exit-code meanings are preserved. Raw tool, parser, transport and credential values are withheld. A diagnostic identifies an instance or wire when the failing boundary supplies that context; generic failures identify the composition instead.

Code What to do next

COMPOSITION_INSTANCE_DEPLOY / COMPOSITION_INSTANCE_CLEANUP

Inspect the named instance and recorded status. Use the original CLI and run identity for cleanup; never remove unrelated resources.

COMPOSITION_WIRE_PROBE

Review the named wire’s operation, endpoint, authentication and probe inputs. A failed probe is not producer acceptance.

COMPOSITION_BUSY / COMPOSITION_RESUME_STATE

Check the active operation and recorded state. Do not bypass locks, adopt another run or regenerate a composition lock to conceal a mismatch.

COMPOSITION_UPGRADE_STORAGE / COMPOSITION_UPGRADE_RESTORED

Review storage safety or the restored previous deployment before retrying. Restoration is not a successful upgrade.

Follow the emitted hint and run dotx compose status <composition.yaml> with the same cache/configuration as the applied run. No diagnostic automatically repairs locks, changes ownership or grants permissions. These improvements do not claim an equivalent failure-report format for top-level single-DOT runtime commands.

For container-backed probes, prepare runner images explicitly before live testing:

dotx compose probe composition.yaml --locked --images

This read-only command emits the selected pinned helper images as JSON. It does not pull images, access lifecycle state, load credentials or execute a Contract operation. A caller preparing a Docker runner must cache the exact image pin on the host daemon; a Kubernetes runner needs its node cache, which is distinct. The four-Contract demo’s preparation task performs the appropriate verified pulls.

Failure-only runtime diagnostics separate image checks, runner startup and operation execution where evidence permits. An unresolved startup phase is not reported as proof that a request reached the producer. Diagnostics retain static codes, timings and recovery guidance, not raw tool stderr, credential-bearing arguments or response payloads. Existing successful probe output and exit-code meanings remain unchanged.

For reusable catalogue examples and explicit deployment selection, see Deployments and examples. For Anchor selectors, Wires, native Secret references, locks and lifecycle safety, use the composition guide.

Validation and resolution are not live acceptance. Active probes run only for supported, explicitly configured Contract operations and transports. The walkthroughs state which endpoints are actually exercised and distinguish real producers, source-adapted integrations and synthetic fixtures.

Current-source Kubernetes/Helm probes read retained logs only after checking the probe container’s completion and exit code. This avoids losing output emitted before an attach stream starts. Each probe executes once, with no hidden retry of an API operation or delivery. Cleanup uses the Pod’s create-time UID and a bounded deletion wait; replacement Pods are not adopted, and failed cleanup cannot produce successful acceptance. This hardening requires the matching source binary, not the original v0.3.0 release.

Ctrl-C or SIGTERM cancels the current Kubernetes probe, completes bounded UID-safe cleanup and stops subsequent selected operations. Recorded evidence reports CANCELLED (or RUNNER_CLEANUP_FAILED if cleanup fails); the command returns 130 for Ctrl-C or 143 for SIGTERM. Allow cleanup to finish before closing the terminal; force-killing the process cannot guarantee cleanup.

Versions and model authority

See Adopting DOT for compatible artifact sets, editor schema associations and the current-source, deployment-aware dotx tool check --dot <bundle> --deployment <exact-id> command. A successful prerequisite report is not live API acceptance.

DOT-Design and its pinned DOT-CLI source versions are kept aligned. Release installation instructions use the published binary; development demos and the diagnostics above may require the exact source revision pinned by the DOT-Design checkout, even when its version label matches a release. See Development and testing for source installation, Bash completion, local CI-equivalent Tasks and prerequisites.

All portable models belong to DOT-Domain. The CLI consumes its generated JSON Schemas and Go bindings; it does not define a competing DOT or Composition input model. Resolved execution details, lock fingerprints and private runtime state are executor concerns. DOT definitions and reusable composition inputs live in DOT-Repository.
