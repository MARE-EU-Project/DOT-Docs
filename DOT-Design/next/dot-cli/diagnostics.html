Inspect and troubleshoot

Use this reference when a preview or live operation needs investigation. For the command map, return to the CLI guide. For a worked deployment, follow Run your first composition. For environment settings and configuration files, see Configure a DOT.

Inspect deployment choices

From the DOT-Design checkout, use the current source-built CLI:

dotx inspect DOT-Repository/DOTs/external/Prometheus-DOT/3.15.1
dotx inspect DOT-Repository/DOTs/external/Prometheus-DOT/3.15.1 --verbose
dotx inspect DOT-Repository/DOTs/external/Prometheus-DOT/3.15.1 --json

The default overview starts with the dot.json fields id, name, version, optional description and groups, and a metadata tree with created / updated. version is the represented tool release, not the catalogue revision or CLI version. The displayed dot.json path is local inspection context.

The runtimes tree preserves each Runtime’s original position ([0], [1], and so on), its platform with engine and version, and its own deployments table. Each table lists every deployment’s id, manifest.type and services count. Runtimes remain separate even when their Platform values match; empty deployment lists are shown explicitly. Tables have outer borders, column edges and a separate header band, including the deployment tables nested inside the Runtime tree. On a terminal, headings are cyan, field names bold and borders dim; PROVIDES is green and REQUIRES magenta. The role words remain visible. Colors are disabled for redirected output, TERM=dumb, ACCESSIBLE=1, or a non-empty NO_COLOR value. For example, use NO_COLOR=1 dotx inspect <DOT-path>. --json always emits plain JSON, including when stdout is a terminal. The contracts, connectors and skills tables use the declared field names, with separate id and name columns where applicable. Every Connector is shown, grouped under role: PROVIDES (interfaces this tool offers) and role: REQUIRES (interfaces this tool needs from other tools). Source order is preserved within each role; empty role groups are omitted. Contract and Skill previews show up to three entries each; use --verbose for the remaining entries and detailed declarations. It never automatically chooses a deployment. Required environment/config-file declarations remain available in --verbose and --json. Storage and host/device declarations are flagged separately so you can review persistence and permissions before deploying.

Use --verbose for all Contract details, selectors, service bindings and detailed configuration declarations. --json includes the same root description, groups and metadata in the complete structured report and overrides --verbose when combined. Invalid sensitive defaults are rejected in every mode; provide secrets through deployment-instance inputs instead. Inspection does not start workloads, test runtime availability or prove live API acceptance. It does not replace dotx validate. The tree/table layout is a terminal view; it does not change the structured --json report or add a Runtime field to that report.

Root Contract metadata comes directly from complete dot.json declarations; ID-only roots fail rather than importing metadata from local files. Existing JSON report fields and ordering are retained; description, groups and metadata are additive root fields. Inspection never downloads or verifies payload bytes; use dotx validate for that separate check. Validation caches digest-verified bytes outside the DOT. Warm it online once before --offline; a cold cache fails without requests or writes. Deployment support uses the same capability list as deploy/lifecycle, including WebAssembly.

Human output ends with one concrete, quoted validation command. Inspection never selects or deploys an alternative automatically. Remote Git targets instead require a persistent checkout before validation, since their inspection clone is temporary.

Understand validation failures

The current source CLI reports a diagnostic code, the affected file, an RFC 6901 JSON Pointer, a short explanation and a repair hint. Schema diagnostics use the selected generated schema to show expected types and exact enum spellings; there is no separate hand-maintained model definition. Input values, manifest contents and raw download errors are withheld to protect credentials. An empty pointer means a document-root or file-level failure. Some catalogue metadata failures identify a directory rather than an individual file.

In 0.4.0, every DOT reader checks the embedded, Java-generated schema before converting JSON into Go values. This includes inspection, catalogue discovery, composition resolution and runtime commands. An explicit --schema can add constraints but cannot waive required model fields, invalid nulls or retired configuration keys. Keep the CLI, generated schema and catalogue revisions aligned. This shared raw-input stage neither fetches payloads nor mutates workloads. dotx validate still verifies declared documents; that verification and live API acceptance are separate stages.

For editors, scripts and CI, request one JSON report on stdout, including failures:

dotx validate DOT-Repository --offline --json

Run this example from a DOT-Design checkout with its pinned catalogue and source-built CLI; from a standalone catalogue checkout use . instead of DOT-Repository. The report has formatVersion: 1, valid, target, kind, completed dots/compositions counts, and diagnostics containing code, file, pointer, message, hint and optional keyword/expected fields. Exit codes remain 0 (valid), 1 (invalid or unavailable), and 2 (usage error). Normal JSON-mode validation failures leave stderr empty. Validation stops at the first failing definition or phase, although a schema failure can report multiple constraints. It never repairs inputs or rewrites reviewed locks automatically.

The same source CLI also reports failures from dotx compose validate <composition.yaml> --json and dotx compose inspect <composition.yaml> --json as one secret-safe JSON document on stdout, including usage errors. These failure reports have formatVersion: 1, valid: false, kind: composition, target, shared diagnostics and evidence: composition-validation-not-live-acceptance. Normal JSON failures leave stderr empty; output-write failures use stderr. Schema diagnostics retain exact field pointers, while resolution failures without finer context identify the composition file. Raw parser, document and transport values are withheld.

Successful composition validation still returns its existing valid, compositionId and unknownEdges summary, and successful inspection still returns resolved execution details. Check the exit code and result, not merely whether stdout contains JSON. These failure-report guarantees do not extend to runtime apply, upgrade, probe or status commands. No lock is regenerated automatically, and an unknown edge remains an explicit limitation rather than live acceptance.

Next configuration and ownership details

Current source keeps mounted literal/default configuration files separate for each execution, including Docker image deployments and previews. Docker image replacement verifies the existing container’s selected DOT/deployment/runtime ownership and removes its exact ID; a foreign collision stops the command. Kubernetes literal environment overrides replace an earlier valueFrom source on the selected container. These fixes require a matching source build; they do not change the already published binary or establish live API acceptance. Compose path-based lifecycle also retains verified dotenv inputs needed for native interpolation and profile selection. Its live preflight uses Compose’s config --variables and config --profiles support; dry-runs remain previews. The matching Next executor reserves DOTX_COMPOSE_ for private staging. Use another prefix for workload variables, native interpolation and operator defaults; a collision is refused before changing the deployment.

For the matching Next build, review the configuration and ownership boundaries, including ordered dotenv overrides, service isolation and handling older native resources. Keep the original CLI and execution context for existing workloads.

Recover from a composition runtime failure

The 0.4.0 release also gives compose apply, upgrade, probe, status and destroy secret-safe diagnostic codes and recovery hints on stderr. This is not a new runtime JSON failure envelope: successful JSON shapes and existing exit-code meanings are preserved. Raw tool, parser, transport and credential values are withheld. A diagnostic identifies an instance or edge when the failing boundary supplies that context; generic failures identify the composition instead.

Code What to do next

COMPOSITION_INSTANCE_DEPLOY / COMPOSITION_INSTANCE_CLEANUP

Inspect the named instance and recorded status. Use the original CLI and run identity for cleanup; never remove unrelated resources.

COMPOSITION_WIRE_PROBE

Review the named edge’s operation, endpoint, authentication and probe inputs. A failed probe is not producer acceptance.

COMPOSITION_BUSY / COMPOSITION_RESUME_STATE

Check the active operation and recorded state. Do not bypass locks, adopt another run or regenerate a composition lock to conceal a mismatch.

COMPOSITION_UPGRADE_STORAGE / COMPOSITION_UPGRADE_RESTORED

Review storage safety or the restored previous deployment before retrying. Restoration is not a successful upgrade.

Follow the emitted hint and run dotx compose status <composition.yaml> with the same cache/configuration as the applied run. No diagnostic automatically repairs locks, changes ownership or grants permissions. These improvements do not claim an equivalent failure-report format for top-level single-DOT runtime commands.

For container-backed probes, prepare runner images explicitly before live testing:

dotx compose probe composition.yaml --locked --images

This read-only command emits the selected pinned helper images as JSON. It does not pull images, access lifecycle state, load credentials or execute a Contract operation. A caller preparing a Docker runner must cache the exact image pin on the host daemon; a Kubernetes runner needs its node cache, which is distinct. The four-Contract demo’s preparation task performs the appropriate verified pulls.

Failure-only runtime diagnostics separate image checks, runner startup and operation execution where evidence permits. An unresolved startup phase is not reported as proof that a request reached the producer. Diagnostics retain static codes, timings and recovery guidance, not raw tool stderr, credential-bearing arguments or response payloads. Existing successful probe output and exit-code meanings remain unchanged.

For reusable catalogue examples and explicit deployment selection, see Deployments and examples. For Connector selectors, Edges, native Secret references, locks and lifecycle safety, use the composition guide.

Validation and resolution are not live acceptance. Active probes run only for supported, explicitly configured Contract operations and transports. The walkthroughs state which endpoints are actually exercised and distinguish real producers, source-adapted integrations and synthetic fixtures.

The 0.4.0 release also supports the bounded native SPARQL query and metrics probes. SPARQL uses the fixed read-only ASK {} request through the selected service binding. Metrics stay under OpenAPI and validate the declared successful OpenMetrics 1.0.0 or Prometheus text 0.0.4 representation with official parsers. OpenMetrics requires EOF; Prometheus text has no EOF marker, so syntactically complete truncation cannot be detected. These checks do not imply arbitrary queries, updates, metric semantics, authorization or production acceptance. They are absent from the published v0.3.0 binary.

Current-source Kubernetes/Helm probes read retained logs only after checking the probe container’s completion and exit code. This avoids losing output emitted before an attach stream starts. Each probe executes once, with no hidden retry of an API operation or delivery. Cleanup uses the Pod’s create-time UID and a bounded deletion wait; replacement Pods are not adopted, and failed cleanup cannot produce successful acceptance. This hardening requires the matching source binary, not the original v0.3.0 release.

Ctrl-C or SIGTERM cancels the current Kubernetes probe, completes bounded UID-safe cleanup and stops subsequent selected operations. Recorded evidence reports CANCELLED (or RUNNER_CLEANUP_FAILED if cleanup fails); the command returns 130 for Ctrl-C or 143 for SIGTERM. Allow cleanup to finish before closing the terminal; force-killing the process cannot guarantee cleanup.

Versions and model authority

See Adopting DOT for compatible artifact sets, editor schema associations and the current-source, deployment-aware dotx tool check --dot <bundle> --deployment <exact-id> command. A successful prerequisite report is not live API acceptance.

DOT-Design and its pinned DOT-CLI source versions are kept aligned. Release installation instructions use the published binary; development demos and the diagnostics above may require the exact source revision pinned by the DOT-Design checkout, even when its version label matches a release. See Development and testing for source installation, Bash completion, local CI-equivalent Tasks and prerequisites.

All portable models belong to DOT-Domain. The CLI consumes its generated JSON Schemas and Go bindings; it does not define a competing DOT or Composition input model. Resolved execution details, lock fingerprints and private runtime state are executor concerns. DOT definitions and reusable composition inputs live in DOT-Repository.
