Complete model reference

Start with the domain overview, then use these chapters to understand each building block, its fields and its relationships. The inventory is discovered from the Java-generated schemas, not maintained as a second model.

  • Identity and capabilities: what a DOT represents, reusable Skills, audit timestamps and software versions.

  • Contracts and Connectors: owned specifications, selected interactions, roles and provider-neutral requirements.

  • Runtimes, deployment and configuration: platform versus mechanism, manifests, services, ports, configuration and requirements.

  • Connecting the DOTs: Composition Model Reference: Vertices, Edges, Connectors, Channels, deployment inputs, materializers, Secret references and security.

  • Probes and assertions: bounded checks for supported HTTP, GraphQL, gRPC and messaging profiles.

Download the comprehensive A4 reference for the same model explanations, generated field tables, relationships and examples. Its diagram page is landscape; the detailed chapters are portrait. The single-page A4 overview remains a compact visual companion, not a substitute for the detailed reference.

Complete class diagram

The complete Mermaid source and zoomable SVG include every public model, its declared instance fields, exact Java types and enum constants. Inherited fields appear on the superclass connected by an inheritance arrow; for example, Manifest.type applies to each concrete manifest. - denotes private fields and # protected fields. Accessors, validation methods and static implementation constants are omitted. JSON names and enum wire values are documented in the generated tables below (for example, JSONExpectation.expectedValue serializes as equals).

The overview and interface/runtime/composition diagrams use the same generated field inventory for every class they show. The separate single-page A4 overview remains a relationship map.

How to read a model entry

Each entry explains its purpose and use, followed by its generated fields, relationships and one JSON example. Field names, JSON types, enum values, base required properties and structural constraints come from the existing generated schema. Reviewed notes explain intent, invariants and common mistakes without redefining those shapes. Java and schema links lead to the authorities.

  • Required means required by the base schema for a full standalone value.

  • Conditional / optional means it is not unconditionally required by that base schema. A selected mode, parent context or cross-field rule can still require it. Follow the conditional schema and model validation.

  • A Java constructor default does not waive a required raw JSON property. This reference does not infer undeclared defaults from example values.

  • Schema enum lists values declared by that generated schema. It is not a promise that every value is valid in every owner: the field explanation and Java cross-field validation can narrow the set. For example, Compose, Kubernetes documents and Helm values accept only YAML or JSON.

  • A Skill reference inside Dot.skills, or a service-level Contract reference, intentionally carries only id; it is not the full entity shown by its standalone field table.

  • Relationships come from the existing Java-derived Mermaid graph. Multiplicities describe those associations; the schema and Java validation determine document validity. A supporting type can be used by several owners.

Follow the integration chain

For executable probes, pair the field reference with the supported probe profiles. Required transport, expectation and cleanup combinations are execution rules; a structurally valid fixture alone does not satisfy them.

  1. A Dot identifies a reusable tool release and references meaningful `Skill`s.

  2. Its owned Contract declarations locate exact specification bytes by URL/hash.

  3. A Connector selects one Contract interaction, expresses a supported requirement, or explicitly declares a contractless boundary.

  4. A Runtime offers compatible Deployment alternatives for one Platform.

  5. A deployment’s Service uses ConnectorBinding to connect logical interfaces to named `ServicePort`s and declares its supported configuration.

  6. A Composition selects DOTs through its Vertices. Each Edge connects two Vertices and contains one or more Channels. A Channel selects a Connector from the DOT chosen by each Vertex.

  7. DeploymentInputs and materializers supply reviewed instance-specific inputs; Secret references name secret sources without embedding their values.

  8. A Channel’s EdgeProbe declares a bounded acceptance check where the CLI supports it.

These relationships are not a packet-flow graph. In particular, PROVIDES to REQUIRES describes interface ownership and dependency, not who initiates a network request. See Connector authoring for the distinction between operation identity, data schemas and semantic meaning.

Examples and acceptance boundaries

The small DOT, interface, file-manifest, Helm values and configuration-default examples reuse the canonical Prometheus declaration and its actual URL/hash references. There is no catalogue EnvFile declaration: that example remains explicitly shape-only, from the Java compatibility corpus, not a downloadable dotenv recommendation. Other examples come from the same reviewed corpus and illustrate individual value shapes. They may use placeholder URLs, images or references requiring an enclosing graph; they are not runnable deployment recipes, producer claims or recommended product versions. Contracts are resolved from authoritative DOT declarations without a separate composition input list. Use Getting started for a real service, readiness checks and cleanup.

Java and generated-schema validation establish declaration invariants, not cross-DOT compatibility, downloads, network reachability, authentication or live producer conformance. The CLI performs the supported resolution and execution checks separately. Resolved compositions, lock digests, concrete endpoints and runtime state are CLI artifacts, not additional portable domain models.

Current source deliberately replaces former inline file documents with the shared Payload URL/hash value. Five file-document owners require it; ConfigFile.payload is optional and forbidden for sensitive files. There is no inline-text or Base64 fallback. Valid Contract JSON is unchanged, although Java callers replace ContractPayload with Payload. This approved change supersedes the former current-source payload freeze; published stable tags retain their historical model. Offline CLI validation requires every needed digest already cached, rehashes each read, and fails on missing or corrupt bytes rather than searching adjacent files or silently repairing them.

Maintaining the reference

From the DOT-Design source checkout, with its pinned catalogue and documentation toolchain available:

task docs:domain:generate
task docs:domain:check
task ci:docs

Generation discovers all exported types, reuses their Java/schema authority and the existing example corpus, and rejects missing prose, unexplained fields and orphan notes. Public documentation checks verify committed outputs and source hashes without requiring private catalogue access; they are not a replacement for the full source/schema drift gate. No deployment is performed.
