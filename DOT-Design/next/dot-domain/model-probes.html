Probes and assertions

How to read this reference explains full objects versus ID-only views, conditional fields and validation boundaries.

AsyncAPIProbe

Describe an active broker delivery check tied to the selected AsyncAPI operation and message.

The executor verifies the message against the Contract and injects fresh correlation at the selected pointer before testing delivery. Match the transport to the resolved broker bindings; stale or unrelated messages are not successful acceptance. This does not establish broker durability, production authorization or end-to-end business processing.

Java authority | Generated JSON Schema

JSON field Value Base presence Meaning and constraints

protocol

string

Required

Broker transport used to execute this delivery fixture. allowed: "MQTT", "NATS", "KAFKA", "AMQP".

message

object

Required

JSON message template whose application content is checked against the selected Contract message.

correlationPointer

string

Required

Location within the message where the fresh probe correlation value is inserted and later checked. pattern restrictions (see schema).

qos

integer

Conditional / optional

Requested MQTT delivery quality for the message exchange. minimum: 0; maximum: 2.

authentication

AsyncAPIProbeAuthentication

Conditional / optional

Broker login configuration for a supported authenticated probe.

Relationships

  • To AsyncAPIProbeAuthentication: containment via authentication; diagram multiplicity 0..1.

  • To AsyncAPIProtocol: typed association via protocol; diagram multiplicity 1.

  • From WireProbe: containment via asyncapi; diagram multiplicity 0..1.

Shape example from the reviewed Java compatibility corpus (not a runnable deployment)
{
  "protocol": "MQTT",
  "message": {
    "id": "demo"
  },
  "correlationPointer": "/id",
  "qos": 1
}

AsyncAPIProbeAuthentication

Provide broker login identity and a reference to its private password for an active delivery check.

The password stays in an executor-supported secret source rather than in the fixture. Whether authentication is supported and required depends on the selected transport and Contract bindings; this object does not configure the broker itself.

JSON field Value Base presence Meaning and constraints

Required

Login identity presented by the probe client. minimum length: 1.

AsyncAPIProtocol

Select the broker transport used by an AsyncAPI active probe.

This choice is separate from message ownership and must agree with the resolved transport binding and supported adapter. It does not declare that every feature of that broker protocol is implemented. Use the exact values emitted by the schema.

Java authority | Generated JSON Schema

Exact JSON values: MQTT, NATS, KAFKA, AMQP.

JSON representation: string; allowed: "MQTT", "NATS", "KAFKA", "AMQP".

Relationships

  • From AsyncAPIProbe: typed association via protocol; diagram multiplicity 1.

Shape example from the reviewed Java compatibility corpus (not a runnable deployment)
"MQTT"

GRPCProbe

Describe a reflection-based RPC check with a finite request and response sequence.

Choose the single-request or request-sequence form, not both, to match the selected RPC shape. The current profile relies on server reflection. Finite stream completion, response count and content assertions are separate checks; declaring a fixture is not proof that a server implements the RPC.

JSON field Value Base presence Meaning and constraints

Conditional / optional

boolean

Required

object

Conditional / optional

Single JSON request message for an RPC with a non-streaming request side.

requests

array of object

Conditional / optional

Ordered JSON messages supplied to a client-streaming request side. minimum items: 1.

responseCount

integer

Conditional / optional

Expected number of responses after the finite RPC completes. minimum: 1.

responseMatch

string

Conditional / optional

Which received responses must satisfy the content expectation. allowed: "ALL", "ANY", "FIRST", "LAST".

expect

JSONExpectation

Conditional / optional

JSON value assertion evaluated against the selected response messages.

  • To GRPCResponseMatch: typed association via responseMatch; diagram multiplicity 0..1.

  • To JSONExpectation: containment via expect; diagram multiplicity 0..1.

  • From WireProbe: containment via grpc; diagram multiplicity 0..1.

GRPCResponseMatch

Choose which responses in a finite RPC result must match an expectation.

Response selection does not replace the expected response count or the RPC completion check. Choose a policy appropriate to the operation instead of treating one matching streaming message as proof of the entire exchange. The schema owns the policy names.

Java authority | Generated JSON Schema

Exact JSON values: ALL, ANY, FIRST, LAST.

JSON representation: string; allowed: "ALL", "ANY", "FIRST", "LAST".

Relationships

  • From GRPCProbe: typed association via responseMatch; diagram multiplicity 0..1.

Shape example from the reviewed Java compatibility corpus (not a runnable deployment)
"ALL"

GraphQLOperation

Supply a supporting GraphQL operation within a probe sequence.

Use this for the verification, trigger or cleanup role selected by GraphQLProbe. The executor checks the document against the same verified schema and the operation kind required for that role; an operation name is not a substitute for the document.

object

Conditional / optional

Named GraphQL inputs for this supporting operation, separate from the main probe inputs.

GraphQLProbe

Describe a GraphQL query, mutation or subscription check against the selected interface.

The executable document must agree with the verified schema and selected operation. The current executor requires a verification query and cleanup mutation for mutation probes, and trigger and cleanup mutations for subscription probes; the transport must suit the operation. These are bounded acceptance fixtures, not a general GraphQL client or a guarantee of application rollback.

GraphQLTransport

Choose how the GraphQL probe operation is delivered.

Transport and operation kind are separate choices and must form an executor-supported combination. Selecting a streaming transport does not make a query a subscription or grant support for arbitrary GraphQL protocols. Use the exact schema spelling.

JSONExpectation

Assert that a selected part of a JSON result equals an expected value.

The pointer selects content, not a URL or query expression; an empty pointer selects the whole document. Explicit null is an expected value and must not be confused with an omitted equals field. Protocol-specific execution determines which result document is checked.

Java authority | Generated JSON Schema

JSON field Value Base presence Meaning and constraints

pointer

string

Required

JSON Pointer locating the value to compare within the result document. pattern restrictions (see schema).

equals

JSON value

Required

Expected JSON value, including an explicit null when that is the intended assertion.

Relationships

  • From GRPCProbe: containment via expect; diagram multiplicity 0..1.

  • From GraphQLProbe: containment via expect; diagram multiplicity 0..1.

  • From OpenAPIProbe: containment via expect; diagram multiplicity 1.

Shape example from the reviewed Java compatibility corpus (not a runnable deployment)
{
  "pointer": "/status",
  "equals": "ready"
}

OpenAPIProbe

Add a JSON response-value assertion to a supported OpenAPI wire probe.

The operation comes from the wire Anchor and verified Contract, not a second handwritten URL or operation definition. A successful HTTP status alone is different from a matched response expectation; executor restrictions still determine which operations can be probed.

Java authority | Generated JSON Schema

JSON field Value Base presence Meaning and constraints

expect

JSONExpectation

Required

Result-value assertion applied in addition to the native Contract response checks.

WireProbe

Choose a protocol-specific active-check fixture for a wire.

Select one protocol fixture matching the resolved Contract standard. Portable fixture validity does not promise that an executor supports every deployment, operation or transport combination. Active checks may call APIs or publish messages and must be deliberately selected; they are not passive topology inspection.
