Runtimes, deployment and configuration

How to read this reference explains full objects versus ID-only views, conditional fields and validation boundaries.

AnchorBinding

Maps a logical DOT Anchor to a named port of one deployment service.

Use an exact Anchor ID from the same DOT and an existing port name on the containing service. The binding connects logical interface selection to deployment structure; it does not contain a URL, credentials or a host-port publication rule.

Java authority | Generated JSON Schema

JSON field Value Base presence Meaning and constraints

anchorId

string

Required

The exact DOT-local Anchor identifier being materialized. minimum length: 1; pattern restrictions (see schema); conditional constraints (see schema).

port

string

Required

The name of the containing service port, not its numeric port value. minimum length: 1.

Relationships

  • From DeploymentService: containment via anchorBindings; diagram multiplicity 0..*.

  • To Anchor: ID/name reference via anchorId.

  • To ServicePort: ID/name reference via port.

Example derived from the canonical Prometheus definition (not a second product)
{
  "anchorId": "build-information",
  "port": "http"
}

CdiDeviceRequirement

Declares a service’s need for a device exposed through the Container Device Interface.

The DOT names a logical requirement and device kind, not a host device path or a concrete allocated device. Deployment inputs bind a fully qualified device of the matching kind. Device allocation, CDI specification installation and authorization remain operator or orchestrator responsibilities.

ConfigFile

Documents a configuration file expected by a service.

The path is the destination inside the workload, not a source file on the operator’s machine. An optional defaultContent is a shared Payload reference, never inline text or Base64; omit it when no default exists. Java null serializes as omission and does not expand raw-schema null acceptance. Instance inputs can supply replacement content. A sensitive file forbids every non-null default Payload, including an empty value or a publicly hosted document; a URL is not a secret-provisioning mechanism. This declaration alone creates no mount and does not verify remote bytes.

The media type describing how the file content should be interpreted.

defaultContent

Payload

Conditional / optional

Optional HTTPS URL and SHA-256 pin of the default file used when no instance replacement is supplied. It must be absent for a sensitive file.

description

string

Conditional / optional

An explanation of the file’s role.

path

string

Required

The destination path where the workload expects the configuration file. minimum length: 1.

required

boolean

Conditional / optional

Whether content must be supplied when the declaration provides none.

sensitive

boolean

Conditional / optional

Whether tooling must protect the file content as sensitive information.

  • To Payload: containment via defaultContent; diagram multiplicity 0..1.

  • From DeploymentConfig: containment via configFiles; diagram multiplicity 0..*.

Deployment

Describes one selectable deployment mechanism and the logical services it materializes.

The selected manifest, including its explicit pinned Payload references, is the complete deployment input; files beside dot.json are not an implicit fallback. Keep service IDs distinct within the deployment and select the deployment explicitly. Configuration belongs to each service, while instance names, live state and lifecycle ownership belong to the executor.

JSON field Value Base presence Meaning and constraints

id

string

Required

The stable name used to select this deployment alternative. minimum length: 1.

manifest

DockerImage or DockerCompose or KubernetesManifest or HelmChart or Vagrantfile or WebAssemblyModule

Required

The platform-specific specification used to create the workload. conditional constraints (see schema).

services

array of DeploymentService

Required

The logical services supplied by this particular deployment.

Relationships

  • To DeploymentService: containment via services; diagram multiplicity 0..*.

  • To DeploymentManifest: containment via manifest; diagram multiplicity 1.

  • From Runtime: containment via deployments; diagram multiplicity 1..*.

Shape example from the reviewed Java compatibility corpus (not a runnable deployment)
{
  "id": "image",
  "manifest": {
    "type": "DOCKER_IMAGE",
    "image": "docker.io/example/api:1.0.0"
  },
  "services": []
}

DeploymentConfig

Declares the configuration options and execution requirements supported by one service.

This is not a bag of applied operator values. Keep environment names, configuration paths, volume names and paths, and CDI requirement names unambiguous within the service; separate services can reuse those keys. Instance inputs supply overrides, storage bindings and secrets. Requirements never grant privileges by themselves.

DeploymentManifest

Provides the common base for concrete deployment specifications.

The existing type property selects the concrete manifest shape; it is not a second infrastructure selector. Supply the fields of that concrete manifest. Domain validation does not execute a payload, fetch a chart or establish deployment success.

DeploymentManifestType

Names how a workload is deployed and links that mechanism to its target platform.

Do not substitute this value for Platform.engine. The manifest subtype and its type must agree, and its target platform must match the enclosing runtime. Executor capabilities and installed tools remain separate from this model vocabulary.

DeploymentService

Describes a logical service provided by one deployment, including its interfaces and configuration surface.

Use stable service IDs for composition inputs and named ports for Anchor bindings. Contract entries are identity references, not copied declarations; their origin must resolve through the DOT interfaces. A logical service is not a native workload selector, and its host is not a promised public endpoint.

Conditional / optional

DockerCompose

References the exact Docker Compose document for a multi-container deployment.

The shared Payload identifies complete document bytes by HTTPS URL and SHA-256, not inline text, Base64 or a compose file beside dot.json. The format describes the downloaded document. Ordered environment-file references follow Compose precedence; instance overrides remain separate. Logical services and any native workload selection must agree with the selected deployment. Verification and cache readiness do not establish live deployment success.

DockerImage

Runs a pre-built container image as a Docker deployment alternative.

Reference a published image rather than expecting the CLI to build a nearby Dockerfile. Ordered environment-file payloads provide reusable defaults; later files and explicit instance environment values take precedence. DockerImageTag

Represents a container image tag as a compact JSON string.

Although Java exposes registry, image and version components, JSON uses one image-reference string, not an object containing those fields. The Java parser is tag-based and rejects digest references. Image-reference parsing alone does not verify registry availability, artifact integrity or executor support.

Java authority | Generated JSON Schema

JSON representation: string.

Relationships

  • From DockerImage: containment via image; diagram multiplicity 1.

EnvFile

References a reusable Docker-compatible environment document through a pinned Payload.

The URL must identify line-oriented dotenv bytes, not an adjacent file, inline string or Base64 content. The containing manifest determines ordering and override precedence. Keep deployment-instance values and credentials out of reusable documents; EnvFile is not a secret reference. Its compatibility-corpus example is shape-only: the current catalogue declares no EnvFile deployment.

Java authority | Generated JSON Schema

JSON field Value Base presence Meaning and constraints

Required

The shared Payload reference whose verified dotenv bytes are passed to Docker or Compose.

  • To Payload: containment via payload; diagram multiplicity 1.

The declaration explains the option; deployment inputs provide the applied value. A reusable default can be used when there is no override, but a sensitive option must not embed a default. Marking a value sensitive is not encryption or a substitute for secret provisioning.

HelmChart

References a Helm chart and preserves its reusable chart-level values.

Keep chart version separate from the represented tool release. The chart reference can use a repository or a self-contained OCI reference; an environment alias needs to be available where deployment runs. OciLinuxNamespace

Identifies a Linux namespace type in OCI execution requirements.

In hostNamespaces, this value requests sharing that namespace with the host, not creating a new isolated namespace. The serialized spelling follows OCI vocabulary. A model value is not permission to grant access, nor a guarantee of support by every adapter.

OciRuntimeRequirements

Declares additional Linux-container execution requirements using OCI vocabulary.

These are requests, not grants or unrestricted privileged mode. Compositions must explicitly authorize the declared set, and an adapter must fail closed when it cannot materialize the request. Duplicate declarations are rejected rather than silently removed during collection conversion.

Platform

Identifies the infrastructure targeted by a runtime, independently of its deployment mechanism.

Keep the platform version separate from the software release and chart version. Java construction defaults the engine to Kubernetes and the platform version to latest; those defaults do not waive required raw JSON properties. A platform declaration does not install the infrastructure or prove that its tools are available; the deployment environment resolves version selectors and checks readiness.

The shared Payload pins downloaded Ruby DSL bytes; it is not embedded code, Base64, a separately structured box declaration or an adjacent-file lookup. Review provisioning, mounts and networking before execution. Service configuration and instance overrides remain separate; verifying the document does not run or certify the virtual machine.

VolumeMount

Declares a logical storage mount expected by a service.

Keep the logical name and workload destination separate from a host bind path, named volume or persistent-volume claim. The instance supplies the concrete source and authorization. A declared read-only expectation must be enforceable by the selected adapter; it is not a storage allocation or a cleanup policy.

WebAssemblyExecution

Selects the WASI execution world expected by a WebAssembly artifact.

Match the artifact’s implemented world to the intended command or HTTP service behavior. Command arguments and HTTP service ports have different executor rules. This selector is not a generic promise to run every WebAssembly component or provide unrestricted operating-system access.

WebAssemblyModule

References exact WebAssembly bytes and the WASI execution world used to run them.

Keep the module location and checksum together so the adapter can verify bytes before execution. The standard adapter supports local/file and HTTPS locations, and command arguments apply only to CLI execution. Service-declared configuration, explicit directory preopens and adapter support determine available resources; choosing a world does not grant arbitrary host access.
