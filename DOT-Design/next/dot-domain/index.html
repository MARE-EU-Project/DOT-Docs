DOT-Domain model

DOT-Domain is the Java library for portable DOT and Composition declarations. It supplies the models and validation rules from which JSON Schemas and CLI input types are generated. It does not deploy services or manage databases.

Aggregate overview

Dot, Skill, Contract, and Composition are independently identified entities; their other model types are embedded values. For the conceptual relationships, start with DOTs for Dummies. This page covers Java integration and model maintenance.

Model overview and complete reference

Use the complete model reference for generated field tables, enum values, relationships, JSON examples and both downloadable references. The sections below link to its relevant entries instead of keeping a second field inventory here.

One model authority

All portable models, including Composition, originate in DOT-Domain. The Victools build produces Schema/schema.json, Schema/composition-v1.schema.json, and Schema/models/*.schema.json in the catalogue. The CLI uses generated Go bindings and embeds the Composition schema; it does not require Java at runtime.

From the DOT-Design checkout root, after an intentional model change:

mvn -pl DOT-Domain process-test-classes
task cli:domain:generate

Never hand-edit generated artifacts. Run task testing:composition:model to check generation drift and the shared compatibility corpus. See the contributor guide for the toolchain and full workflow gates.

Resolved compositions, locks, concrete endpoints, secrets and private lifecycle state remain executor concerns; they are not additional portable Java models. The architecture boundaries explain which component owns each fact.

Model baseline and compatibility

The published baseline is 0.4.0. Select dot-domain-models-0.4.0.tar.gz with its matching release manifest and checksums. The earlier dot-domain-models-0.3.0.tar.gz and historical corpus labels remain evidence of that earlier baseline, not the schema package for 0.4.0.

Preserve valid inputs and reviewed locks for the selected baseline. Source/API compatibility changes, migration steps and remaining gates are recorded in the compatibility policy and model specification. Neither a schema archive nor passing tests establishes live producer acceptance.

Deployment-free model gate

task testing:models

This runs the full Java/schema/Go/catalogue/lock gate without deploying workloads. Initial bootstrap may download pinned validation tools. Runtime acceptance (task ci:live), presenter qualification (task testing:demo), independent onboarding and owner approval remain separate.

Reference-aware validation and collection safety

Validate raw required-property presence with the generated schema before deserialization. Java constructor defaults cannot distinguish an omitted required property from an explicitly supplied default. Then use ordinary validator.validate(dot) for Jakarta Bean Validation and aggregate invariants.

For example, this Java builder creates a typed declaration; it does not connect to a broker or prove message delivery:

AsyncAPIProbe probe = AsyncAPIProbe.builder()
    .protocol(AsyncAPIProtocol.MQTT)
    .correlationPointer("/id")
    .build();

The portable IdentityReference group validates ID-only Skill and service Contract references. A standalone entity needs its complete declaration. Root Contracts use ContractDeclaration; model-level ID-only references remain readable, but catalogue/CLI publication requires complete owned declarations. The Java model performs no catalogue or network I/O: use full dotx validate for authoritative assets, selectors and cross-DOT resolution.

@ValidAnchor delegates aggregate reference and binding checks to AnchorValidator. Collection setters reject duplicate service IDs before constructing an ordered Set; validation also detects collisions after in-place ID mutation. @UniqueElements supplies the shared Java/schema list constraints, without blanket deduplication or reordering. Service configuration keys are unique within their own service, not across unrelated services.

Identity, versioning, and references

Use identity and capability entries for IDs, metadata, Skills and Version, and product/release conventions when publishing a catalogue bundle. Entity equality is ID-based; changing mutable fields does not regenerate identity.

Contracts

The Contract entry defines its fields. The representation matrix is the maintained standard/format/selector guide. Do not infer allowed owner combinations from the DataFormat enum alone.

Anchors and bindings

See Anchor model entries for fields and constraints, and Anchor authoring for operation selection, compatibility and deployment binding.

Runtime two-layer model

The Runtime and Platform entries explain platform versus mechanism. Java runtime validation checks deployment/platform alignment and distinct deployment IDs; enum membership alone does not promise executor support.

Deployment manifests

Use the manifest reference for subtype fields, exact discriminator values and examples. Adapter execution and supported runtime operations belong in the CLI guide.

Service configuration declarations

The configuration reference explains service-scoped defaults, files, storage and device/privilege requirements. Use the multi-service design guide to select logical services and native workloads. The payload migration covers retired file-document fields; it does not provide a local-file fallback.

Serialization and persistence adapters

  • Builder collections have initialized mutable defaults.

  • Optional null fields serialize as absent where specified; this does not imply that explicit JSON null is accepted. JSON assertions retain equals: null intentionally.

  • Jackson reference views serialize Skill and service Contract references as ID-only objects; validate them in the appropriate reference context above.

  • Preserve textual/UUID identifiers and version representations. The Java library has no database or ORM annotations; persistence belongs to adapters.

Java callers affected by collection-setter or shared Payload API changes must recompile. Consult the compatibility policy before exchanging an existing artifact set or migrating authored documents.

Class diagram

The complete generated Mermaid diagram shows every public type. The A4 reference sheet is the compact export; PlantUML export is also available. Detailed fields and examples remain in the complete reference.

Ordinary model builds leave committed exports unchanged. Follow reference maintenance to regenerate and check them through the existing Java/schema authority.

Build and test

From the DOT-Design checkout root:

# Library unit tests; no service or database required
mvn -pl DOT-Domain test

The Java build enforces 100% instruction and branch coverage. For schema regeneration, complete builds and test selection, use the contributor guide.
