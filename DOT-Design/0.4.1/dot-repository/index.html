DOT-Repository

Find a tool, choose its deployment and connect it to others. DOT-Repository is the version-controlled catalogue used by dotx. It holds reusable DOT definitions, capability references, generated schemas and reviewed compositions. It can be cloned independently of the DOT-Design development workspace.

New to the ecosystem? Start with DOTs for Dummies, then follow DOTs in Action to use and create real DOTs. For installation and repository access, use Getting started.

Find and inspect a DOT

Use one matching CLI/catalogue revision set. Released walkthroughs use the catalogue recorded in the CLI release manifest. For current-source work, use one DOT-Design checkout’s pinned CLI and catalogue; a version label alone does not identify later changes. See compatibility and access guidance.

With that CLI installed, run from the DOT-Repository checkout root:

dotx repository list --repository .
dotx repository inspect Prometheus@3.15.1 --repository .
dotx repository resolve Prometheus@3.15.1 --repository .

Expected: the discovered catalogue, details of that exact Prometheus release and the path to its dot.json. Inspection helps you choose an explicit deployment ID; it does not start a service. These commands create no workloads, so no runtime cleanup is needed.

Read the selected release’s adjacent README for prerequisites, supported deployment choices, interface limitations and the kind of evidence available. Use the Prometheus quickstart for an actual deployment, API check and cleanup. Many catalogue examples are previews rather than complete live walkthroughs.

Understand the layout

DOT-Repository/
  DOTs/
    external/<product>/<tool-release>/dot.json
    internal/<product>/<tool-release>/dot.json
    testing/...
  Skills/
  Compositions/
  Schema/
Directory What belongs there

DOTs/external/

Tools owned outside MARE. External ownership does not establish readiness.

DOTs/internal/

Components owned or developed within MARE.

DOTs/testing/

Clearly identified synthetic, source-adapted, planning or runtime-test definitions.

Skills/

Capability definitions referenced by the DOTs' textual Skill IDs.

Compositions/

Reusable use-case graphs with reviewed locks, README guidance and non-secret inputs.

Schema/

JSON Schemas generated from DOT-Domain. Catalogue authors do not define a second model here.

The DOTs/ filesystem is the index: definitions are discovered recursively. Current catalogue publication uses one product folder with exact release leaves. Each release has one canonical dot.json containing all its supported runtime/deployment alternatives. There is no mutable latest copy. The released tutorial’s pinned catalogue may retain the historical layout; identity-based CLI lookups avoid depending on either directory spelling. See products and supported releases.

Validate declarations

From the same DOT-Repository checkout root:

dotx validate .

This discovers the DOT definitions and reusable compositions, checks their applicable declaration rules and references, verifies declared URL/hash documents, and validates the required reviewed composition locks. Downloads may be needed. --offline requires an already verified cache; missing or corrupt bytes fail rather than silently changing the selected inputs.

Validation starts no workloads. It is separate from a successful deployment, live API acceptance and production readiness:

Evidence Meaning

Base/reusable validation

The selected declaration rules and applicable interface bindings pass.

Strict interface profile

--profile interoperable checks declared Contract coverage for Anchors and exposed service ports. Catalogue entries can still have explicit interface gaps.

Live acceptance

The recorded producer, deployment and operations passed the exercised runtime assertions, with a recorded cleanup result. It does not qualify every alternative or API.

Do not add placeholder Contracts to make a readiness result green. Prefer release-matched official specifications. Keep source-derived Contracts, explicit interface gaps, runtime-only components and test fixtures clearly identified. See readiness and integration limits.

Reuse and contribute

  • Use a DOT: inspect its exact release and follow its supported quickstart.

  • Improve a definition: keep the product identity, interfaces and deployment alternatives together. Follow safe DOT authoring and editing.

  • Add a use case: keep scenario-specific configuration outside product definitions. Use composition authoring, then review its topology and lock before any deployment.

  • Operate a composition: follow its own prerequisites, live assertions and ownership-safe cleanup. The composition walkthroughs explain the qualified paths and remaining boundaries.
