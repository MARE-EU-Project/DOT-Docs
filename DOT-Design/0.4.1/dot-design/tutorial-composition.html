3. Connect your DOT to another tool

Create and review a connection between your Prometheus definition and the catalogue’s Node Exporter, then verify that Prometheus scrapes its metrics. Continue in the same Bash shell after verifying Lesson 1’s standalone cleanup.

Goal: a reviewed two-DOT, one-Wire graph, a labelled scrape returning 1, and verified cleanup of its owned resources. You will learn: exact instance selection, provided-to-required Wires, configuration and reviewed inputs.

Create the use-case configuration

This file belongs to your monitoring use case, not to the shared product. The label will let you distinguish your configured scrape from an arbitrary successful Prometheus response:

(
set -euo pipefail
set -o noclobber
cat > "$LAB/prometheus.yml" <<'YAML'
global:
  scrape_interval: 5s
scrape_configs:
  - job_name: node-exporter
    static_configs:
      - targets: [node-exporter:9100]
        labels:
          tutorial: zero-to-hero
YAML
chmod 0644 "$LAB/prometheus.yml"
)

The file is non-secret. Mode 0644 lets the unprivileged Prometheus container read the mounted file; its enclosing workspace stays private. Do not apply these permissions to secret files. The initial target is a placeholder: the Wire will write the selected instance’s real host and port into the execution copy.

Create a fresh graph from the reviewed example

MONITORING_TEMPLATE="$DOT_REPOSITORY/Compositions"
MONITORING_TEMPLATE+="/node-exporter-prometheus-monitoring"
MONITORING_TEMPLATE+="/composition.yaml"
dotx compose new --from "$MONITORING_TEMPLATE" \
  --repository "$DOT_REPOSITORY" --name zero-to-hero \
  --output "$LAB/composition.yaml" --yes

Expected: a new UUID and a two-DOT, one-Wire preview. The template and its lock stay untouched. No lock is created for your draft and no service is deployed. The template’s configuration references are initially shared; redirect them before editing a configuration.

Read the draft before changing it:

Field Purpose in this graph

apiVersion, kind

Identify the generated Composition format, not a tool release or runtime.

id, name, version

A fresh ownership UUID, a readable use-case name and this graph’s version. The graph’s 1.0.0 is separate from each tool’s release.

dots

Named instances, exact tool identities, selected deployments and instance inputs. prometheus is an instance name; Prometheus@3.15.1 is its tool identity.

contracts

Verified interface inputs resolved from their exact owning DOTs, not copied specifications.

wires

Connections and the configuration needed to materialize them.

exposedAnchors

Names you can select with --forward, such as prometheus-query. An exposure does not add authentication.

Open $LAB/composition.yaml and make two changes. Use the editor/save workflow:

nano "$LAB/composition.yaml"

  1. Replace only the prometheus entry under dots with:

    Keep the four leading spaces shown before - name, matching the other DOT item in the CLI-created draft. YAML indentation is part of the document.

        - name: prometheus
      source: ./prometheus
      dotId: Prometheus@3.15.1
      dotVersion: 3.15.1
      deployment: docker-image
      dependsOn: [node-exporter]

    Before, this entry selected repository://Prometheus@3.15.1 and deployment docker. After, ./prometheus and docker-image select your private authored definition. Its identity, tool release and readiness dependency stay the same.

  2. In node-metrics-to-prometheus, change materializer.source to prometheus.yml. Keep the other Wire fields unchanged.

    Before, the source points to the template’s runtime/prometheus.yml (the draft may show its full absolute path). After, it names your own file beside the draft:

    materializer:
  type: CONFIG_FILE
  source: prometheus.yml

    This last snippet shows the changed field’s location, not the complete materializer: retain its existing valueFrom and target below these lines.

./prometheus selects your authored definition, not the catalogue’s deployment. The local docker-image ID comes from your dotx new output. Leave Node Exporter and the composition’s Contract inputs at their exact catalogue coordinates. The owned Prometheus Contract has the same verified bytes as that release’s catalogue declaration. Relative file paths resolve beside this YAML file.

Understand the connection

The retained Wire names these model relationships:

from: {instance: node-exporter, anchorId: node-metrics}
to: {instance: prometheus, anchorId: scrape-target}
materializer:
  type: CONFIG_FILE
  source: prometheus.yml
  valueFrom: ENDPOINT_HOST_PORT
  target:
    instance: prometheus
    service: prometheus
    path: /etc/prometheus/prometheus.yml
    jsonPointer: /scrape_configs/0/static_configs/0/targets/0

from provides metrics; to requires them. The materializer derives the producer’s address and places it at one location in the consumer’s configuration. It does not implement the scrape: Prometheus does that. dependsOn expresses startup ordering; a Wire expresses an interface connection.

In the pointer /scrape_configs/0/static_configs/0/targets/0, each 0 means the first item in a list. Follow scrape_configs to its first job, then static_configs to its first entry, then targets to its first value: node-exporter:9100 in your file. The materializer replaces that scalar with the selected producer’s address in the execution copy; your source file is kept as the input.

Node Exporter’s metrics operation uses a source-derived OpenAPI projection. It is not a vendor-published OpenAPI specification or complete OpenMetrics certification. Both sides select that same exact interface. The unprivileged exporter observes its container; this exercise makes no physical-host claim.

Validate, lock and preview

These are deliberate review steps: validate the edited declaration, create its lock, inspect the exact resolved inputs and topology, then preview deployment. The block stops if any step fails; it starts no services.

(
set -euo pipefail
dotx compose validate "$LAB/composition.yaml" \
  --repository "$DOT_REPOSITORY"
dotx compose lock "$LAB/composition.yaml" --repository "$DOT_REPOSITORY"
dotx compose inspect "$LAB/composition.yaml" \
  --repository "$DOT_REPOSITORY" --locked
dotx compose topology "$LAB/composition.yaml" \
  --repository "$DOT_REPOSITORY" --locked
dotx compose apply "$LAB/composition.yaml" \
  --repository "$DOT_REPOSITORY" \
  --locked --dry-run --forward "prometheus-query=$TUTORIAL_PORT"
printf 'Graph verified: two DOTs, one Wire. No service has started.\n'
)

Expected: two DOTs, one Wire and a deployment preview using your local docker-image definition. Review $LAB/composition.lock.json: it binds exact definitions, documents and configuration. A lock is reproducibility evidence, not runtime state or a second authored model. Intentional input changes require another explicit lock review; never regenerate locks just to hide an error.

Open the lock and check the selections
Where to look Expected fields and meaning

dots[], entry with instance: "prometheus"

source: "./prometheus", dotId: "Prometheus@3.15.1", deploymentId: "docker-image", and a digest beginning sha256: Your private definition and selected deployment are pinned by their bytes.

dots[], entry with instance: "node-exporter"

source: "repository://Node-Exporter@1.12.1", deploymentId: "docker", and a digest The exact catalogue release is selected.

inputs[], entry with source: "prometheus.yml"

A name beginning wire:node-metrics-to-prometheus:config: and a digest The Wire’s materializer uses the pinned input scrape configuration. This does not establish that a scrape has run.

Array order and digest values can differ. Relative source paths may be normalized (prometheus and ./prometheus select the same folder here). Stop if the selected sources or deployments differ: review your edits before regenerating the lock. Do not edit the lock by hand. These entries describe resolved inputs; the live query below checks the actual scrape.

Preview checkpoint

The preview is complete when validation, lock review, topology and dry-run succeed using your local Prometheus definition. No composition services have started yet. Continue below to run and verify the connection. If you choose only to review declarations, you can instead continue with Lesson 4’s declaration exercise; skip query and destroy for any graph you never applied.

Try a controlled diagnostic

Copy the YAML beside its original so relative inputs still resolve. This block refuses to replace an existing diagnostic file:

(
set -euo pipefail
set -o noclobber
cat "$LAB/composition.yaml" > "$LAB/diagnostic.yaml"
)

After that succeeds, open $LAB/diagnostic.yaml using the editor workflow. Change only node-metrics-to-prometheus’s `from.anchorId from node-metrics to missing-metrics, save, and run:

dotx compose validate "$LAB/diagnostic.yaml" --repository "$DOT_REPOSITORY"

Expect a nonzero exit and a missing-Anchor message naming missing-metrics in node-exporter. A different error is not the intended result. Restore node-metrics in that copy and repeat the same validation; it should succeed. Create no diagnostic lock and leave the reviewed original unchanged.

Run and ask a meaningful question

Use an unused TUTORIAL_PORT (default 19041). Before applying, keep the stop command below available. Run it even if apply or a query fails. Preserve the original workspace, cache and binary for recovery.

if test -n "${DOTX_TUTORIAL_DOCKER_ID:-}" &&
  current_docker_id="$(docker info --format '{{.ID}}')" &&
  test -n "$current_docker_id" &&
  test "$current_docker_id" = "$DOTX_TUTORIAL_DOCKER_ID"; then
  printf '%s\n' \
    'Starting Node Exporter and your Prometheus;' \
    'the next check waits for their labelled scrape...'
  dotx compose apply "$LAB/composition.yaml" \
    --repository "$DOT_REPOSITORY" \
    --locked --forward "prometheus-query=$TUTORIAL_PORT"
else
  printf '%s\n' \
    'Docker target is missing, changed or unreachable.' \
    'Restore the original Docker connection.' \
    'Do not replace its recorded ID.' >&2
  false
fi
(
set -euo pipefail
set -o pipefail
scraped=false
started=$SECONDS
next_notice=$SECONDS
printf '%s\n' \
  'Checking the labelled Node Exporter scrape through Prometheus...'
for ((attempt=0; attempt<90; attempt++)); do
  if curl --fail --silent --max-time 3 --get \
    --data-urlencode \
    'query=up{job="node-exporter",tutorial="zero-to-hero"}' \
    "http://127.0.0.1:$TUTORIAL_PORT/api/v1/query" |
    jq -e '.status == "success" and
      any(.data.result[]?; .value[1] == "1")' >/dev/null; then
    scraped=true
    break
  fi
  if ((SECONDS >= next_notice)); then
    printf 'Waiting for the scrape: attempt %s/90, %ss elapsed\n' \
      "$((attempt + 1))" "$((SECONDS - started))"
    next_notice=$((SECONDS + 5))
  fi
  sleep 1
done
if ! $scraped; then
  printf '%s\n' \
    'Scrape check timed out. Inspect compose status, then run' \
    'the Lesson 3 cleanup block before retrying.' >&2
  exit 1
fi
curl --fail --silent --show-error --max-time 5 \
  "http://127.0.0.1:$TUTORIAL_PORT/api/v1/status/buildinfo" |
  jq -e '.status == "success" and .data.version == "3.15.1"'
dotx compose status "$LAB/composition.yaml" \
  --repository "$DOT_REPOSITORY"
printf 'Verified: your labelled Node Exporter scrape is up (value 1).\n'
printf 'Try the same query in Prometheus: http://127.0.0.1:%s/\n' \
  "$TUTORIAL_PORT"
)

Expected: the check reports progress while waiting, build information returns true, status lists the selected instances, and a Verified: message confirms the labelled scrape. The loop permits up to 90 attempts with three-second HTTP timeouts and one-second pauses. Open the URL printed by the check (Prometheus with the default port) and evaluate. For a remote browser use the SSH forwarding instructions with this lesson’s selected port:

up{job="node-exporter",tutorial="zero-to-hero"}

The result 1 establishes your labelled scrape, not merely an HTTP 200. The label came from your configuration; the target address came from the Wire. The original catalogue and its configuration are unchanged.

Stop before extending

if test -n "${DOTX_TUTORIAL_DOCKER_ID:-}" &&
  current_docker_id="$(docker info --format '{{.ID}}')" &&
  test -n "$current_docker_id" &&
  test "$current_docker_id" = "$DOTX_TUTORIAL_DOCKER_ID"; then
  dotx compose destroy "$LAB/composition.yaml" \
    --repository "$DOT_REPOSITORY"
else
  printf '%s\n' \
    'Docker target is missing, changed or unreachable.' \
    'Restore the original Docker connection.' \
    'Do not replace its recorded ID.' >&2
  false
fi

Require Cleanup verified:: the CLI checked that the recorded containers, managed networks and disposable volumes are absent. Composition destroyed: alone is not that proof. If cleanup fails or is interrupted, restore Docker access and retry the original destroy command with the same draft, lock, cache and binary. Retained ownership receipts support that retry. The lab’s time-series data is disposable; do not prune unrelated resources. A later COMPOSITION_STATE_MISSING only means the lifecycle record is gone.

If the result differs

Symptom What to check before retrying

INPUT_YAML

Check the edited list item’s four leading spaces and the surrounding list. Do not add a second dots: key. Validate again before creating a lock.

A missing Anchor or a lock mismatch

Compare the exact instance, Anchor and local definition references with the reviewed edit. If an input changed intentionally, inspect it before explicitly recreating the lock. A new lock cannot repair an invalid reference.

No sample, or a sample with value 0

0 means the target’s scrape failed; no sample means the selected series is absent. Check lifecycle status, the node-exporter job, the tutorial label and the Wire’s materializer source. The API build-information check alone is insufficient.

A readiness or query timeout

Stop and use this lesson’s destroy command. Keep the original files, cache and binary if cleanup fails; use the recovery guide.

Checkpoint

Complete this lesson when the labelled query returns 1 and Cleanup verified: confirms absence of the owned resources. Keep the draft, lock and input file for Lesson 4. Preserve the original cache and binary while any cleanup is unresolved. The preview checkpoint alone establishes declaration review, not a working scrape.

Explain it back: which direction does this connection run?

The Wire points from Node Exporter’s provided Anchor to Prometheus’s required Anchor. At runtime, Prometheus sends an HTTP scrape request to Node Exporter. The Wire describes the interface relationship; the application implements the request. The materializer supplies its address through configuration.
