One Prometheus DOT, two runtimes

This optional presenter lane answers: "Can we reuse the same DOT without copying its product definition when the deployment runtime changes?"

The catalogue composition prometheus-docker-kubernetes-portability selects the existing configuration-docker-compose and configuration-kubernetes-manifest profiles of the same Prometheus DOT: ID Prometheus@3.15.1, upstream release 3.15.1. Both resolve its official OpenAPI Contract, use the same digest-pinned upstream image, and declare the same default self-scrape configuration and GOGC=75. No product descriptors, Contracts or default configurations are copied for this demonstration.

These are two independent servers with zero wires. This demonstrates deployment and configuration portability, not replication, data migration, or cross-runtime communication. Use the four-Contract demo for actual Docker-to-Kubernetes exchanges, and the secure-API composition for authentication and authorization between several products.

Prepare and preview

Run from the DOT-Design checkout root on Linux amd64. Install its exact pinned CLI using task cli:install; Go is needed for installation, not by the running binary. Follow the contributor checkout/tool guidance. The released v0.2.5 binary predates this lane’s cross-runtime repetition and restrictive-umask config-mode fixes; the version string alone is insufficient. Requirements: Task, Git, Bash, jq, curl, ss, GNU coreutils, Docker with Compose, kubectl and a Ready Linux-amd64 Minikube node with Docker runtime. Select context minikube. No Java, Kubernetes cluster provisioning or credentials are needed once those local prerequisites are installed and ready.

task testing:demo:portability:dry-run
task testing:demo:portability:prepare

The first command validates the reviewed lock and renders the two selected deployments without deploying anything. Temporary default-config files are materialized in an owned preview cache and removed on exit. The second command is explicit preparation, not read-only preflight: it pulls only the selected digest-pinned image into Docker and the Minikube node cache. It does not deploy the composition. Preparation requires registry access and does not imply live API acceptance or universally offline operation.

Present the comparison

# Optional: choose a fresh namespace and unused Kubernetes forwarding port.
export DOTX_PORTABILITY_NAMESPACE=dotx-prometheus-portability-presentation
export DOTX_PORTABILITY_KUBERNETES_PORT=19083
task testing:demo:portability:present

The Compose profile’s declared localhost port is 18919. Both host ports must be unused. Never delete an unknown workload to free them. The task refuses existing namespaces and Compose project resources; it does not adopt them.

The task then:

  1. Resolves the same canonical DOT/Contract for both instances and requires the same immutable image pin. It reads the image’s own --version output in a disposable, network-disabled container to establish the expected API version.

  2. Applies both native profiles through dotx compose apply and records status.

  3. Verifies the actual container/pod image identities, bounded readiness, official build-information version, runtime GOGC, default configuration and a real healthy self-scrape on both servers.

  4. Displays the locked topology, a live comparison table and inspection URLs, then holds the verified services for bounded inspection.

  5. Destroys only this run’s resources and verifies no Compose containers, networks, volumes, namespace, forwards or composition state remain.

The default selected image currently reports Prometheus 3.15.1; the assertion derives the version from its pinned bytes rather than assuming that a version label or two matching server responses prove provenance. The runtime receipts record actual image IDs and observation timestamps. The terminal table reports GOGC=75 and up=1 for each independently verified server.

Say: "The DOT identity and API Contract stay the same. The selected deployment mechanism, resource identities and endpoint change. That is reuse of one product definition, not two products that happen to have similar names."

While paused, open the displayed localhost URLs at /targets, or inspect the redacted result.json and each runtime’s receipt in the printed private run directory. The printed native status command includes the run’s cache and frozen kubeconfig; keep both when inspecting or recovering that run.

Press Enter to clean up. EOF, Ctrl-C and presenter timeout also invoke cleanup, but return a nonzero status. A successful demonstration requires the final cleanup=PASSED receipt. Native deployment details stay in apply.log; early Compose process failures retain bounded startup diagnostics before cleanup.

For noninteractive acceptance and an automated inspection/Enter rehearsal:

task testing:demo:portability:live
# Requires Python 3; also exercises a Kubernetes port override.
task testing:demo:portability:rehearse

Storage and acceptance boundaries

Data is disposable. Native Compose destroy removes this test project’s named TSDB volume. The selected Kubernetes profile has no persistent volume. This comparison does not move history between servers, prove persistence/backup semantics or certify every Prometheus API and deployment variant.

The CLI admits one native Kubernetes instance of this DOT alongside isolated Docker instances. It still rejects two native Kubernetes instances with fixed object names, including when a Docker instance separates them in the document. Do not bypass that guard or infer arbitrary same-namespace object isolation.

If interrupted, inspect the receipt and use the recorded cache/kubeconfig for native status/destroy on the same composition. Never substitute a new run’s cache, delete unrelated resources or strip namespace finalizers. The Anchor live E2E workflow offers this lane explicitly as prometheus-portability; dry-run CI exercises the same script. Runtime and fixture acceptance remain distinct from production certification.
